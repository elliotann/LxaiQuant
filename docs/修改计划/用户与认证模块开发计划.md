```
公开路径（无需认证）：
  POST /api/auth/login

  POST /api/auth/refresh
  GET  /api/auth/check-username
  GET  /api/auth/check-email
```

### 3.4 JWT 设计

```json
// Token 载荷
{
  "sub": "U000000000000001",     // userId
  "username": "admin",
  "role": "ADMIN",
  "iat": 1700000000,
  "exp": 1700086400
}

// Access Token：30 分钟过期
// Refresh Token：7 天过期（Redis 中持久化，撤销时删除）
```

### 3.5 Redis Token 黑名单

- logout 时将当前 Access Token 的 jti（JWT ID）加入 Redis，TTL = Token 剩余有效期
- JwtAuthFilter 中先检查 Redis 中是否存在该 jti，存在则拒绝
- Refresh Token 撤销：从 Redis 删除 refresh token 记录

### 3.6 前端适配

- `stores/auth.ts`：login 成功后存储 JWT，axios interceptor 自动添加 `Authorization: Bearer <token>`
- 新增 axios response interceptor：收到 401 时自动尝试 refresh token，失败则跳转登录页
- `router/index.ts`：路由守卫增加 JWT 过期检查

```sql
-- ============================================================
-- 权限表：定义系统中所有的操作权限
-- ============================================================
CREATE TABLE `permission` (
    `id`         INT          NOT NULL AUTO_INCREMENT,
    `perm_code`  VARCHAR(50)  NOT NULL COMMENT '权限编码，如 user:create, strategy:delete',
    `perm_name`  VARCHAR(100) NOT NULL COMMENT '权限名称，如 创建用户',
    `module`     VARCHAR(50)  COMMENT '所属模块，如 user, strategy, backtest',
    `create_time` DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_perm_code` (`perm_code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='权限表';

-- ============================================================
-- 角色表
-- ============================================================
CREATE TABLE `role` (
    `id`          INT          NOT NULL AUTO_INCREMENT,
    `role_code`   VARCHAR(30)  NOT NULL COMMENT '角色编码，如 ROLE_ADMIN, ROLE_PREMIUM',
    `role_name`   VARCHAR(50)  NOT NULL COMMENT '角色名称，如 管理员',
    `description` VARCHAR(255) COMMENT '角色描述',
    `create_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_role_code` (`role_code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='角色表';

-- ============================================================
-- 角色-权限关联表（多对多）
-- ============================================================
CREATE TABLE `role_permission` (
    `id`            INT       NOT NULL AUTO_INCREMENT,
    `role_id`       INT       NOT NULL COMMENT '角色ID',
    `permission_id` INT       NOT NULL COMMENT '权限ID',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_role_perm` (`role_id`, `permission_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='角色权限关联表';

-- ============================================================
-- 用户-角色关联表（多对多）
-- 用户表原有的 role 字段保留作为"主角色"快速判断，
-- 此表支持用户拥有多个角色的扩展能力
-- ============================================================
CREATE TABLE `user_role` (
    `id`       INT         NOT NULL AUTO_INCREMENT,
    `user_id`  VARCHAR(32) NOT NULL COMMENT '用户ID',
    `role_id`  INT         NOT NULL COMMENT '角色ID',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_user_role` (`user_id`, `role_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户角色关联表';
```

### 4.5 权限注册表 PermissionRegistry

```java
        new PermissionDef("backtest:advanced","高级回测", "回测管理"),

        new PermissionDef("membership:manage", "管理会员", "会员管理"),
```

**优点：** 加新接口时，加一行枚举就行，不需要手动去 DB INSERT。

### 4.6 权限缓存：Redis + 实时生效

用户权限信息**不走 JWT 载荷**（JWT 签发后不可吊销），改为**每次请求从 Redis 读取**：

```
请求 → JwtAuthFilter 解析 JWT 拿到 userId
     → 查 Redis: "permissions:{userId}"
         ├─ 有缓存 → 直接返回 Set<permCode>
         └─ 无缓存 → 查 DB → 写入 Redis（TTL 5分钟）→ 返回
     → 设置到 SecurityContext
     → @PreAuthorize 校验
```

管理员在前端修改角色权限时：
```
保存 → 后端更新 DB
     → 删除 Redis 中所有拥有该角色的用户的缓存键
     → 这些用户的下一次请求自动重新加载
```

**效果：** 最长延迟 = 下一次请求的时间，几乎实时生效。

### 4.12 数据权限管理

#### 设计目标

在资源权限（控制"能不能访问某个接口"）基础上，增加**数据权限**（控制"能看到哪些数据"）：

| 用户类型 | 数据范围 |
|---------|---------|
| **管理员（ADMIN）** | 所有用户的数据（不限制） |
| **普通用户（BASIC/PREMIUM）** | 只能看到自己的数据（`user_id = 当前用户`） |

#### 涉及表

| 表名 | 数据权限字段 | 说明 |
|------|-------------|------|
| `credits_log` | `user_id` | 积分变动记录 |
| `payment_transaction` | `user_id` | 支付交易记录 |
| `membership_subscription` | `user_id` | 会员订阅记录 |
| `recharge_address` | `user_id` | 充值地址 |
| `local_wallet` | `user_id` | 钱包余额 |
| `fund_flow` | `user_id` | 资金流水 |
| `t_member_third_account` | `user_id` | 第三方交易账号 |
| `user_role_rel` | `user_id` | 用户角色关联 |

以下系统级表不做数据过滤（所有人可见）：
- `sys_role`、`sys_permission`、`sys_role_permission` — 角色/权限定义是全局的
- `sys_menu` — 菜单配置全局共享
- `sys_dict` — 字典数据全局共享

#### 技术方案

采用 **MyBatis-Plus InnerInterceptor** + **注解标记 Mapper** 的方式，自动为 SQL 追加数据权限条件：

```
请求 → JwtAuthFilter（设置认证信息）
     → Service（调用 Mapper）
         → DataPermissionInterceptor（拦截 SQL）
             → 判断角色：
                 ADMIN  → 不追加条件（全量数据）
                 普通用户 → 自动追加 WHERE user_id = ?
             → 执行 SQL
```

**核心组件：**

1. `@DataScope(field = "user_id")` — 注解，标注在需要数据过滤的 Mapper 接口上
2. `DataPermissionInterceptor` — MyBatis-Plus `InnerInterceptor` 实现
   - 从 `SecurityContextHolder` 获取当前用户角色和 ID
   - 管理员 → 跳过，不拦截
   - 普通用户 → 通过 JSqlParser 解析 SQL，自动追加 `user_id = ?` 条件
3. `MyBatisPlusConfig` — 注册 `DataPermissionInterceptor` 到 `MybatisPlusInterceptor`

#### 实现要点

- `@DataScope` 注解只放在 **Mapper 接口**上，不放在 Service
- `DataPermissionInterceptor` 只拦截 SELECT 查询（`beforeQuery`），UPDATE/DELETE 按 ID 操作不受影响
- 用户信息从 `SecurityContextHolder.getAuthentication()` 获取，与 JWT 过滤器保持一致
- 使用 JSqlParser（MyBatis-Plus 3.5.x 内置依赖）解析 SQL，避免字符串拼接

### 5.4 积分扣减核心逻辑（乐观锁）

```sql
-- SQL 级原子扣减，避免并发超扣
UPDATE `user`
SET `credits_balance` = `credits_balance` - #{required},
    `version` = `version` + 1
WHERE `user_id` = #{userId}
  AND `credits_balance` >= #{required}
  AND `version` = #{version}
```

如果 `UPDATE` 影响行数为 0，说明余额不足或版本冲突，抛出 `InsufficientCreditsException`。

### 5.5 USDT 支付流程

```
用户选择积分包/套餐
       │
       ▼
后端创建 PaymentTransaction（status=PENDING）
返回 paymentAddress + memo
       │
       ▼
前端展示 TRC20 收款地址 + 金额（QRCode）
       │
       ▼
用户转账 USDT（链上）
       │
       ▼
TronGrid Webhook → POST /api/payment/callback
       │
       ▼
后端二次验证：
  1. 查询 tx_id 是否已处理（防重放）
  2. 调用 TronGrid API 确认交易状态
  3. 验证收款地址、金额、代币类型（USDT）
       │
       ▼
验证通过 → 更新订单状态为 SUCCESS
         → 增加积分 / 升级会员
         → WebSocket 推送通知到前端
```

## 七、关键风险与决策建议

### 7.1 风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| JWT 密钥泄露 | 所有 Token 可被伪造 | 密钥定期轮换 + 环境变量配置 + Redis 黑名单 |
| 乐观锁冲突（高并发扣积分） | 部分请求失败 | 重试机制 + 队列化扣减（MQ异步） |
| TronGrid Webhook 不稳定 | 用户支付后长时间未到账 | 前端轮询 + 手动补单后台 |
| RBAC 权限修改需重启 | 权限调整生效慢 | 缓存权限到 Redis，动态刷新 |
| 现有 UUID Token 用户平滑迁移 | 用户需重新登录 | 双 Token 并存过渡期 72h |

### 7.2 决策点

| 决策项 | 方案 B 选择 | 备选 |
|--------|-----------|------|
| 用户表角色字段保留 | 保留 `role` 作为主角色快速判断，`user_role` 表做多角色扩展 | 完全迁移到多表 |
| 乐观锁 vs SELECT ... FOR UPDATE | 乐观锁（版本号），避免锁表影响 | FOR UPDATE（高并发计费场景） |
| Redis 共享模块 | 复用 `ai-common` 的 Redis 配置，ai-member 增加 redis starter 依赖 | 独立 Redis 连接 |
| 支付回调验证 | TronGrid API 二次验证 + tx_id 防重放 | 仅信任 Webhook 签名 |
| 前端权限控制粒度 | 指令级 `v-permission` + 路由守卫 | 仅路由级控制 |

### 9.6 动态菜单前端改动

**背景**：左侧菜单改为从后端 API `/api/admin/menus` 动态获取，按用户权限过滤，不再硬编码在前端。

**修改文件：**

| 文件 | 改动 |
|------|------|
| `src/api/admin.ts` | 新增 `getMenus()` 方法调用 `GET /api/admin/menus` |
| `src/components/layout/SidebarNav.vue` | 完全重写：onMounted 时调用 `getMenus()` 获取菜单树 → 递归渲染分组/叶子节点 → 图标从字符串动态解析为 Element Plus 组件 → 当前路由高亮 → 点击 emit `item-click(routePath)` |
| `src/components/layout/V3Layout.vue` | 新增 `routeToTabKey` 映射表（routePath → tab组件key）；`handleNavClick(routePath)` 先映射到 tab key，无对应 tab 时 `router.push(routePath)` 直接路由跳转 |
| `src/views/DashboardLayout.vue` | 新增 `routeToTabKey` 映射表；`handleNavItemClick(routePath)` 先映射到 nav item key，无对应时 `router.push(routePath)` 直接路由跳转 |

**数据流：**
```
用户登录 → JWT Auth → GET /api/admin/menus
                           │
                    MenuServiceImpl.getMenuTree()
                      ├─ 查询 sys_menu（enabled=true）
                      ├─ 从 SecurityContext 获取用户权限
                      ├─ 过滤无权限的菜单
                      └─ 构建树结构返回
                           │
                           ▼
                    SidebarNav.vue 渲染菜单树
                           │
                    用户点击菜单项
                           │
                           ▼
                    emit("item-click", routePath)
                           │
                           ▼
              V3Layout/DashboardLayout.handleNavClick()
                ├─ routeToTabKey[routePath] 存在?
                │    ├─ 是 → 创建/切换到对应 tab
                │    └─ 否 → router.push(routePath)
                └─ 直接路由跳转
```

**图标映射规则**：`SidebarNav.vue` 中维护 `iconMap` 对象，将后端的图标字符串（如 `Monitor`, `TrendCharts`）映射到 Element Plus 图标组件实例，支持 20+ 图标类型。
