# 灵宝定时实时建议方案

## 一、现状分析

### 1.1 当前实时建议流程（聊天驱动）

```
用户前端聊天输入 (skill=live-advice)
  |
  +-> POST /api/agent/chat/stream （AgentController）
  |     |
  |     +-> AgentService.chatStream()
  |           |
  |           +-> SkillLoader.getSkill("live-advice")  → 加载 live-advice.md
  |           +-> enrichSystemPrompt()                  → McpTool.getContextData()
  |           |     |
  |           |     +-> QuantMarketTools.getContextData("live-advice", symbol)
  |           |           → 预取 ticker + 1h 分析 + 15m 分析 + 15m K 线
  |           |
  |           +-> AiServices.build(streamingChatModel, systemPrompt, tools)  → TokenStream
  |           +-> 返回流式 SSE 到前端
```

关键点：
- **触发条件**：必须有用户在聊天界面主动发消息
- **主体**：仅针对当前用户请求的单一 symbol
- **AI 能力**：`live-advice.md` skill 已经包含多周期分析（15m/1H/4H/1D）、趋势判断（高低点法）、入场/止损/止盈逻辑、风控建议（默认 100X 杠杆，单笔亏损 ≤ 1.5%）
- **行情注入方式**：通过 `enrichSystemPrompt()` 将 `QuantMarketTools.getContextData()` 预取的行情数据注入到 system prompt，而非让 AI 自行调用工具获取
- **信号生成**：前端解析 AI 返回的 JSON tradeplan，用户手动点击按钮后调 `/api/signal/create-from-advice` 生成信号

### 1.2 当前定时任务模式

系统已使用 XXL-JOB 分布式任务调度：

| 已有任务 | Cron | 用途 |
|---------|------|------|
| `liveTradingStrategyJob` | 每 5 分钟 | 实盘交易策略 |
| `dataSyncJob` | 每小时 | 数据同步 |
| `AnalysisScheduler` | 每 30 分钟 | 批量 AI 分析（@Scheduled + @Async） |

XXL-JOB 配置类：`XxlJobConfig.java`，执行器端口 9999。

### 1.3 存在的 gap

| 方面 | 现状 | 问题 |
|------|------|------|
| 触发方式 | 用户主动聊天 | 用户不看聊天时无法自动获取建议 |
| 覆盖范围 | 单次单 symbol | 无法批量监控多个品种 |
| 信号持久化 | HTTP 请求上下文内完成 | 定时任务中缺少可复用的服务层入口 |
| 更新频率 | 无规律 | AI 建议不能保持及时性 |

## 二、设计目标

在保留原有聊天驱动实时建议不变的前提下，**新增**定时自动执行模式，实现灵宝实时建议的**两种触发方式并存**：

1. **聊天驱动（原有）**：用户在聊天界面发消息触发 → 流式 SSE 回复
2. **定时触发（新增）**：XXL-JOB 按周期自动触发 → 系统内自动生成信号，WebSocket 推送

两种模式共享同一套核心 AI 分析逻辑（`live-advice.md` skill + `QuantMarketTools` 行情数据），仅在触发方式和输出形式上不同。具体目标如下：

1. **定时触发**：每 15 分钟 / 30 分钟 / 1 小时（可配置）自动调用 AI 分析
2. **批量覆盖**：对用户关注列表中的所有 symbol 逐个执行
3. **自动生成信号**：AI 返回的 tradeplan 自动解析并写入系统
4. **信号推送**：生成的信号实时推送到前端（STOMP WebSocket / 通知栏）
5. **兜底防打扰**：信号强度低于阈值时忽略，避免噪音

## 四、详细设计

### 4.1 复用 AgentService（不走独立 LLM 调用）

**核心思路**：ScheduledAdviceService 不单独调 LLM，而是通过 AgentService 加载 `live-advice.md` skill，与前端小灵宝使用**完全相同的 prompt 和行情注入逻辑**。

```
改造前: ScheduledAdviceService → LlmGenerateController.generateText() + 独立 prompt (live_advice_v1.md)
改造后: ScheduledAdviceService → AgentService.chat("live-advice", userPrompt, null) + skill (live-advice.md)
```

**AgentService.chat() 天然提供的优势**：
1. **Skill 一致性**：加载 `ai-agent/src/main/resources/skills/live-advice.md`，与前端聊天使用同一个 prompt
2. **行情注入一致性**：`enrichSystemPrompt()` → `QuantMarketTools.getContextData("live-advice", symbol)` 自动注入 ticker、1h 分析、15m 分析、15m K 线
3. **工具调用能力**：如需额外数据（如持仓），AI 可主动调用 `McpTool` 获取

**AgentService 所需改造**：

`AgentService` 目前有 `chatStream()`（流式，返回 TokenStream），`chat()`（同步）。如果 `chat()` 已存在则直接复用，否则增加同步方法：

```java
// AgentService 已存在的方法（直接复用）：
public String chat(String skillName, String userInput, String sessionId)  // 同步
public TokenStream chatStream(String skillName, String userInput, String sessionId)  // 流式
```

**ScheduledAdviceService.generateForSymbol() 改造伪代码**：

```java
public void generateForSymbol(String symbol, String accountId, String interval, BigDecimal leverage) {
    // 1. 构建 user prompt（与小灵宝聊天输入格式一致）
    String userPrompt = String.format(
        "请分析 %s（%s），账户 %s，杠杆 %s。根据当前行情自动给出交易建议。",
        symbol, interval, accountId, leverage
    );

    // 2. 调用 AgentService（复用 live-advice skill + QuantMarketTools 行情注入）
    String llmResponse = agentService.chat("live-advice", userPrompt, null);

    // 3. 解析 tradeplan JSON（与聊天模式解析逻辑一致）
    Map<String, Object> tradeplan = parseTradeplan(llmResponse);

    // 4. 创建信号（entryType 从 tradeplan 中取，不写死 MARKET）
    createSignal(adviceId, tradeplan, symbol, intervalEnum, latestPrice, leverage);
}
```

**关键变化对比**：

| 方面 | 改造前 | 改造后 |
|------|--------|--------|
| Prompt 来源 | `ai-quant/prompts/live_advice_v1.md` | `ai-agent/skills/live-advice.md` |
| 行情注入 | 手动 50 根单周期 K 线 + RSI | `QuantMarketTools.getContextData()` → ticker + 1h/15m 分析 + 15m K线 |
| LLM 调用 | `llmGenerateController.generateText()` | `AgentService.chat()` (langchain4j) |
| 工具调用 | 无 | 支持（McpTool） |
| 输出一致性 | 与小灵宝不一致 | **与小灵宝完全一致** |

### 4.3 LiveAdviceSchedulerService（定时任务编排层，需改造）

```java
@Service
public class LiveAdviceSchedulerService {

    /** 定时执行入口 */
    public void executeScheduledAdvice() {
        // 1. 检查开关
        if (!properties.isEnabled()) {
            return;
        }

        // 2. 获取待监控 symbol 列表（从配置或关注列表）
        List<SymbolConfig> symbolConfigs = properties.getSymbols();

        // 3. 逐 symbol 执行（带速率控制）
        for (SymbolConfig cfg : symbolConfigs) {
            if (RateLimiter.tryAcquire(cfg.getSymbol())) {
                try {
                    // 调用改造后的 ScheduledAdviceService（内部复用 AgentService）
                    AdviceResult result = scheduledAdviceService.generateForSymbol(
                        cfg.getSymbol(), cfg.getAccountId(),
                        cfg.getInterval(), cfg.getLeverage()
                    );
                    // 信号强度过滤
                    if (result.getSignal() != null && result.getSignal().getStrength() >= properties.getSignalStrengthThreshold()) {
                        signalService.batchSave(List.of(result.getSignal()));
                        signalPushService.pushToWebSocket(result.getSignal());  // STOMP 推送
                    }
                } catch (Exception e) {
                    log.error("定时建议执行失败, symbol={}", cfg.getSymbol(), e);
                }
            });
        } else {
                log.info("symbol={} 已到达速率限制，跳过本轮", cfg.getSymbol());
            }
        }
    }

    /** 获取待监控 symbol 列表 */
    private List<SymbolConfig> getMonitoredSymbols() {
        // 方案 A: 从用户关注列表中获取活跃 symbol（查 UserWatchlist 表）
        // 方案 B: 从配置文件中读取静态列表（ScheduledLiveAdviceProperties.symbols）
        // 一期推荐方案 B，后续可扩展为方案 A
        return properties.getSymbols();
    }
}
```

### 4.4 XXL-JOB JobHandler（定时任务入口）

```java
@Component

    @Override

```

### 4.5 各组件保持兼容

`LiveAdviceController` 的聊天驱动流程和 `AgentController` 均保持**完全不变**。定时模式不经过 Controller，直接由 `LiveAdviceSchedulerService` 调用 `AgentService`。

两者的调用路径完全独立：

```
聊天模式：用户前端 → AgentController → AgentService.chatStream() → SSE 流式回复
定时模式：XXL-JOB → LiveAdviceSchedulerService → ScheduledAdviceService → AgentService.chat() → 同步回复
```

### 4.6 监控列表获取方案

| 方案 | 描述 | 优缺点 |
|------|------|--------|
| **A. 用户关注列表** | 从 `user_watchlist` 表读取所有用户的所有关注 symbol | 覆盖面广，但多用户 symbol 过多时执行轮次太长 |
| **B. 静态配置列表** | application.yml 中配置 `live-advice.scheduled.symbols` | **简单可控，一期推荐** |
| **C. 动态推导** | 从用户交易记录/策略运行记录中自动推导 | 自适应强，实现复杂 |

**一期推荐方案 B（静态配置）**，原因：
- 系统已有 `ScheduledLiveAdviceProperties.symbols` 配置，零新增表
- 配置即可上线，无需额外前端页面
- 后续可扩展为方案 A：新增 `user_watchlist` 表，定时任务从中读取活跃用户的关注 symbol 并集，聚合后去重执行

### 4.7 信号过滤与防打扰

AI 定时输出的信号可能质量参差不齐，需要设置过滤规则：

```
AI tradeplan → 信号列表
  |
  +-> 1. signalStrength < threshold(默认40)？ → 丢弃
  +-> 2. 与已有信号比对，方向和入场价相近 → 去重合并（详见 4.13）
  +-> 3. 通过过滤 → 持久化 + 推送（详见 4.12）
```

### 4.11 信号与交易机器人挂钩

这是最关键的环节：定时生成的 TechnicalSignal 如何自动触发交易？现有体系中有**三条路径**可选。

#### 路径 A：信号驱动策略（推荐，零耦合）

**原理**：系统已有 `signalBasedStrategyImpl` 策略类型，运行中的机器人会定期扫描 `TechnicalSignal` 表，找到匹配的信号后自动创建订单。

```
定时建议 → TechnicalSignal (source=AI_LIVE_ADVICE_SCHEDULED, indicatorType=robotId)
                ↑ 匹配 signalSymbol + signalIndicatorType
                │
TradingBot (signalBasedStrategyImpl, 已运行中)
    │
    └─ DefaultDealStrategyTrade.signalBasedLogic()
         │  每 N 秒扫描 TechnicalSignal
         │  条件: signalDataFrom + signalSymbol = 当前交易对
         │        signalIndicatorType = 机器人ID
         │        status = PENDING
         │
         └─ 有有效信号？→ createTradeOrder() → TradeOrder
```

**配置示例**：
```yaml
# TradingBot 配置
bot:
  strategyType: signalBasedStrategyImpl
  tradingPair: BTCUSDT
  # 定时建议写入的 TechnicalSignal 需满足：
  #   signalDataFrom = bot 的 account.memberPlatform
  #   signalSymbol   = bot 的 tradingPair
  #   source         = AI_LIVE_ADVICE_SCHEDULED
  #   status         = PENDING
  # 机器人即会自动扫描到该信号并执行
```

**优点**：
- 完全解耦：建议只管生成信号，机器人只管消费信号
- 复用现有能力：`signalBasedStrategyImpl` 已有完善的信号过滤、仓位计算、风控逻辑
- 支持多机器人：同一信号可被多个不同配置的机器人消费或忽略

**缺点**：
- 机器人有自己的轮询间隔（秒级），信号到订单有延迟
- 需要保证 `signalIndicatorType` 的命名约定一致

#### 路径 B：定时建议直接下单（强耦合，不推荐）

**原理**：在 `LiveAdviceSchedulerService` 中，解析 tradeplan 后直接调用 `TradeOrderServiceAdapter` 创建订单。

```
定时建议 → LiveAdviceSchedulerService
    │
    ├─ ScheduledAdviceService.generateForSymbol() → tradeplan
    ├─ save TechnicalSignal (记录)
    └─ TradeOrderServiceAdapter.openOrder() → TradeOrder (直接下单)
```

**可能的问题**：
- 实时建议的 tradeplan 仅含方向/价格/仓位建议，缺少订单创建所需的完整字段（accountId、memberId、平台信息等），需额外补齐
- 跳过机器人的风控逻辑（止损止盈、仓位管理、加仓策略等），相当于裸下单

#### 路径 C：OpenClaw 外部机器人桥接

**原理**：系统已有 `OpenClawBridgeController`，外部机器人通过 HTTP 拉取信号并自行执行交易。

```
定时建议 → TechnicalSignal (存库)
                ↓
OpenClaw 机器人 → GET /api/openclaw/signals → 拉取 PENDING 信号
                ↓
OpenClaw 外部执行交易（不在本系统内）
```

**适用场景**：交易执行由外部机器人（如 OpenClaw）负责，本系统仅负责 AI 信号生成。

#### 推荐方案

| | 路径 A：信号驱动策略 | 路径 B：直接下单 | 路径 C：OpenClaw 桥接 |
|--|---|---|---|
| **耦合度** | 低（通过 DB 解耦） | 高 | 低 |
| **延迟** | 秒级（轮询间隔） | 即时 | 取决于外部拉取频率 |
| **风控** | 复用机器人风控 | 需自行实现 | 外部负责 |
| **侵入性** | 无需改现有代码 | 需新增下单调用 | 复用已有桥接 |
| **适用阶段** | 一期首选 | 不推荐 | 已有 OpenClaw 时选用 |

**一期推荐路径 A**，原因：
1. 系统已有 `signalBasedStrategyImpl`，完整可用
2. 定时建议只需保存 `TechnicalSignal`，与聊天驱动的信号格式一致（仅 `source` 不同）
3. 用户只需在机器人管理页面创建/启动一个 `signalBasedStrategyImpl` 类型的机器人即可
4. 零代码改动即可验证端到端流程

### 4.12 信号推送实现（SignalPushService）

**目的**：定时建议生成的信号需要实时推送到前端，让用户即时感知。

**服务类设计**：

```java
@Component
public class SignalPushService {

    @Resource
    private SimpMessagingTemplate messagingTemplate;  // Spring STOMP

    /**
     * 推送单条信号到 /topic/signals
     */
    public void pushSignal(TechnicalSignalDTO signal) {
        SignalPushMessage msg = SignalPushMessage.builder()
            .type("NEW_SIGNAL")
            .source(signal.getSource())             // AI_LIVE_ADVICE_SCHEDULED
            .symbol(signal.getSymbol())
            .direction(signal.getDirection())        // BUY/SELL
            .entryPrice(signal.getEntryPrice())
            .entryType(signal.getEntryType())        // MARKET/LIMIT/CONDITION
            .strength(signal.getStrength())
            .reason(signal.getReason())
            .generatedAt(signal.getGeneratedAt())
            .ttlMinutes(signal.getTtlMinutes())
            .build();

        messagingTemplate.convertAndSend("/topic/signals", msg);
    }

    /**
     * 批量推送（供 LiveAdviceSchedulerService 调用）
     */
    public void pushSignals(List<TechnicalSignalDTO> signals) {
        signals.forEach(this::pushSignal);
    }
}
```

### 4.13 信号去重策略

**问题**：每 15 分钟执行一次，相邻轮次可能生成方向、价位非常接近的重复信号，导致信号表膨胀和前端干扰。

**去重规则**（在 `TechnicalSignalServiceImpl.saveTechnicalSignal()` 中实现）：

```
对于新生成的信号 N：
  1. 查询最近 30 分钟内，symbol + direction 相同的未过期信号
  2. 如果存在已有信号 S，且 |N.currentPrice - S.currentPrice| / S.currentPrice < 1%：
     - 视为重复信号
     - 更新 S 的强度（取 MAX），更新 createTime 为最新时间，不新增记录
     - 策略：保留较新信号，合并强度取较大值
  3. 如果不存在重复，则正常插入
```

**实现位置**：`ai-signal` 模块 `TechnicalSignalServiceImpl.saveTechnicalSignal()` 中，在 hash 去重之后、实体转换之前插入语义去重逻辑。已完成 ✅

### 4.14 未完成信号跳过机制（方案 A：简单跳过 ✅ 已实现）

**问题**：定时任务每轮对同一个 symbol 生成信号时，如果上一轮的信号还没被交易系统处理（如 PENDING 挂单未成交、EXECUTING 执行中），再生成新信号会造成混乱。

**方案 A 实现**（已上线）：

```
generateForSymbol(symbol, ...) 入口：
  │
  +-> hasActiveSignal(symbol)？
  │     ├─ 查询 trade_signal 表，该 symbol 是否有 PENDING / EXECUTING / PARTIALLY_FILLED 的记录
  │     ├─ 有 → log.info("存在未完成的交易信号，跳过本次生成") → return null
  │     └─ 无 → 继续正常执行
  │
  +-> AgentService.chat() → LLM 分析...
  +-> createSignal() → 保存 + 推送
```

```java
private boolean hasActiveSignal(String symbol) {
    List<TradeStatus> activeStatuses = List.of(
        TradeStatus.PENDING, TradeStatus.EXECUTING, TradeStatus.PARTIALLY_FILLED
    );
    for (TradeStatus status : activeStatuses) {
        List<TradeSignal> signals = tradeSignalService.queryTradeSignalsBySymbolAndStatus(symbol, status);
        if (signals != null && !signals.isEmpty()) {
            return true;
        }
    }
    return false;
}
```

**效果**：只要该 symbol 还有未完成的交易信号（挂单中、执行中、部分成交），定时任务就不会再生成新信号，避免重复下单风险。挂单成交（FILLED）或取消（CANCELLED/FAILED）后，下次定时即可正常生成。

## 七、注意事项

### 7.1 LLM 限流

- AI 接口通常有 QPS/TPS 限制。`maxConcurrentSymbols=3` 控制并发数，`symbolIntervalMs=3000` 控制间隔
- 按 symbol 维度做 `RateLimiter`，避免同一 symbol 在短时间内被重复分析
- 考虑使用信号去重（相同 symbol + 相同方向 + 入场价偏差 < 1% 的视为重复信号，忽略）

### 7.2 信号时效性

- 定时建议生成的信号应设置 `ttlMinutes`（默认=时间间隔，如 15 分钟）
- 超时未处理的信号自动过期，前端标记为过期信号
- 用户界面显示信号生成时间，帮助判断时效性

### 7.3 关注列表为空

- 如果用户没有设置任何关注 symbol，定时任务应跳过执行并记录日志
- 建议在云平台后台或配置页面提供一个默认监控列表作为 fallback

### 7.4 多用户 vs 系统级

定时建议的监控列表配置是**全局配置**。如果多用户需要各自独立的定时建议，则需改造为**用户级配置**，复杂度剧增。

**建议**：一期先做系统级（单 config 控制所有监控 symbol），后续扩展为用户级关注列表。

### 7.5 与现有 AnalysisScheduler 的区别

| | AnalysisScheduler | 本方案 |
|--|------------------|--------|
| 用途 | 技术指标趋势分析 | AI 实时建议 + 自动信号 |
| 数据来源 | 技术指标 | AI (LLM) |
| 输出 | 分析报告存入数据库 | TechnicalSignalDTO |
| 执行频率 | 30 分钟 | 15 分钟 / 1 小时可配 |
| 触发方式 | @Scheduled | XXL-JOB |
| 展示位置 | 分析报告列表 | 实时信号列表 + WebSocket 推送 |

## 九、后续优化方向

### 9.1 方案 B：旧信号取消 + 新信号覆盖

方案 A 简单跳过可能导致在趋势行情下错失机会。方案 B 改为：
- 发现同 symbol 有 PENDING 信号时，不是跳过，而是先将旧信号 **取消**（CANCELLED）
- 再正常生成新信号
- 适用场景：趋势行情中，AI 最新判断比几分钟前的判断更有价值

```java
// 伪代码
private void cancelExistingAndProceed(String symbol) {
    List<TradeSignal> pending = tradeSignalService.queryPendingTradeSignals(symbol);
    for (TradeSignal sig : pending) {
        tradeSignalService.cancelTradeSignal(sig.getId(), "被新AI定时信号覆盖");
    }
    // 继续正常生成
}
```

**注意**：如果旧信号已经在交易所有挂单（PARTIALLY_FILLED），则需要先撤单再取消，涉及交易所 API 调用。

### 9.2 方案 C：与交易所状态同步

方案 A/B 只检查数据库状态，但如果数据库和交易所实际状态不一致（如系统重启丢失状态），仍可能重复下单。

- 生成信号前，先通过交易所 API 查询该 symbol 的**实际未成交挂单**
- 如果有挂单，先撤单（或跳过）
- 确保数据库状态与交易所状态一致后再生成新信号

**复杂度**：高。需要接入 `ITradeService` 或 `ExchangeOrderService` 调用交易所撤单接口。

### 9.3 方案 D：时间窗口抑制 + 方向反转检测

结合方案 A 和策略灵活性：
- 同 symbol 未完成信号 → 跳过（同方案 A）
- 但如果新信号方向和当前持仓方向 **相反**（如做多→做空），视为反转信号：
  - 先平仓（FILLED 状态已有持仓）
  - 再生成新反向信号
- 适用场景：趋势反转行情，AI 判断转向后需要立即响应

### 9.4 方案 E：信号强度阈值动态过滤

根据市场波动率动态调整信号强度阈值：
- 高波动时期（如 ATR > 均值 2σ）：提高阈值，过滤噪音信号
- 低波动时期：降低阈值，抓住关键机会
- 结合 `ScheduledLiveAdviceProperties.signalStrengthThreshold` 配置

### 10.9 是否需要配置 TradingBot + Strategy

**不需要。** AI 定时信号与现有的 Bot + Strategy 系统是两条独立的链路。

**两条链路对比：**

| | **AI 定时信号（本方案）** | **Bot + Strategy 系统（已有）** |
|---|---|---|
| 信号来源 | LLM 分析（`AgentService`） | 技术指标计算（`SignFactory`） |
| 执行方式 | XXL-JOB 定时触发，每次跑一轮 | `TradingBot` 启动后无限循环处理K线 |
| 是否自动下单 | ❌ **只生成信号 + WebSocket 推送，不自动下单** | ✅ 会自动调用 `TradeOrderService.createOrder()` |
| 配置要求 | 只需 `application.yml` 的监控列表 | 需前端配置 `TradingBot` + `Strategy` |
| 前端展示 | 小铃铛通知 + K线页面信号指示器 | 走 Bot 后台，独立展示 |
| 是否需要 Bot | ❌ 不需要 | ✅ 必须 |

**核心结论：** 当前 AI 定时信号是"建议推送"模式——LLM 分析出方向/入场价/强度，通过 WebSocket 推送给用户做参考，**不具备自动下单能力**。

**如果后续需要让 AI 信号自动下单，有两种方案：**

1. **新增 XXL-JOB 消费信号**：新建一个定时任务，扫描 `technical_signal` 表中 PENDING 状态的 AI 信号，直接调用 `TradeOrderService.createOrder()` 下单。
   - 优点：独立于 Bot 体系，实现简单
   - 缺点：缺少 Bot 的风控/加仓/分批平仓能力

2. **集成到 Bot 体系**：改造 `SignalCacheManager` 或 `SignalMultiDirectionStrategy`，让现有 TradingBot 也能消费 AI 生成的 `TechnicalSignal`。这样 Bot 的风控、加仓、分批平仓能力全都能用上。
   - 优点：复用 Bot 完整能力
   - 缺点：改造成本较高

**建议**：实盘模拟测试阶段先用"只推送、不下单"模式验证 AI 信号的准确性。验证通过后再实施方案 2（集成到 Bot 体系），让 AI 信号通过 Bot 自动执行下单。
