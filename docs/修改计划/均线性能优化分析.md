# 均线（MA）选择卡顿性能优化分析

## 一、问题描述

在 K 线页面选择「均线」指标后，页面出现明显卡顿，响应缓慢。

## 二、相关源码分析

### 2.1 用户操作链路

```
用户点击「均线」checkbox
  → setIndicator('ma', true)
    → indicators.value = { ...indicators.value, ma: true }  // Vue 响应式触发
    → maConfig.value.enabled = true
    → nextTick(() => updateMA())
```

### 2.2 updateMA() 执行链路

```
updateMA()
  → 4x chart.value.addSeries(LineSeries, { ... })    // 创建 EMA9/21/55/144 线
  → 4x emaArray(closes, period)                      // 计算 EMA（全量数据）
  → 4x series.setData(lineData)                       // 设置数据（触发渲染）
```

### 2.3 关键数据量

| 项目 | 数值 |
|---|---|
| `MAX_CACHE_SIZE` | 5000 根 K 线 |
| `LOAD_BATCH_SIZE` | 300 根 |
| 均线条数 | 4 条（EMA9/21/55/144） |
| 每次 `setData()` 数据量 | ~5000 点 |
| 新增 DOM/线层数 | 4 条 LineSeries |

## 三、性能瓶颈分析

### 3.1 首次开启：4 次 addSeries() 调用（瓶颈 #1）

**问题**：`updateMA()` 中，当 `maSeriesRef` 为空时，会连续 4 次调用 `chart.addSeries(LineSeries)`。

LightweightCharts 每次 `addSeries()` 都会触发：
- 价格刻度重算（pane 0 已有的 CandleSeries + 新增的 LineSeries）
- 内部数据结构初始化
- 布局重排

**影响程度**：高。4 次连续调用累积开销大。

### 3.2 4 次 setData() 触发多次渲染（瓶颈 #2）

**问题**：每条 EMA 线独立调用 `setData(lineData)`，每条都携带 ~5000 个数据点。

LightweightCharts 的 `setData()` 是同步操作，每次调用都会：
1. 校验数据格式
2. 更新内部数据索引
3. 触发 Canvas 绘制
4. 触发自动缩放

**影响程度**：高。4 次 `setData()` 导致 4 次重复渲染。

### 3.3 全量数据重复计算（瓶颈 #3）

**问题**：`emaArray()` 每次被调用时都从第 1 根 K 线开始计算。

`emaArray()` 虽然是 O(n)，但 4 个周期独立计算，没有复用中间结果。

**影响程度**：中。纯计算耗时占比不高，但累积增加可感知延迟。

### 3.4 Vue 响应式级联触发（瓶颈 #4）

**问题**：`setIndicator` 中使用对象展开创建新引用：

```
indicators.value = { ...indicators.value, [name]: checked };
```

这创建了一个全新的对象，所有依赖 `indicators` 或其属性的计算属性/watch 都会重新求值。

**影响程度**：低-中。

### 3.5 额外发现：loadByTime 中无条件调用所有 updateXxx() 函数

**问题**：数据加载后，`loadByTime` 中无条件调用了 13 个 `updateXxx()` 函数，即使指标未启用也会执行 cleanup 判断：

```javascript
function loadByTime(...) {
  ...
  updateMA();
  updateMACD();
  updateRSI();
  updateBOLL();
  updateCAL();
  updateSAR();
  updateVOLUME();
  updateOBV();
  updateCANDLE();
  updateKalman();
  updateSUP();
  ... // 其他 updateXxx
}
```

**影响程度**：低。每个 `updateXxx` 在指标未启用时只做 `if (!seriesRef) return` 判断，开销很小。

### 3.6 真正瓶颈定位

经过分析，**真正的瓶颈排序**是：

1. **#1（最重要）**：**4 次 setData() 触发 4 次 Canvas 渲染** — 每次 setData(5000 点) 都会触发 LightweightCharts 内部完整渲染管线
2. **#2**：**首次 addSeries() 创建 4 条 LineSeries** — 价格刻度重算开销
3. **#3**：**emaArray() 全量计算** — 纯 CPU 计算，但现代浏览器 20k 次简单浮点运算在 5ms 以内，占比不高

## 四、优化方案

### 方案 A：批量操作 + requestAnimationFrame（推荐快速实施）

**思路**：减少重复的 setData 调用次数，利用 requestAnimationFrame 合并渲染。

```javascript
async function updateMA() {
  if (!chart.value) return;
  const cfg = maConfig.value;
  const data = dataCache.value;
  if (!data.length) return;

  const chartApi = chart.value;
  const currentSeries = maSeriesRef.value;
  const opens = data.map((d) => d.open);
  const closes = data.map((d) => d.close);
  const highs = data.map((d) => d.high);
  const lows = data.map((d) => d.low);

  // 目标：所有 addSeries + 所有 setData 合并到一个渲染帧
  const promises: Promise<void>[] = [];

  for (const [refKey, period] of [['ema1', 9], ['ema2', 21], ['ema3', 55], ['ema4', 144]]) {
    if (currentSeries[refKey]) continue;
    currentSeries[refKey] = chartApi.addSeries(LineSeries, { ... });
  }

  // 等待下一帧（给 addSeries 足够时间合并布局）
  await new Promise(r => requestAnimationFrame(r));

  const lines = [
    { ref: 'ema1', values: emaArray(closes, 9), label: 'EMA9' },
    { ref: 'ema2', values: emaArray(closes, 21), label: 'EMA21' },
    { ref: 'ema3', values: emaArray(closes, 55), label: 'EMA55' },
    { ref: 'ema4', values: emaArray(closes, 144), label: 'EMA144' },
  ];

  for (const line of lines) {
    const series = currentSeries[line.ref];
    if (!series) continue;
    const lineData = [];
    for (let i = 0; i < data.length; i++) {
      const v = line.values[i];
      if (v != null) lineData.push({ time: data[i].time, value: v });
    }
    series.setData(lineData);
  }
  // 所有 setData 也在同一帧完成
}
```

**改动量**：低。仅修改 `updateMA()` 内部逻辑。
**预期效果**：减少 ~60% 的重复渲染开销。

### 方案 B：可见范围裁剪

**思路**：只对当前可视区域的数据点进行 setData，而非全量 5000 点。

```javascript

  ...

  if (!logicalRange) return;
  const startIdx = Math.max(0, Math.floor(logicalRange.from));
  const endIdx = Math.min(data.length - 1, Math.ceil(logicalRange.to));
  const visibleData = data.slice(startIdx, endIdx + 1);
  const visibleCloses = visibleData.map(d => d.close);
  // 只对 visibleData 计算 EMA
  ...
  // setData 时只设 visibleData 范围的 200-400 点
  ...
}
```

**改动量**：中。需要处理缩放/平移时重新计算。
**预期效果**：setData 数据量从 5000 点降至 200-400 点，渲染开销减少 ~90%。

## 五、方案 D：延迟加载骨架屏（深入讨论）

### 5.1 核心思路

```
用户点击「均线」
  → 立即创建 LineSeries（无数据）
  → 立即加载 MA 占位骨架线（如用简单 SMA 近似，计算极快）
    或使用 rAF 延迟后直接全量加载（感知优化）
  → 完整数据就绪后，替换骨架线
```

### 5.2 具体实现路径

#### 5.2.1 两条骨架线实现

```javascript
async function updateMA() {
  if (!chart.value) return;
  if (!indicators.value.ma) { /* cleanup */ return; }

  const cfg = maConfig.value;
  const data = dataCache.value;
  if (!data.length) return;

  const chartApi = chart.value;

  // step 1: 先创建所有 series（无数据），addSeries 开销不可避免但只做一次
  const seriesMap = { ema1: null, ema2: null, ema3: null, ema4: null };
  for (const key of Object.keys(seriesMap)) {
    if (!maSeriesRef.value[key]) {
      maSeriesRef.value[key] = chartApi.addSeries(LineSeries, { ... });
    }
  }

  // step 2: 骨架线 — 用最后 50 根 K 线计算近似 MA，秒出
  const previewCount = 50;
  const previewData = data.slice(-previewCount);
  const previewCloses = previewData.map(d => d.close);

  for (const [key, period] of [['ema1', 9], ['ema2', 21], ['ema3', 55], ['ema4', 144]]) {
    const series = maSeriesRef.value[key];
    if (!series) continue;
    const values = smaArray(previewCloses, period); // SMA 计算比 EMA 更快
    const lineData = [];
    for (let i = 0; i < previewData.length; i++) {
      if (values[i] != null) lineData.push({ time: previewData[i].time, value: values[i] });
    }
    series.setData(lineData); // 只设 50 点，极快
  }

  // step 3: 下一帧加载全量数据
  await new Promise(r => requestAnimationFrame(r));
  const closes = data.map(d => d.close);
  for (const [key, period] of [['ema1', 9], ['ema2', 21], ['ema3', 55], ['ema4', 144]]) {
    const series = maSeriesRef.value[key];
    if (!series) continue;
    const values = emaArray(closes, period);
    const lineData = [];
    for (let i = 0; i < data.length; i++) {
      if (values[i] != null) lineData.push({ time: data[i].time, value: values[i] });
    }
    series.setData(lineData); // 全量替换
  }
}
```

#### 5.2.2 无骨架线实现（纯 rAF 延迟）

更简单：直接加一个 `await requestAnimationFrame` 延迟，让 UI 先响应。

```javascript
async function updateMA() {
  ...
  // 先让 checkbox UI 变化渲染完成
  await new Promise(r => requestAnimationFrame(r));
  // 再开始 MA 计算和渲染
  ...
}
```

### 5.3 方案 D 优缺点分析

| 维度 | 评分 | 说明 |
|---|---|---|
| **用户体验** | ★★★☆☆ | 用户先看到骨架线再看到精确线，有两次视觉变化。如果预览线和全量线差异大，会明显"跳动" |
| **实现复杂度** | ★★☆☆☆ | 高。需要管理骨架/全量两个状态，处理极端情况（快进、缩放、数据更新） |
| **对真实瓶颈的作用** | ★☆☆☆☆ | **不能解决 addSeries 和 setData 的根本开销**，只是把卡顿分摊到两个阶段 |
| **代码可维护性** | ★★☆☆☆ | 需要维护两套渲染逻辑，状态管理复杂 |
| **与其他指标兼容性** | ★★★☆☆ | 如果其他指标也用类似模式，复杂度翻倍 |

**关键结论**：方案 D 本质上是一个**体验优化**（让用户感觉更快），而非性能优化（实际总耗时更多，因为计算了两次）。LightweightCharts 的渲染瓶颈没有被减少。

## 六、后端计算方案（与方案 D 对比讨论）

### 6.1 后端方案核心思路

利用现有的后端架构优势：

```
前端点击「均线」
  → POST /api/v1/kline/indicator/ma
    { symbol, interval, periods: [9, 21, 55, 144] }
  → 后端从数据库查询 K 线
  → 使用 ta4j 的 EMAIndicator 计算
  → 返回计算结果
  → 前端直接 setData 渲染（跳过计算环节）
```

### 6.2 现有基础设施

项目**已有完整技术储备**：

| 组件 | 已存在 | 位置 |
|---|---|---|
| **ta4j EMAIndicator** | ✅ 稳定实现 | `ta4j-core: EMAIndicator` |
| **BarSeries 构建** | ✅ `IndicatorWrapHelper.buildSeries()` | `ai-data/utils/IndicatorWrapHelper.java` |
| **K 线数据查询** | ✅ `candlestickService.getLastKlines()` | `ai-quant:KLineV1ServiceImpl` |
| **指标计算 API 模式** | ✅ `TrendlineController` + `TrendlineService` | `ai-quant:controller/market/TrendlineController` |
| **K 线指标 API 端点** | ✅ 已有占位 `/api/v1/kline/indicator` | `KLineV1Controller.calculateIndicator()` |

### 6.3 后端计算与前端计算的对比

| 对比维度 | 前端计算（现状） | 后端计算（新方案） |
|---|---|---|
| **计算耗时** | 5ms (5000点 × 4EMA) | <1ms（服务端更快，但差异可忽略） |
| **数据传输量** | dataCache 已在前端，无需额外传输 | 返回 4 × ~5000 点 ≈ 80KB，有网络延迟 |
| **setData 渲染** | 仍触发 4 次 ~5000 点渲染 | 仍触发 4 次渲染，数据量相同 |
| **数据裁剪能力** | 受限，需保持 dataCache 全量数据 | ✅ 后端可只返回可视范围或降采样数据 |
| **占用主线程** | ❌ 计算 + 渲染都在主线程 | ✅ 不占用主线程，但网络请求也有开销 |
| **复用计算** | 不支持，每次开关都重算 | ✅ 可用 Redis 缓存计算结果 |
| **后端 CPU 负载** | 无 | 低（EMA 计算是 O(n) 简单运算） |
| **架构复杂性** | 低 | 中（需维护 API + 处理实时更新） |

### 6.4 后端方案的真正价值

**#### 关键点：前端真正瓶颈在 setData 渲染，不在计算**

纯 JS 计算 5000 点 × 4 条 EMA 仅需约 5ms，而 `setData()` + Canvas 渲染需要 ~100ms+。**即使把计算搬去后端，setData 渲染瓶颈依然存在。**

所以后端方案的真实价值在于：

**1. 数据降采样（最重要）**

后端可以返回经过降采样的数据，减少 setData 的数据量：

```
当前：前端的 dataCache 有 5000 根 K 线
  → emaArray 计算 5000 个点
  → setData(5000 个点)

后端返回 500 个代表性点（每 10 根取一个）：
  → setData(500 个点)  ← 渲染量减少 90%
```

但降采样可能损失精度，需要谨慎处理。

**2. 按可视范围返回（更有价值）**

后端只返回当前图表可视范围内的 MA 数据：

```
前端发送 visibleFrom / visibleTo 时间戳
  → 后端只计算这个范围内的 ~200 个点
  → setData(200 个点)  ← 渲染量减少 ~96%
```

前端配合 `timeScale().subscribeVisibleTimeRangeChange()` 在用户缩放/平移时按需请求。

**3. 利用 ta4j 的 CachedIndicator**

ta4j 的 `CachedIndicator` 会缓存计算结果，多次取值不会重复计算。这在用户切换可见范围时复用效果明显。

**4. 后端降采样方案对比**

| 方案 | 数据量 | 渲染耗时估算 | 精度损失 |
|---|---|---|---|
| 当前前端全量 | 5000 点 | ~100ms | 无 |
| 后端全量返回 | 5000 点 | ~100ms | 无 |
| 后端每 N 根取 1 点 | 500 点 | ~10ms | 可能遗漏拐点 |
| 后端按可见范围 | ~200 点 | ~5ms | 无（精确） |
| 后端按可见范围 + 缩放预加载 | ~500 点 | ~10ms | 无 |

#### 6.5.2 后端实现

```java
// 利用现有 TrendlineController 的模式
@Service
public class MaIndicatorService {

    public Map<Integer, List<MaPoint>> calculateMA(
            String symbol, String interval, List<Integer> periods,
            String type, Long fromTime, Long toTime) {

        // 1. 查询 K 线
        List<Candlestick> klines = candlestickService.getLastKlines(...);
        BarSeries series = IndicatorWrapHelper.buildSeries(klines);

        // 2. 计算所有周期的 MA
        Map<Integer, List<MaPoint>> result = new HashMap<>();
        for (int period : periods) {
            Indicator<Num> maIndicator = createIndicator(series, type, period);
            List<MaPoint> points = new ArrayList<>();
            for (int i = series.getBeginIndex(); i <= series.getEndIndex(); i++) {
                if (fromTime != null && toTime != null) {
                    long barTime = series.getBar(i).getBeginTime().toEpochSecond();
                    if (barTime < fromTime || barTime > toTime) continue;
                }
                Num value = maIndicator.getValue(i);
                if (value != null && !value.isNaN()) {
                    points.add(new MaPoint(
                        series.getBar(i).getBeginTime().toEpochSecond(),
                        value.doubleValue()
                    ));
                }
            }
            result.put(period, points);
        }
        return result;
    }
}
```

#### 6.5.3 前端集成

```javascript
async function updateMA() {
  if (!chart.value) return;

  // 获取当前可见范围
  const visibleRange = chart.value.timeScale().getVisibleRange();
  const resp = await api.post('/api/v1/kline/indicator/ma', {
    symbol: currentSymbol.value,
    interval: currentInterval.value,
    periods: [9, 21, 55, 144],
    type: 'EMA',
    visualRange: visibleRange ? {
      fromTime: Math.floor(visibleRange.from),
      toTime: Math.ceil(visibleRange.to),
    } : undefined,
  });

  const { data } = resp;
  // 创建或更新 series
  for (const [key, period] of [['ema1', 9], ...]) {
    if (!maSeriesRef.value[key]) {
      maSeriesRef.value[key] = chart.value.addSeries(LineSeries, { ... });
      await new Promise(r => requestAnimationFrame(r));
    }
    const points = data[String(period)];
    maSeriesRef.value[key].setData(points);
  }
}

// 监听可见范围变化，重新请求
chart.value.timeScale().subscribeVisibleTimeRangeChange(() => {
  if (indicators.value.ma) updateMA();
});
```

### 6.7 后端方案的风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| **网络延迟** | 每次请求增加 ~10-100ms | 使用请求缓存（keyed by symbol+interval+period+timeRange），避免重复请求 |
| **实时性** | 新 K 线到来时 MA 数据需更新 | 后端返回时附带最新 barTime，前端用当前 dataCache 最后若干根做增量 EMA 修正 |
| **服务端压力** | 高并发下频繁请求 MA | Redis 缓存 MA 结果，TTL=K线间隔×2 |
| **降采样精度** | K 线拐点可能丢失 | 建议优先使用「按可视范围精确返回」而非「降采样」 |

### 7.2 推荐路径

**短期（1-2 天）**：方案 A + 方案 B 合并实施
- 前端 `updateMA()` 加入 `requestAnimationFrame` 合并渲染
- 只对可见范围的数据点做 `setData`
- 改动最小，风险最低，效果明显（~200 点 vs 5000 点）

**中期（3-5 天）**：后端计算 API
- 新增 `/api/v1/kline/indicator/ma` 端点
- 按可见范围精确返回 MA 数据
- ta4j 计算确保精度
- 利用 Redis 缓存进一步提高性能
- 后续可扩展支持 MACD、RSI、BOLL 等其他指标

**长期**：后端指标计算平台
- 统一所有技术指标由后端计算
- 前端只负责渲染，不做任何指标计算
- 前端 `indicators.ts` 可逐步废弃

## 八、验证方法

1. 使用 Chrome DevTools Performance 录制勾选「均线」前后的火焰图
2. 对比优化前后 `updateMA()` 总耗时
3. 对比 `scripting` / `rendering` / `painting` 阶段耗时
4. 对比 setData 数据量（全量 vs 可见范围）
5. 确认其他指标（MACD、RSI 等）不受影响

## 九、未解决的问题

1. 其他指标（MACD、BOLL、Kalman 等）切换时是否也有类似卡顿？
2. 后端方案中，如果用户缩放/平移非常频繁，是否需要防抖/节流？
3. 增量 K 线更新时，后端 MA 如何与前端最后一根 K 线对齐？
