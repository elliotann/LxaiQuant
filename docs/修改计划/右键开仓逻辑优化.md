## 一、现状分析

### 1.1 当前流程

```
用户移动十字线到目标 K 线
  │
  └─ subscribeCrosshairMove → handleCrosshairMove → focusedKlineData = {time, ohlc}
       │
       └─ 右键点击图表区域
            │
            └─ handleContextMenu → 显示右键菜单
                 │
                 └─ "开单" → handleOpenOrderFromContextMenu
                      ├─ 从 focusedKlineData 读取 context (time/price)
                      ├─ 初始化表单 (side=BUY, orderType=MARKET)
                      └─ toggleOrderPanel() → 显示右侧开单面板
                           └─ 用户填写参数 → submitManualOpenOrder
                                └─ POST /manual-orders/open → appendManualOrderMarker
```

### 1.2 关键代码片段

**handleOpenOrderFromContextMenu**（~L11139）：
- 从 `focusedKlineData` 读取 time / close
- 写入 `manualOrderContextTime / manualOrderContextPrice / manualOrderContextKlineTime`
- 初始化 `manualOrderForm.side = "BUY"`, `orderType = "MARKET"`
- 调用 `toggleOrderPanel()` 打开右侧面板

**submitManualOpenOrder**（~L11177）：
- 校验：机器人 → 账户 → 金额 → 限价
- 调 API：`POST /manual-orders/open`
- 成功：`appendManualOrderMarker(side)` + ElMessage
- 失败：`ElMessage.error`

### 1.3 并行存在的快捷入口

- `handleInsertLongSignal()` — 直接市价开多，固定 quantity=1，不弹面板
- `handleInsertShortSignal()` — 直接市价开空，固定 quantity=1，不弹面板

## 二、待讨论/优化点

### 2.1 右键定位方式

**问题**：当前位置获取依赖于 `focusedKlineData`（十字线聚焦的 K 线），而非右键点击位置对应的时间/价格。

```
右键点击 → 不读取点击位置的 time/price
          → 依赖 focusedKlineData（依赖十字线位置）
          → focusedKlineData 回退策略（无聚焦时取 dataCache 最新一根）
```

**结论**：方案 C ✅

> **方案 C**：优先用点击位置反查（`chart.timeScale().coordinateToTime(event.clientX)`），无匹配时降级到十字线（`focusedKlineData`），再退到 `dataCache` 最新一根。

**改动要点**：
- `handleContextMenu` 中增加 `coordinateToTime` 反查逻辑
- 将反查结果作为首选，`focusedKlineData` 作为降级

### 2.2 开单入口与交互路径

**问题**：右键 → "开单" → 面板展开 → 填参数 → 提交，共 4 步，路径较长。

**结论**：方案 A + SMC 自动算 TP/SL + **面板显示盈亏比** ✅

> 保持现有面板不变，但右键开单时自动填入止盈止损价，数据来源为 SMC 多周期分析。同时在面板中**自动计算并显示盈亏比**。

**TP/SL 计算规则**：

```
开多 (BUY):
  SL = 15m SMC 最近支撑位下方 1%
  TP = 1h SMC 最近阻力位

开空 (SELL):
  SL = 15m SMC 最近阻力位上方 1%
  TP = 1h SMC 最近支撑位
```

**支撑/阻力搜索逻辑**：
- 从 SMC 数据中收集所有可用价位
- 按类型优先级过滤：订单块 > 均衡区 > 强/弱点 > 周期高低
- 从候选中选出距离当前价最近的一个

**兜底策略**：找不到支撑/阻力时，使用固定百分比
- SL = 市场价格 × (1 - 5% 开多 / 1 + 5% 开空)
- TP = 市场价格 × (1 + 10% 开多 / 1 - 10% 开空)

**数据获取**：右键开单时即时拉取 15m 和 1h 的 SMC 数据，后续重复调用走浏览器 HTTP 缓存

**盈亏比展示**：
- 在 TP/SL 输入行下方、提交按钮上方新增一行，显示 `盈亏比 R:R`
- 计算方式：`abs(TP - entryPrice) / abs(SL - entryPrice)`，保留 2 位小数
- 只有当 TP 和 SL 都有效时才显示，否则显示 `-`
- 使用 computed 实时计算，用户手动修改 TP/SL 时同步更新

### 2.3 handleInsertLongSignal 与右键"开单"的关系

**问题**：两者功能重叠但实现不同：

| 维度 | handleInsertLongSignal | 右键"开单" |
|------|----------------------|-----------|
| 入口 | 外部按钮 | 右键菜单 |
| quantity | 固定 1 | 用户可调 |
| 面板 | 无 | 有 |
| 参数 | 无（固定 MARKET） | 可调方向/类型/杠杆/TP/SL |

**结论**：方案 C ✅

> 去掉 `handleInsertLongSignal` / `handleInsertShortSignal` 两个外部快捷按钮，统一走右键菜单的"开单"入口。
> 
> 同时将**均衡区（equilibriumCenter）** 加入支撑/阻力优先级计算。

**改动要点**：
- 删除图表上方对应的快捷按钮 DOM
- 删除 `handleInsertLongSignal` 和 `handleInsertShortSignal` 方法
- 支撑/阻力优先级更新为：订单块 > 均衡区 > 强/弱点 > 周期高低

### 2.4 开单面板数据初始化

**问题**：点击"开单"时只初始化了 `side/orderType/limitPrice`，其他字段（金额/杠杆/止盈止损）保持上次输入。

**结论**：方案 B ✅

> 每次打开面板时：SMC 自动算出的 TP/SL 覆盖旧值，其他字段（金额、杠杆、保证金模式等）保持用户上次输入的值。

## 三、后端改动：同方向持仓时自动加仓

### 3.1 问题

当前 `ManualController.open()` 对所有手动开仓都走 `tradeOrderService.createOrder()` 创建独立订单。如果机器人下已经有**同方向的持仓**，应该走**加仓（add-position）逻辑**，而不是新建一笔独立仓位。

### 3.2 改动逻辑

```
ManualController.open()
  │
  ├─ 校验参数（不变）
  │
  ├─ 查询该机器人下同方向是否有未平仓订单
  │    └─ tradeOrderService.getPositionOrders(accountId, symbol)
  │         └─ 过滤 orderSide = mappedSide 且未平仓的订单
  │
  ├─ 无同方向持仓 → 走现有 createOrder 逻辑（不变）
  │
  └─ 有同方向持仓 → 走加仓逻辑
       ├─ 调用 tradeOrderService.addPosition() 或等效方法
       ├─ 更新持仓批次信息（批次号、累计数量、均价）
       └─ 返回合并后的持仓信息
```

### 3.3 结论

**后端已有完整支持**：
- `ITradeOrderService.getPositionOrders(accountId, symbol)` — 查持仓
- `ITradeOrderService.suppOrder(TradingStrategyParams)` — 加仓
- `DefaultDealStrategyTrade.suppOrder()` — 加仓执行

### 3.4 实际代码改动

#### ManualController.open() 新增逻辑

**1. TP/SL 从 metadata 提取**（在 builder 构建后、extras 处理前）：

```java
// 从 metadata 中提取止盈/止损价
if (req.getMetadata() != null) {
    Object tpObj = req.getMetadata().get("tpPrice");
    Object slObj = req.getMetadata().get("slPrice");
    if (tpObj instanceof Number) {
        builder.takeProfitPrice(new BigDecimal(tpObj.toString()));
    }
    if (slObj instanceof Number) {
        builder.stopLossPrice(new BigDecimal(slObj.toString()));
    }
}
```

**2. 同方向持仓检查**（在 extras 设置后、idempotency key 检查前）：

```java
// 检查是否有同方向持仓，有则走加仓逻辑
List<OrderVO> existingPositions =
        tradeOrderService.getPositionOrders(req.getAccountId(), req.getSymbol());
boolean hasSameSidePosition = existingPositions != null && existingPositions.stream()
        .anyMatch(o -> o != null && o.getOrderSide() != null
                && mappedSide.equalsIgnoreCase(o.getOrderSide()));

if (hasSameSidePosition) {
    boolean suppOk = tradeOrderService.suppOrder(builder.build());
    secrets.clear();
    if (!suppOk) {
        return ApiResponse.error("加仓失败");
    }
    Map<String, Object> result = new HashMap<>();
    result.put("result", "supplemented");
    return ApiResponse.success("手动加仓已触发", result);
}
```

**设计说明**：
- idempotency key 检查在加仓判断**之后**，确保已创建订单的重复请求不会被误判为加仓
- 加仓成功后的返回结构体使用 `result=supplemented` 标识，区别于新建订单的 `orderId`
- 与现有平仓 (`/close`) 和反手 (`/reverse`) 方法中使用的 `getPositionOrders` + `orderSide` 过滤逻辑保持一致
