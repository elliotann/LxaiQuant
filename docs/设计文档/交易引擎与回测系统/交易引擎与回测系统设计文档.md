## 1. 概述

交易引擎与回测系统是整个量化交易平台的核心执行层，负责策略的构建、执行、持仓管理、风险控制以及历史回测评估。

### 1.1 在整体架构中的位置

交易引擎与回测系统位于业务服务层，上层对接机器人任务调度与交易策略模块，下层依赖市场数据服务与交易所适配层：

```
┌─────────────────────────────────────┐
│     机器人管理 / 交易策略模块          │
├─────────────────────────────────────┤
│       交易引擎与回测系统              │
│  ┌──────────────┐ ┌──────────────┐  │
│  │  DefaultDeal │ │  Backtest    │  │
│  │  Strategy    │ │  Engine      │  │
│  │  Trade       │ │              │  │
│  └──────┬───────┘ └──────┬───────┘  │
│         │                │          │
│  ┌──────┴────────────────┴───────┐  │
│  │        ta4j 核心框架           │  │
│  └───────────────────────────────┘  │
├─────────────────────────────────────┤
│   市场数据服务 / 交易所适配层         │
└─────────────────────────────────────┘
```

### 1.2 核心目标

- **实盘交易**: 实时 K 线驱动，执行策略入场/出场逻辑，管理持仓生命周期
- **回测评估**: 基于历史 K 线模拟策略运行，计算绩效指标，支持参数优化
- **双向持仓**: 支持同时持有多头和空头仓位
- **风险控制**: 多种出场规则（止损、止盈、移动止损、时间止损等）
- **加仓功能**: 允许在已有持仓方向上加仓，摊平成本

## 3. 核心交易引擎

### 3.1 接口定义

交易引擎的核心接口 `IDealStrategyBasic` 定义了策略执行的主流程：

```
IDealStrategyBasic
├── execStrategy()                    ← 主入口，协调策略执行
├── initBarSeries()                   ← 初始化 K 线序列
├── buildStrategy()                   ← 构建策略（Spring Bean 加载）
├── executeTradingLogic()             ← 执行交易逻辑
│   ├── processPositionExits()        ← 处理持仓出场
│   └── processEntrySignals()         ← 处理入场信号
├── createLongOrder()                 ← 开多仓
├── createShortOrder()                ← 开空仓
└── determineExitTypes()              ← 确定出场类型
```

### 3.2 主执行流程

```
execStrategy()
│
├─ 1. initBarSeries()
│      └─ 通过 KlineDataProviderFactory 获取最新 K 线数据
│          └─ 使用 IndicatorWrapHelper.buildSeries() 构建 BarSeries
│
├─ 2. 判断机器人是否运行
│      ├─ 未运行 → 跳过本次执行
│      └─ 运行中 → 继续
│
├─ 3. executeTradingLogic(lastIndex)
│      ├─ processPositionExits(lastIndex)    ← 先处理出场
│      └─ processEntrySignals(lastIndex)     ← 再处理入场
│
└─ 4. sampleAndEnqueueEquityPoint()          ← 采样权益曲线
```

### 3.3 DefaultDealStrategyTrade 实现

`DefaultDealStrategyTrade` 是 `IDealStrategyBasic` 的默认实现，支持两种运行模式：

#### 运行模式

| 模式 | 配置值 | 说明 |
|------|--------|------|
| 传统单方向 | `indicator_driven` | 基于入场条件规则（`IndicatorDrivenDirectionRule`）触发入场，出场由规则引擎管理 |
| 双向持仓 | `multi_direction` | 基于信号缓存（`SignalCacheManager`）驱动入场，支持同时持有多/空仓位 |

#### 策略构建流程

```
buildStrategy()
│
├─ indicator_driven 模式
│   ├─ 入场规则: IndicatorDrivenDirectionRule
│   └─ 出场规则(组合):
│       ├─ DirectionalStopLossRule          (固定止损)
│       ├─ DirectionalTrailingStopRule       (移动止损)
│       ├─ DirectionalStopGainRule           (固定止盈)
│       ├─ ExtTrailingStopGainRule           (移动止盈)
│       ├─ BatchTakeProfitRule              (分批止盈)
│       ├─ MacdCrossExitRule / PinVolumeExitRule (技术指标出场)
│       ├─ DirectionalTimeBasedStopGainRule  (时间止盈)
│       ├─ DirectionalTimeBasedStopLossRule  (时间止损)
│       └─ SmcDynamicExitRule               (SMC 动态出场)
│
└─ multi_direction 模式
    ├─ 入场: 信号缓存 SignalCacheManager 驱动
    └─ 出场规则组合（同上）
```

#### 开仓流程

```
createLongOrder() / createShortOrder()
│
├─ 1. 获取分布式锁 (RedissonDistributedLock)
│
├─ 2. 检查持仓数量限制 (bactCount / positionLimit)
│
├─ 3. 检查补仓条件 (shouldTriggerSupplementaryOrder)
│      └─ 满足则计算补仓数量
│
├─ 4. 计算仓位
│      ├─ SignalWeightedMultiPositionExecutionModel (信号权重分配)
│      └─ ContractSpecUtils 合约计算（杠杆/面值/乘数）
│
├─ 5. 创建订单发送到交易所
│
└─ 6. 释放分布式锁
```

#### 出场处理

```
processPositionExits(lastIndex)
│
├─ 1. 获取当前所有持仓
│
├─ 2. 对每个持仓:
│      ├─ 获取持仓方向 (LONG/SHORT)
│      ├─ 确定适用的出场类型 (determineExitTypes)
│      ├─ 检查 MultiPositionStrategy.shouldExitSignal()
│      ├─ 检查传统策略 shouldExit()
│      └─ 触发出场则执行平仓
│
└─ 3. 出场幂等性保障 (Redis)
       ├─ shouldProcessExit()   ← 检查是否已处理
       └─ markExitProcessed()   ← 标记已处理
```

## 4. 策略构建体系

### 4.1 传统单方向策略 (indicator_driven)

基于入场条件规则构建的传统策略：

```
规则构成:
  入场: IndicatorDrivenDirectionRule
        检测入场指标条件是否满足
  出场: ExitRule 组合
        出场规则通过 Spring 配置动态组合
```

### 4.2 双向持仓策略 (multi_direction)

基于信号缓存的双向策略：

```
信号缓存 (SignalCacheManager)
  ├─ 从 Redis 读取 AI 模型产生的信号数据
  ├─ 信号包含: 方向(LONG/SHORT)、权重、入场价格、出场条件
  └─ 提供 shouldEnter() / shouldExit() 判断

信号权重分配 (SignalWeightedMultiPositionExecutionModel)
  ├─ 根据信号权重分配仓位大小
  └─ 支持多个信号源的权重聚合
```

### 4.3 出场规则组合

出场规则通过 `OrDirectionalRule` 组合，任一规则满足即触发出场：

```
exitRule = OrDirectionalRule
  ├─ DirectionalStopLossRule(close, lossPercentage)
  ├─ DirectionalTrailingStopRule(close, trailPercentage)
  ├─ DirectionalStopGainRule(close, gainPercentage)
  ├─ ExtTrailingStopGainRule(close, trailGainPercentage)
  ├─ BatchTakeProfitRule(close, profitLevels)
  ├─ DirectionalTimeBasedStopLossRule(maxHoldBars)
  ├─ DirectionalTimeBasedStopGainRule(profitHoldBars)
  └─ SmcDynamicExitRule(series, multiTimeframe)
```

## 5. 出场规则系统

### 5.1 规则分类

| 类别 | 规则类 | 说明 |
|------|--------|------|
| **固定止损** | `DirectionalStopLossRule` | 基于入场价的固定百分比止损，支持多/空方向 |
| **移动止损** | `DirectionalTrailingStopRule` | 随价格向有利方向移动而调整的止损线 |
| **固定止盈** | `DirectionalStopGainRule` | 基于入场价的固定百分比止盈 |
| **移动止盈** | `ExtTrailingStopGainRule` | 随价格移动的止盈线 |
| **分批止盈** | `BatchTakeProfitRule` | 设置多层止盈目标，分批出场 |
| **技术出场** | `MacdCrossExitRule` | MACD 金叉/死叉出场信号 |
| **技术出场** | `PinVolumeExitRule` | 放量异常 K 线出场 |
| **时间止损** | `DirectionalTimeBasedStopLossRule` | 持仓时间超过最大限制时出场 |
| **时间止盈** | `DirectionalTimeBasedStopGainRule` | 持仓达到目标时间后出场 |
| **SMC 动态出场** | `SmcDynamicExitRule` | Smart Money Concept 动态出场，支持多周期 |
| **信号反转** | `LongSignalReversalExitRule` | 多头信号反转出场 |
| **信号反转** | `ShortSignalReversalExitRule` | 空头信号反转出场 |

### 5.2 方向性规则设计

`DirectionalRule` 是方向感知的规则基类，继承自 ta4j 的 `Rule` 接口：

```
DirectionalRule (接口)
├── isSatisfied(int index, TradingRecord tradingRecord)
├── getDirection() → Direction (LONG / SHORT)
│
├── DirectionalStopLossRule          ← 方向性止损
├── DirectionalStopGainRule          ← 方向性止盈
├── DirectionalTrailingStopRule      ← 方向性移动止损
├── DirectionalTimeBasedStopLossRule ← 方向性时间止损
└── DirectionalTimeBasedStopGainRule ← 方向性时间止盈
```

方向性规则根据持仓方向（LONG/SHORT）自动选择正确的价格比较逻辑：
- **多头**: 价格下跌到止损位触发
- **空头**: 价格上涨到止损位触发

### 5.3 出场规则组合

```
出场规则组合逻辑:
  1. 读取配置文件，确定启用的出场类型
  2. 根据配置创建对应规则实例，配置参数
  3. 通过 OrDirectionalRule 组合所有规则
  4. 任一规则满足即触发出场

出场幂等性:
  通过 Redis 记录已处理的出场事件，防止:
  ├─ 同一根 K 线多次触发出场
  └─ 多线程并发处理出场
```

### 5.4 出场类型配置

配置文件中的出场规则配置结构：

```yaml
exit-rules:
  fixed-stop-loss:
    enabled: true
    percentage: 2.0
  trailing-stop-loss:
    enabled: true
    percentage: 3.0
  take-profit:
    enabled: true
    type: fixed_percent
    percentage: 5.0
  trailing-stop-gain:
    enabled: true
    percentage: 2.0
  batch-take-profit:
    enabled: true
    levels:
      - percentage: 3.0, ratio: 0.3
      - percentage: 5.0, ratio: 0.3
      - percentage: 8.0, ratio: 0.4
  technical-take-profit:
    enabled: true
    type: macd_cross
  time-based-take-profit:
    enabled: true
    bars: 96
  time-based-stop-loss:
    enabled: true
    bars: 192
  smc-exit:
    enabled: true
    multi-timeframe: true
```

## 6. 加仓功能

### 6.1 概述

加仓功能允许在已有持仓的方向上增加仓位，通过摊平成本提高盈利潜力。加仓逻辑集成在开仓流程中，是 `createDirectionalOrder()` 的一部分。

### 6.2 加仓判断逻辑

```
shouldTriggerSupplementaryOrder()
│
├─ 1. 检查是否开启加仓功能 (supplementaryOrderEnabled)
│
├─ 2. 获取当前持仓数量
│
├─ 3. 检查补仓数量限制:
│      ├─ batchCount > currentPositionCount
│      └─ positionLimit > currentPositionCount
│
├─ 4. 检查补仓间隔:
│      └─ 距离上次补仓的 bar 数 >= gapBars
│
└─ 5. 满足条件 → 计算补仓数量
        └─ applyLossSupplementItemTakeProfit()
```

### 6.3 补仓数量计算

```
补仓数量 = baseAmount × supplementLevelMultiplier[level]
其中:
  - baseAmount: 基础开仓数量
  - supplementLevelMultiplier: 各补仓层级的乘数配置
  - level: 当前补仓次数
```

### 6.4 补仓后处理

```
applyLossSupplementItemTakeProfit()
│
├─ 1. 更新平均持仓价格
│      └─ avgPrice = (总成本) / (总数量)
│
├─ 2. 更新总持仓数量
│
├─ 3. 持久化 TradeOrderItem
│      └─ 记录每次补仓的明细（价格、数量、时间）
│
└─ 4. 更新止盈价格（如有需要）
```

## 7. 双向持仓支持

### 7.1 核心概念

双向持仓（MultiPosition）是系统的核心扩展能力，允许同时持有多头和空头仓位，基于 ta4j 框架的 `MultiPositionTradingRecord` 实现。

### 7.2 核心类关系

```
MultiPositionTradingRecord
├── 继承自 BaseTradingRecord (ta4j)
├── 支持同时管理多个持仓
├── 提供方向感知的持仓管理
│
MultiPositionStrategy (接口)
├── shouldEnter(int index, TradingRecord) → DirectionResult
├── shouldExitSignal(int index, TradingRecord, Direction) → boolean
├── getEntryRule() → Rule
├── getExitRule() → Rule
├── getLongEntryRule() → Rule
├── getShortEntryRule() → Rule
│
```

### 7.3 信号缓存集成

`SignalCacheAware` 接口将 AI 信号系统与交易引擎桥接：

```
SignalCacheAware
├── getLongEntryRule() → Rule
├── getShortEntryRule() → Rule
├── getExitRule() → Rule
│
SignalCacheManager
├── 从 Redis 读取信号数据
├── 构建入场/出场规则
└── 支持回测时注入历史信号
```

### 7.4 双向入场逻辑

```
processEntrySignals(lastIndex)
│
├─ 1. 检查当前是否为双向模式 (multi_direction)
│
├─ 2. 多头入场判断:
│      ├─ 检查 LongEntryRule.isSatisfied()
│      ├─ 检查持仓限制
│      └─ 满足 → createLongOrder()
│
├─ 3. 空头入场判断:
│      ├─ 检查 ShortEntryRule.isSatisfied()
│      ├─ 检查持仓限制
│      └─ 满足 → createShortOrder()
│
└─ 4. 旧策略兼容 (单方向策略)
       └─ 传统 shouldEnter() 判断
```

## 8. 回测系统

> ⚠️ **重要概念区分：四种回测类型**
> 
> 系统提供四种回测类型，引擎分层清晰，不可混淆：
> 
> | 回测类型 | 后端入口 | 引擎层 | 说明 |
> |---------|---------|--------|------|
> | **QUICK_BACKTEST** (快速回测) | `BacktestService.runEnhancedBacktest()` | **ta4j 标准回测引擎** `BarSeriesManager` + `LiveTradingRecord` | 纯框架级快速模拟，零成本模型，当前收盘价成交，纯内存计算，不涉及数据库 |
> | **MULTI_STRATEGY_COMPARISON** (多策略对比) | 同上 `runMultipleStrategies()` | **ta4j 标准回测引擎**（跑 N 次取对比） | 同快速回测引擎，并行执行多个策略对比 |
> | **WALK_FORWARD_OPTIMIZATION** (步进优化) | `BacktestService.runParameterRangeOptimization()` | **ta4j walk-forward** 分段滚动优化 | 按时间窗口分段训练+验证 |
> | **TRADITIONAL_BACKTEST** (传统回测) | `runTraditionalBacktestWithDataCapture()` → `strategy.execStrategy()` | **实盘全链路引擎** `DefaultDealStrategyTrade` | 走完整实盘逻辑（锁、持久化、信号缓存、出/入场规则引擎），仅不实际发单到交易所 |
>
> ```
> ┌────────────────────────────────────────────────────────────┐
> │                  回测引擎分层架构                            │
> │                                                            │
> │  QUICK_BACKTEST ← 快速校准参考                             │
> │  MULTI_STRATEGY_COMPARISON                                 │
> │  WALK_FORWARD_OPTIMIZATION                                 │
> │       ↓ 都基于 ta4j 标准回测引擎                            │
> │  ┌─────────────────────────────────┐                       │
> │  │  ta4j BarSeriesManager          │ ← 框架层，纯内存模拟   │
> │  │  + LiveTradingRecord            │                       │
> │  └─────────────────────────────────┘                       │
> │                                                            │
> │  TRADITIONAL_BACKTEST ← 全真模拟基准                       │
> │       ↓ 基于实盘交易引擎                                     │
> │  ┌─────────────────────────────────┐                       │
> │  │  DefaultDealStrategyTrade       │ ← 业务层，全链路模拟   │
> │  │  + 信号缓存 / 出入场规则 /      │                       │
> │  │  锁 / 持久化 / 权益采样          │                       │
> │  └─────────────────────────────────┘                       │
> │                                                            │
> │  传统回测是唯一走实盘逻辑的路径，                               │
> │  作为其他三种回测结果的基准校准参考                             │
> └────────────────────────────────────────────────────────────┘
> ```

> 🔍 **快速回测 vs 传统回测 深层对比**
> 
> 两种回测的核心差异**不在执行引擎层，而在策略构造层**。以下是详细对比：
> 
> ### 执行循环对比
> 
> | 维度 | ta4j 标准 BarSeriesManager | 快速回测 (BacktestEngine) | 传统回测 (execStrategy) |
> |------|--------------------------|------------------------|----------------------|
> | **循环方式** | `for(i=begin..end)` 一次性遍历 | 同 ta4j 标准 `for` 循环 | `do-while` 增量推进，逐个 bar fetch + update |
> | **判断入口** | `strategy.shouldOperate(i, record)` | 同上 | `executeTradingLogic()` → `processPositionExits()` + `processEntrySignals()` |
> | **成交模型** | `TradeOnNextOpenModel`（下一根K线开盘价） | `TradeOnCurrentCloseModel`（**当前K线收盘价**） | 通过 `TradeOrderServiceAdapter` 写订单到数据库 + `PendingOrderWorker` 轮询填充 |
> | **成本模型** | `ZeroCostModel` | 可配 (`commissionRate`/`slippageRate`) | 实盘费率标准 |
> 
> ### 策略构造对比（核心差距）
> 
> ```
> 传统回测 (DefaultDealStrategyTrade.buildStrategy())
>   ├─ 从 BidirectionalProperties 读取全部配置
>   ├─ 构建入场规则: IndicatorDrivenDirectionRule / SignalCacheManager
>   ├─ 构建出场规则组合:
>   │   ├─ DirectionalStopLossRule      (fixed-stop-loss)
>   │   ├─ DirectionalTrailingStopRule   (trailing-stop-loss)
>   │   ├─ DirectionalStopGainRule       (take-profit)
>   │   ├─ ExtTrailingStopGainRule       (trailing-stop-gain)
>   │   ├─ BatchTakeProfitRule           (batch-take-profit)
>   │   ├─ MacdCrossExitRule / PinVolumeExitRule (technical)
>   │   ├─ DirectionalTimeBasedStopGainRule / DirectionalTimeBasedStopLossRule
>   │   └─ SmcDynamicExitRule            (smc-exit)
>   └─ 所有规则通过 OrDirectionalRule 组合
> 
> 快速回测 (BacktestService.createStrategyByType())
>   ├─ indicator_driven → buildIndicatorDrivenStrategy()
>   │   ├─ 入场: 从 EntryRuleCondition 构建
>   │   └─ 出场: ❌ 空 OrDirectionalRule（没有配置读取）
>   ├─ SIGNAL_BASED  → createSignalBasedStrategy()
>   │   ├─ 入场: SignalCacheAware (同传统路径的 multi_direction)
>   │   └─ 出场: ✅ 有实际 exit rule
>   └─ TREND_LINE_BOTH → 简单 SMA 金叉死叉
> ```
> 
> **核心问题**：`buildIndicatorDrivenStrategy()` 只构建入场规则，出场规则是一个**空的** `OrDirectionalRule()` — 相当于没有配置任何止损止盈。而传统路径会从 `BidirectionalProperties` 读取并构建**全部 8+ 种出场规则**。
> 
> ### 附加功能差异
> 
> 传统回测相比快速回测多出以下**非交易逻辑**开销：
> 
> | 功能 | 快速回测 | 传统回测 | 影响 |
> |------|---------|---------|------|
> | Redis 分布式锁 | ❌ | ✅ `RedissonDistributedLock` | 传统回测有锁等待时间，实盘中可能导致滑点 |
> | 订单数据库持久化 | ❌ | ✅ 写入 `TradeOrder` 表 | 传统回测有 IO 开销 |
> | Redis 出场幂等性 | ❌ | ✅ `shouldProcessExit()` / `markExitProcessed()` | 防止重复出场 |
> | Redis 权益曲线采样 | ❌ | ✅ `sampleAndEnqueueEquityPoint()` | 用于实时监控 |
> | 仓位计算/合约规格 | ✅ 内存计算 | ✅ 同样走 `ContractSpecUtils` | 逻辑一致 |
> | 补仓逻辑 | ❌ | ✅ `shouldTriggerSupplementaryOrder()` | 传统回测有加仓判断 |
> 
> ### 结论
> 
> **快速回测可以与传统回测保持逻辑一致，只需解决策略构造的统一问题。**
> 
> 两者本质都是：**拿 ta4j 或扩展的策略，填充入场规则和出场规则，然后运行执行循环。**
> 
> 差异只在**执行方式**（for 循环 vs do-while）和**非功能性逻辑**（落库/锁），不在**交易决策规则**本身。策略规则统一后，快速回测的结果可作为传统回测的快速近似，差异仅来自成交时机和 IO 开销。
> 
> ```
> 重构后的统一架构:
> 
>                     ┌─────────────────────────────┐
>                     │  公共策略规则工厂 (复用层)     │
>                     │                              │
>                     │  buildStrategy(config)       │← 统一入口
>                     │  ├─ buildEntryRules(config)  │← 入场规则
>                     │  └─ buildExitRules(config)   │← 出场规则组合
>                     │                              │
>                     └──────────┬──────────────────┘
>                                │ 返回同一套 Strategy
>                                │
>             ┌──────────────────┴──────────────────┐
>             │                                     │
>             ▼                                     ▼
>    ┌──────────────────┐                  ┌──────────────────┐
>    │ BacktestEngine    │                  │ DefaultDeal      │
>    │ (快速/多策略/步进) │                  │ StrategyTrade    │
>    │                   │                  │ (传统回测/实盘)   │
>    │ for(i=begin..end) │                  │ do-while 逐 Bar  │
>    │ 纯内存遍历         │                  │ DB 全链路         │

## 12. 重构计划

### 12.1 快速回测 vs 传统回测差异分析

**核心结论：快速回测与传统的差距不在执行引擎层，而在策略构造层。**

当前系统策略构造碎片化在三处，违反"不要重复造轮子，尽量公用"规则：

| 策略构造入口 | 入场规则 | 出场规则 | 使用方 |
|------------|---------|---------|--------|
| `DefaultDealStrategyTrade.buildStrategy()` | IndicatorDrivenDirectionRule / SignalCacheManager | **8+种全量**（止损/止盈/移动/时间/SMC等） | 传统回测、实盘 |
| `BacktestService.buildIndicatorDrivenStrategy()` | IndicatorDrivenDirectionRule | **空 OrDirectionalRule** ❌ | 快速回测 indicator_driven |
| `BacktestService.createSignalBasedStrategy()` | SignalCacheAware | ✅ 有实际 exit rule | 快速回测 SIGNAL_BASED |
| `BacktestService.createTrendLineBothStrategy()` | SMA 金叉/死叉 | 简单反向规则 | 快速回测 TREND_LINE_BOTH |

**快速回测需要保持与传统回测一致的三大关注点：**

1. **策略构造时序** — 快速回测一次性拿到全部 Bar，传统回测增量追加。ta4j 指标是增量可计算的，只要 bar 顺序一致，结果一致。
2. **出场规则触发边界** — 传统回测的 `processPositionExits()` 有三层出场判断（固定止损 → 信号缓存 → 传统 shouldExit），快速回测只走了第三层。统一后应全部由 `Strategy.shouldOperate()` 承载。
3. **成交价格对齐** — 快速回测用 `TradeOnCurrentCloseModel`（当前收盘价），传统回测走 `PendingOrderWorker`（模拟市价单）。两者用同一个价格源，逻辑一致。
4. **绩效指标统一** — 目前指标计算分布在 `BacktestEngine.calculateMetrics()` 和 `BacktestController.calculateTraditionalMetrics()` 两处，应合并为一套。

### 12.2 重构目标与原则

**目标**：快速回测、多策略对比、步进优化、传统回测四种类型使用**同一套策略规则**，仅在执行方式和持久化时机上不同。

**原则**：
1. **代码尽量公用** — 不重复造轮子，已有的 `DefaultDealStrategyTrade.buildStrategy()` 策略构造逻辑提取为公共工厂
2. **共用的是 Strategy 本身**（入场 Rule + 出场 Rule 组合）
3. **不该共用的是 Execution 方式**（for 循环 vs do-while，纯内存 vs DB 全链路）
4. **保持包结构风格一致**，类名和命名规范统一
5. **不改 ta4j 和 XChange 源码**

### 12.3 关键设计决策

```
统一后的架构:

                    ┌──────────────────────────────┐
                    │   StrategyFactory (新建)      │
                    │   公共策略规则工厂              │
                    │                              │
                    │  buildStrategy(config)       │← 统一入口
                    │  ├─ buildEntryRules(config)  │← 入场规则构建
                    │  ├─ buildExitRules(config)   │← 出场规则构建
                    │  │   (读取 BidirectionalProperties) │
                    │  └─ composeStrategy(rules)   │← Rule → Strategy 组合
                    └──────────┬───────────────────┘
                               │ 返回同一套 Strategy
                               │
            ┌──────────────────┴──────────────────┐
            │                                     │
            ▼                                     ▼
   ┌────────────────────┐                ┌──────────────────┐
   │ BacktestEngine      │                │ DefaultDeal      │
   │ (快速/多策略/步进)   │                │ StrategyTrade    │
   │                     │                │ (传统回测/实盘)   │
   │ for(i=begin..end)   │                │ do-while 逐 Bar  │
   │ TradeOnCurrentClose │                │ 订单系统逐条落库  │
   │ 纯内存遍历           │                │ DB 全链路模拟     │
   │ 结果批量落库         │                │                  │
   └────────────────────┘                └──────────────────┘
            │                                     │
            └────────── 同一套 Strategy ───────────┘
```

**关键决策**：
- `StrategyFactory` 只依赖于 `BidirectionalProperties` + `BarSeries`，**不依赖** `DefaultDealStrategyTrade` 的业务上下文（锁、订单服务等）
- 快速回测不丢失能力：`SignalCacheAware`、`SignalWeightedMultiPositionExecutionModel`、合约交易等保持不变
- 指标计算统一到 `BacktestEngine.calculateMetrics()` 一处

## 13. 扩展 ta4j 的交易引擎与回测系统架构

### 13.1 概述

本系统基于 **ta4j 0.22.6** 框架进行扩展，核心动因是 ta4j 原生 `BaseTradingRecord` 仅支持单一方向的净持仓，而本系统需要支持 **双向多空、加减仓、部分平仓、信号驱动入场** 等生产级特性。

**核心设计思路：组合两个 `BaseTradingRecord`**

不创建自定义的 `MultiPositionTradingRecord`，而是用两个原生 `BaseTradingRecord` 分别管理多头和空头持仓：

```
CompositeTradingRecord
├── longRecord:  BaseTradingRecord  ← 多头持仓（BUY entry / SELL exit）
└── shortRecord: BaseTradingRecord  ← 空头持仓（SELL entry / BUY exit）
```

**这样带来的简化：**
- 复用 ta4j 原生 `BaseTradingRecord` 的完整逻辑（PositionBook、getTrades、盈亏计算）
- 复用 ta4j 原生 `BarSeriesManager` 的回测执行流程
- 复用 ta4j 原生 `Strategy`、`Rule` 接口，无需自定义方向感知接口
- 出场调度用原生 `OrRule` 链即可，无需分层调度器

**扩展原则：**
- 不改 ta4j 源码 — 通过**组合**而非继承来扩展
- 尽量复用原生组件，减少自定义接口 — 只在必要时添加适配层
- 回测与实盘统一入口 — `execStrategy` 通过 `testMode` 切换

**ta4j → 本系统映射：**

| ta4j 原生 | 本系统扩展 | 扩展方式 |
|-----------|------------|---------|
| `TradingRecord` | `CompositeTradingRecord`（组合两个 BaseTradingRecord） | **组合** |
| `BarSeriesManager` | 复用原生，添加 `TradingOrderServiceAdapter` 适配 | **复用** |
| `Rule` → `boolean` | 复用原生 `Rule`，用 `OrRule` 链组合出场条件 | **复用** |
| `Strategy` | 复用原生 `Strategy`，多空各一个实例 | **复用** |
| `PositionBook` | 复用原生，longRecord/shortRecord 各持一个 | **复用** |

### 13.2 扩展点总览

| 层级 | ta4j 原生 | 本系统扩展 | 差异说明 |
|------|----------|-----------|---------|
| **内存层** | `BaseTradingRecord` + `PositionBook` | `CompositeTradingRecord`（组合两个 BaseTradingRecord） | **组合**而非新增，多空各持一个原生 Record |
| **回测层** | `BarSeriesManager.run()` | **复用**原生 BarSeriesManager，多空各跑一次 | 无需自定义回测管理器 |
| **规则层** | `Rule` → `boolean` | **复用**原生 `Rule`，用 `OrRule` 链组合 | 无需 DirectionalRule/ExitSignal |
| **策略层** | `Strategy` 接口 | **复用**原生 `Strategy`，多空各一个实例 | 无需 MultiPositionStrategy |
| **执行层** | 回测 `for` 循环，实盘无标准流程 | `execStrategy` 双模式（testMode 切换） | 回测/实盘统一入口，DB 全链路 |
| **出场调度** | 单一 `shouldExit()` | `OrRule` 链组合多条件出场 | 无需分层调度器，用原生 OrRule 即可 |
| **信号层** | 无 | `SignalCacheManager` | AI 信号桥接，生成多空 Rule |
| **绩效层** | `BasePerformanceReport`（基础） | `PerformanceMetrics`（Sharpe/Sortino/年化等） | 更全面的绩效评估体系 |

### 13.3 扩展详解

#### 13.3.1 内存层：CompositeTradingRecord

**职责：** 组合两个原生 `BaseTradingRecord`，分别管理多头和空头持仓。

**核心数据结构：**

```
CompositeTradingRecord
├── longRecord:  BaseTradingRecord     ← 多头持仓（BUY→SELL）
│     ├── positionBook: PositionBook(BUY)
│     ├── currentPosition: Position
│     └── closedPositions: List<Position>
├── shortRecord: BaseTradingRecord     ← 空头持仓（SELL→BUY）
│     ├── positionBook: PositionBook(SELL)
│     ├── currentPosition: Position
│     └── closedPositions: List<Position>
├── orderAdapter: TradingOrderServiceAdapter  ← DB 订单适配
└── matchPolicy: ExecutionMatchPolicy  ← FIFO / AVG_COST
```

**设计要点：**
- `longRecord` 接收 **BUY entry + SELL exit**，`shortRecord` 接收 **SELL entry + BUY exit**，符合 ta4j 原生的方向逻辑
- 每个 `BaseTradingRecord` 内部的 `PositionBook` 独立维护自己的开平仓顺序
- 部分平仓（AVG_COST）通过 **拆单** 实现：一笔平仓拆为"已平 Position"和"剩余 Position"，分别放入 closed 和 open 列表

**与旧方案对比：**

| 维度 | 旧方案（MultiPositionTradingRecord） | 新方案（CompositeTradingRecord） |
|------|-------------------------------------|----------------------------------|
| 实现方式 | 自定义实现 TradingRecord 接口 | **组合**两个原生 BaseTradingRecord |
| 代码量 | ~600 行自定义代码 | ~100 行组合代码 |
| 双向管理 | 自定义 BUY/SELL 双 List | 原生 PositionBook 各管各的 |
| getTrades 缓存 | 自定义双重锁 | 复用原生 |
| 测试覆盖 | 需自测全部逻辑 | 继承 ta4j 原生测试保障 |
| 风险 | 可能引入边界 Bug | **低风险**，核心逻辑在原生 |

**关键流程：**

> **rebuildFromDB** — 从数据库重建内存持仓

```
rebuildFromDB(accountId, symbol)
  → orderAdapter.loadOpenPositions(accountId, symbol)
      → for each openPosition:
          方向 == BUY  → longRecord.enter(trade)
          方向 == SELL → shortRecord.enter(trade)
```

> **enter** — 入场（委托给对应方向的 Record）

```
enter(trade, side)
  if side == BUY  → longRecord.enter(trade)
  if side == SELL → shortRecord.enter(trade)
```

> **exit（AVG_COST 部分平仓）** — 拆单方式

```
exit(fill, side)
  record = (side == BUY) ? longRecord : shortRecord
  if fill.amount >= openPosition.amount
      // 全平：直接走原生 exit
      record.exit(fill)
  else
      // 部分平仓：手动拆为两个 Position
      closedPosition = new Position(entryTrade, exitTrade)    // 已平部分
      remainingPosition = new Position(remainingEntryTrade)   // 剩余部分
      record.getPositionBook().replaceLast(remainingPosition)  // 替换末位
      record.addClosedPosition(closedPosition)                // 加入已平仓
```

#### 13.3.2 回测层：复用原生 BarSeriesManager

**职责：** 不复写自定义回测管理器，直接使用原生 `BarSeriesManager`，多空各跑一次。

```
// 回测流程（伪代码）
BarSeriesManager manager = new BarSeriesManager(series, executionModel)

// 多头回测
TradingRecord longRecord = manager.run(longStrategy)
// 空头回测（对同一根 Series）
TradingRecord shortRecord = manager.run(shortStrategy)

// 合并结果
CompositeResult result = new CompositeResult(longRecord, shortRecord)
```

**为什么不需要自定义 BacktestManager：**

| 旧方案（MultiPositionBacktestManager） | 新方案 |
|----------------------------------------|--------|
| 自定义 for 循环，同时处理多空入场/出场 | 原生 BarSeriesManager 跑两次，逻辑清晰 |
| 内部耦合 DirectionalRule 和 ExitSignal | 原生 Strategy + Rule，无自定义接口 |
| 多策略并行需额外实现 | 外部用线程池并行调用两次即可 |
| 测试需自建 | 复用 ta4j 的 BarSeriesManagerTest |

**成交模型适配：**

| 回测类型 | 成交模型 | 说明 |
|---------|---------|------|
| 快速回测 | `TradeOnCurrentCloseModel` | 当前 K 线收盘价成交 |
| 传统回测 | `TradingOrderServiceAdapter`（自定义，实现 TradeExecutionModel） | 写订单到数据库，轮询模拟成交 |

#### 13.3.3 规则层：复用原生 Rule

**职责：** 不复写自定义的 `DirectionalRule`/`ExitSignal`，直接使用 ta4j 原生 `Rule` 接口。

**规则适用说明：**

原生的 ta4j `Rule` 返回值 `boolean` 足以表达出场信号。方向信息由对应方向的 `TradingRecord` 隐式携带：
- `longRecord.getExitRule()` 中的规则作用于多头持仓
- `shortRecord.getExitRule()` 中的规则作用于空头持仓

```
// 多头出场规则
Rule longExitRule = new OrRule(
    new StopLossRule(close, 0.05),        // -5% 止损
    new TakeProfitRule(close, 0.10),      // +10% 止盈
    new TrailingStopLossRule(close, 0.03) // 3% 移动止损
)

// 空头出场规则
Rule shortExitRule = new OrRule(
    new StopLossRule(close, 0.05),
    new TakeProfitRule(close, 0.10),
    new TrailingStopLossRule(close, 0.03)
)
```

**出场原因追溯：**

出场原因用 ta4j `Rule` 的 `describe()` 方法或自定义规则名称即可：
```
StopLossRule stopLoss = new StopLossRule(close, 0.05);
stopLoss.describe("STOP_LOSS_5%");  // ta4j 0.22.6 支持
```

**扩展的自定义 Rule（仍继承原生 Rule 接口）：**

| 规则 | 说明 | 备注 |
|------|------|------|
| `MacdCrossExitRule` | MACD 出场 | 继承 `AbstractRule` |
| `PinVolumeExitRule` | 放量出场 | 继承 `AbstractRule` |
| `TimeBasedStopLossRule` | 时间止损 | 继承 `AbstractRule` |
| `TimeBasedTakeProfitRule` | 时间止盈 | 继承 `AbstractRule` |
| `SmcDynamicExitRule` | SMC 动态出场 | 继承 `AbstractRule` |
| `SignalReversalExitRule` | 信号反转出场 | 继承 `AbstractRule` |
| `FixedStopLossRule` | 固定止损 | 继承 `AbstractRule` |
| `FixedTakeProfitRule` | 固定止盈 | 继承 `AbstractRule` |

这些规则都继承 ta4j 原生 `AbstractRule`（实现 `Rule` 接口），返回 `boolean`，不引入新的接口体系。

#### 13.3.4 策略层：复用原生 Strategy

**职责：** 不复写 `MultiPositionStrategy`，直接使用 ta4j 原生 `Strategy` 接口，多空各一个实例。

```
// 多头策略
Strategy longStrategy = new BaseStrategy(
    longEntryRule,    // Rule → boolean
    longExitRule      // Rule → boolean (OrRule 链)
)

// 空头策略
Strategy shortStrategy = new BaseStrategy(
    shortEntryRule,   // Rule → boolean
    shortExitRule     // Rule → boolean (OrRule 链)
)

// 回测执行
TradingRecord longRecord = manager.run(longStrategy);
TradingRecord shortRecord = manager.run(shortStrategy);
```

**策略模式对比：**

| 模式 | 入场规则来源 | 出场规则 | 说明 |
|------|-------------|---------|------|
| `indicator_driven` | `IndicatorDrivenRule`（指标条件） | `OrRule` 链 | 传统技术指标策略 |
| `multi_direction` | `SignalCacheManager` 生成 Rule | `OrRule` 链 | AI 信号驱动的双向策略 |

**SignalCacheManager 桥接：**

```
// SignalCacheManager 输出的是原生 Rule，而非 DirectionalRule
SignalCacheManager signalManager = new SignalCacheManager(redisTemplate);

Strategy longStrategy = new BaseStrategy(
    signalManager.getLongEntryRule(),    // 返回 Rule
    signalManager.getLongExitRule()      // 返回 Rule
)
Strategy shortStrategy = new BaseStrategy(
    signalManager.getShortEntryRule(),
    signalManager.getShortExitRule()
)
```

#### 13.3.5 执行层：execStrategy 双模式架构

**职责：** 统一实盘与回测的执行入口，通过 `testMode` 切换。

```
execStrategy(params)
├── initBarSeries()                       ← K 线初始化
├── buildStrategy()                       ← 构建多空两个 Strategy
├── rebuildRecordFromDB()                 ← DB→内存重建（仅实盘模式）
├── do
│     executeTradingLogic(lastIndex)
│     ├── 处理 PENDING 限价单撮合
│     ├── longStrategy.shouldExit(i, longRecord)  → OrRule 链
│     ├── shortStrategy.shouldExit(i, shortRecord) → OrRule 链
│     ├── processEntrySignals()                   ← 入场信号
│     └── sampleAndEnqueueEquityPoint()
│     updateBarSeries(nextBar)            ← K 线推进（仅测试模式）
│   while (isTradingActive())
└── 返回执行结果
```

**双模式差异：**

| 维度 | 测试模式（testMode=true） | 实盘模式（testMode=false） |
|------|--------------------------|--------------------------|
| 触发方式 | 用户手动触发 | XXL-JOB 定时调度 |
| K 线推进 | `do-while` 遍历所有 K 线 | 单次执行，无 K 线推进 |
| 订单持久化 | 写入数据库 | 写入数据库 |
| Redis 幂等 | 不启用 | 防止重复出场 |
| 分布式锁 | 不启用 | 防并发开仓 |
| Record 生命周期 | 复用整个回测过程 | 每次调度重建 |

#### 13.3.6 信号层：SignalCache 桥接

**职责：** 将 AI 模型产生的信号数据（Redis）桥接到交易引擎，生成原生 `Rule`。

```
SignalCacheManager
├── 从 Redis 读取信号数据
│     ├── 方向: LONG / SHORT
│     ├── 权重: 0.0 ~ 1.0
│     ├── 入场价格区间
│     └── 出场条件
├── 构建入场/出场 Rule（返回原生 Rule）
│     ├── getLongEntryRule()   → Rule   ← 多头入场条件
│     ├── getShortEntryRule()  → Rule   ← 空头入场条件
│     ├── getLongExitRule()    → Rule   ← 多头出场条件
│     └── getShortExitRule()   → Rule   ← 空头出场条件
└── 回测模式下从数据库注入历史信号
      └── buildInMemorySignalCache()
```

输出直接供给 `BaseStrategy` 构造器，无需 `SignalWeightedMultiPositionExecutionModel`。

#### 13.3.7 出场调度：OrRule 链

**职责：** 用 ta4j 原生 `OrRule` 组合多条件出场，替代自定义分层调度器。

```
// 多头出场规则链（短路 OR，任一满足即出场）
Rule longExitRule = new OrRule(
    new FixedStopLossRule(close, stopLossPercent),        // 固定止损
    new FixedTakeProfitRule(close, takeProfitPercent),    // 固定止盈
    new TrailingStopLossRule(close, trailPercent),        // 移动止损
    new MacdCrossExitRule(macd, signal),                  // MACD 出场
    new PinVolumeExitRule(volume, threshold),             // 放量出场
    new TimeBasedStopLossRule(series, maxHoldBars),       // 时间止损
    new SignalReversalExitRule(signalManager)             // 信号反转出场
)

// 空头出场规则链（独立配置，参数可与多头不同）
Rule shortExitRule = new OrRule(
    new FixedStopLossRule(close, shortStopLossPercent),
    new FixedTakeProfitRule(close, shortTakeProfitPercent),
    // ... 同上
)
```

**设计要点：**
- `OrRule` 是 ta4j 原生组合规则，短路求值（任一满足即停止）
- 多空规则链独立配置，参数可以不同
- 出场原因通过 `Rule.describe()` 获取规则名称，无需 `ExitType` 枚举
- 若需要 Redis 幂等，在 `execStrategy` 中统一检查，而非在规则内部

**与旧方案对比：**

| 维度 | 旧方案（分层出场） | 新方案（OrRule 链） |
|------|------------------|-------------------|
| 实现方式 | `processPositionExits()` + 6 层优先级 | 原生 `OrRule` 组合 |
| 代码量 | ~200 行自定义调度 | 0 行调度代码（纯配置） |
| 优先级控制 | 硬编码优先级数字 | OrRule 链顺序 = 优先级 |
| 扩展性 | 新增规则需修改调度器 | 新增规则只需追加到 OrRule |
| Redis 幂等 | 内嵌在调度器中 | `execStrategy` 统一处理 |

### 13.4 与 ta4j 架构对比

| 维度 | ta4j 原生 | 本系统扩展 | 扩展方式 |
|------|----------|-----------|---------|
| **交易记录** | `BaseTradingRecord` + `PositionBook` | `CompositeTradingRecord`（组合两个 BaseTradingRecord） | **组合** |
| **回测管理器** | `BarSeriesManager.run()` | **复用**原生，多空各跑一次 | **复用** |
| **策略接口** | `Strategy`（shouldEnter/shouldExit） | **复用**原生 `BaseStrategy`，多空各一个 | **复用** |
| **规则接口** | `Rule` → `boolean` | **复用**原生 `Rule`，`OrRule` 链组合 | **复用** |
| **规则组合** | `OrRule` / `AndRule` / `NotRule` | **复用**原生组合规则 | **复用** |
| **成交模型** | `TradeOnNextOpenModel` | `TradeOnCurrentCloseModel` / 自定义 | **实现** TradeExecutionModel |
| **成本模型** | `ZeroCostModel` | `RecordedTradeCostModel` | **实现** CostModel |
| **订单系统** | 纯内存 | DB 持久化（TradingOrderServiceAdapter） | **适配** TradeExecutionModel |
| **绩效指标** | `BasePerformanceReport` | `PerformanceMetrics`（Sharpe/Sortino 等） | **新增** 计算引擎 |
| **参数优化** | `BacktestExecutor` | Walk-Forward + 参数范围优化 | **扩展** BacktestExecutor |

### 13.5 扩展原则与约束

1. **不改 ta4j 源码** — 所有扩展通过 **组合**（优先）和继承（必要时）实现，`ta4j-master` 目录保持只读。
2. **优先复用，慎重新增** — `Strategy`、`Rule`、`BarSeriesManager`、`PositionBook` 等原生组件优先复用，只在 DB 适配层（`TradingOrderServiceAdapter`）和自定义 Rule（如 `MacdCrossExitRule`）处新增代码。
3. **组合优于继承** — `CompositeTradingRecord` 是组合模式的典型应用：两个原生 `BaseTradingRecord` 各自独立运行，通过组合实现双向交易。
4. **回测与实盘统一策略** — 同一套 `Strategy` + `Rule` 组合，回测和实盘使用相同的策略构造代码，只在执行方式（`testMode`）上区分。
5. **DB 是唯一持久化源** — 实盘模式内存 Record 每次从数据库重建，状态不依赖序列化。
6. **后续方向：**
   - 将多空策略构造提取为 `StrategyFactory`，统一管理 `longStrategy` + `shortStrategy` 的创建
   - `CompositeTradingRecord` 补充 `SPECIFIC_ID` 匹配策略
   - 绩效指标计算统一到 `PerformanceMetrics` 一处

## 遗留设计问题（待重构）

### 1. 策略路由逻辑问题

**问题描述**：策略类型通过 DB `strategy.class_name` 字段映射到代码路由，存在以下设计缺陷：

```
createBacktestTaskDTO
  → resolveStrategyClassName(UUID)  查 DB 取 class_name
  → strategyType = class_name       作为路由 key
  → createStrategyByType            硬编码匹配
```

**具体问题**：
- DB 里存的是旧的 `"signalBasedStrategyImpl"`，代码路由不认识，走到 `SpringContextUtil.getBean()` 报错
- 传统回测同样依赖 `class_name` 路由，但用 `equalsIgnoreCase` 匹配 `"multi_direction"`、`"indicator_driven"` 等字符串
- 快速回测用 `BacktestService.createStrategyByType()` 自己的路由表，与传统回测 `DefaultDealStrategyTrade.buildStrategy()` 的路由表是两套，维护成本高
- `class_name` 和代码中的策略别名（如 `"multi_direction"`）没有强绑定关系，改 DB 字段或代码都容易漏同步

**期望的改进方向**：统一路由表，所有回测路径走同一个策略解析入口。
