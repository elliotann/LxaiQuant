附录：内存模型全生命周期数据流转（设计文档 v1.12 最终版）
说明：本节旨在串联回测引擎中所有核心内存对象（MemoryPosition、EntryRecord、ActionRecord、TradeRecord）从创建、运行时变更到最终持久化的完整路径，帮助开发者理解“循环内零 I/O”与“事后反向聚合”的设计精髓。

二、核心对象生命周期详细流转（含关键字段演进）
1. MemoryPosition（持仓状态）的生命周期
   text
   [创建] ──► [持仓中] ──► [部分平仓] ──► [完全平仓] ──► [销毁 (置 null)]

具体流转：
Step 1: 开仓
BacktestContext.openPosition()
→ 判断方向 (LONG/SHORT)
→ 创建 MemoryPosition (positionId, symbol, direction, avgPrice, totalQuantity)
→ 添加第一个 EntryRecord 到 entries 列表
→ 赋值给 context.longPosition 或 context.shortPosition

Step 2: 持仓中（每 Bar 更新未实现盈亏）
BacktestContext.sampleEquity()
→ position.updateUnrealizedPnl(currentPrice)  // 仅计算，不改变 totalQuantity

Step 3: 加仓 (新增)
BacktestContext.addPosition()
→ position.addEntry(new EntryRecord)  // 追加到 entries 列表
→ position.avgPrice = 加权平均重算 (基于当前剩余数量)
→ position.totalQuantity += 新数量

Step 4: 部分平仓 (新增)
BacktestContext.reducePosition(closePercent=50%)
→ position.reduceQuantity(closeQty)  // FIFO 扣减 entries
├─ 从最早 entry 开始扣减 (修改 entry.quantity)
├─ 若 entry 被扣尽 → 从 entries 列表中移除
└─ 若 entry 部分扣减 → 修改其 quantity
→ position.totalQuantity -= closeQty
→ position.avgPrice 不变 (FIFO 方式不重算均价，保持历史成本)

Step 5: 完全平仓
BacktestContext.closePosition()
→ position.reduceQuantity(全部)  // 清空所有 entries
→ position.totalQuantity = 0
→ context.longPosition = null 或 context.shortPosition = null
→ 聚合生成 TradeRecord (见下方)
→ 此时 MemoryPosition 对象失去引用，等待 GC
2. EntryRecord（开仓明细）的演进与字段说明
   关键字段设计：

字段	类型	可变性	用途
entryId	String	不可变	唯一标识，关联平仓明细
positionId	String	不可变	归属仓位ID
initialQuantity	BigDecimal	不可变	原始开仓数量（用于聚合统计）
quantity	BigDecimal	可变	当前剩余数量（用于 FIFO 扣减）
price	BigDecimal	不可变	开仓价格
fee	BigDecimal	不可变	手续费
barIndex	int	不可变	开仓时的 K 线索引
text
[创建] ──► [归属持仓] ──► [被部分平仓] ──► [被完全平仓] ──► [归档]

具体流转：
Step 1: 开仓时创建
context.openPosition()
→ EntryRecord.builder()
.entryId(UUID)
.positionId(positionId)
.initialQuantity(开仓数量)   // 如 1.0
.quantity(开仓数量)          // 初始 = initialQuantity
.price(openPrice)
.fee(手续费)
.barIndex(i)
.build()
→ position.entries.add(record)
→ context.entryRecords.add(record)  // 全局列表（全量日志）

Step 2: 加仓时创建
context.addPosition()
→ 同样创建 EntryRecord，initialQuantity = quantity = 加仓数量
→ 追加到同一个 position.entries
→ 同样加入全局 entryRecords

Step 3: 部分平仓时修改 (FIFO)
context.reducePosition()
→ position.reduceQuantity() 遍历 entries
→ 若扣减部分数量: entry.setQuantity(entry.getQuantity() - remaining)  // 仅修改 quantity，initialQuantity 不变
→ 若扣尽: iterator.remove()  // 从 position.entries 移除（但全局 entryRecords 仍保留）

Step 4: 持久化时转换
flush() 阶段
→ EntryConverter.toEntity(entry) → TradeOrderItem
→ 使用 initialQuantity 作为入库的 volume（原始开仓量），quantity 作为当前剩余量（状态字段）
→ 即使 EntryRecord 已被移出 position.entries，它仍然在全局 entryRecords 中
→ 所有 EntryRecord 都会落库，用于审计追溯
3. ActionRecord（动作日志）的流转
   text
   [创建] ──► [追加] ──► [持久化]

具体流转：
Step 1: 任何交易动作发生时创建（不可变快照）
- 开仓 → ActionRecord(action="ENTRY", price, quantity, equityBefore, equityAfter)
- 加仓 → ActionRecord(action="SCALE_IN", ...)
- 全平 → ActionRecord(action="EXIT", pnl, exitType, equityBefore, equityAfter)
- 部分平 → ActionRecord(action="EXIT_PARTIAL", pnl, closePercent, ...)

示例 (平仓时):
BigDecimal equityBefore = getEquity(price);
position.reduceQuantity(...); // 修改状态
BigDecimal equityAfter = getEquity(price);
ActionRecord.builder()
.barIndex(i)
.action("EXIT")
.price(exitPrice)
.quantity(closeQty)
.pnl(realizedPnl)
.equityBefore(equityBefore)
.equityAfter(equityAfter)
.exitType(exitType)
.positionId(positionId)
.closedDetails(closedDetails)  // FIFO 逐笔明细 (entryId → 盈亏)
.build()
→ context.actionRecords.add(record)

Step 2: 持久化时转换
flush() 阶段
→ 过滤出 action="EXIT" 或 "EXIT_PARTIAL" 的 ActionRecord
→ ActionConverter.toCloseItemEntity() → TradeOrderCloseItem
→ 通过 closedDetails 中的 entryId 关联 TradeOrderItem.orderItemSn
4. TradeRecord（已平仓交易聚合）的生成时机与聚合逻辑
   text
   [触发条件] ──► [聚合生成] ──► [加入列表] ──► [持久化]

触发条件:
当 MemoryPosition.totalQuantity 由正数变为 0 时 (即完全平仓)

聚合过程 (context.closePosition() 内部):
Step 1: 从 context.entryRecords 中过滤该 positionId 的所有记录
Step 2: 计算累计开仓总量 = Σ entry.initialQuantity  (而非被修改后的 quantity)
Step 3: 计算加权平均开仓价 = Σ(entry.price × entry.initialQuantity) / 累计总量
Step 4: 从最近的 ActionRecord 中获取平仓价、平仓时间、ExitType
Step 5: 计算总盈亏 = Σ(平仓价 - 开仓价) × entry.initialQuantity × 方向
Step 6: 构建 TradeRecord (不可变)
TradeRecord.builder()
.positionId(positionId)
.symbol(symbol)
.direction(direction)
.entryPrice(加权均价)
.exitPrice(平仓价)
.quantity(累计开仓总量)  // 注意：使用 initialQuantity 总和
.pnl(总盈亏)
.entryTime(首次开仓时间)
.exitTime(平仓时间)
.exitType(exitType)
.build()
Step 7: context.trades.add(tradeRecord)

持久化:
flush() 阶段
→ TradeRecord 对应 TradeOrderClose (平仓批次主表)
→ 关联的 ActionRecord 对应 TradeOrderCloseItem (平仓明细表)

四、关键设计要点（避免混淆）
问题	答案
为什么要区分 EntryRecord 和 TradeRecord？	EntryRecord 是开仓明细（FIFO 扣减的最小单位），TradeRecord 是整笔交易的聚合（绩效计算的最小单位）。EntryRecord 是 1:N 的关系，TradeRecord 是 N:1 的聚合结果。
为什么 EntryRecord 要有 initialQuantity 和 quantity 两个字段？	quantity 用于循环内 FIFO 扣减（可变），initialQuantity 用于 flush() 时聚合统计（不可变）。两者分离避免了部分平仓后历史数据丢失的问题。
TradeOrder（仓位主表）为什么不直接从 MemoryPosition 转换？	因为回测循环结束时，longPosition / shortPosition 已被置为 null。TradeOrder 必须由 entryRecords 按 positionId 分组聚合生成，保证即使仓位已平、对象已销毁，仍能还原完整的主表记录。
部分平仓时，TradeRecord 何时生成？	只有当仓位完全平仓（totalQuantity 变为 0）时才生成。部分平仓只生成 ActionRecord，不生成 TradeRecord，因为绩效指标需要"完整交易"作为统计单位。
ActionRecord 为什么不直接操作 MemoryPosition？	ActionRecord 是"历史日志"（不可变），MemoryPosition 是"当前状态"（可变）。如果相互依赖，会导致对象图混乱、持久化时难以序列化。正确的做法是引擎调度：引擎从 MemoryPosition 读取数据 → 执行变更 → 将变更结果"拍快照"写入 ActionRecord。
MemoryPosition 和 TradeOrder 的关系是什么？	MemoryPosition 是运行时指针（临时对象），TradeOrder 是持久化实体（数据库记录）。MemoryPosition → TradeOrder 是 1:1 的逻辑映射（同一个仓位），但持久化时 TradeOrder 由日志聚合生成，而非直接转换。
