1. 背景与目标
1.1 现状
当前量化交易系统已具备完整的交易数据存储能力，包含以下核心表：

ai_trade_order — 仓位主表

ai_trade_order_item — 开仓明细

ai_trade_order_close — 平仓操作主表

ai_trade_order_close_item — 平仓明细

系统已支持：

多空双向交易

加减仓（同一仓位下多笔开仓）

部分平仓

1.2 痛点
表命名与字段语义与 ta4j 回测框架的核心概念不一致，导致回测与实盘数据难以统一管理。

平仓明细未直接关联仓位主表，查询复杂度高。

缺少仓位级别汇总字段，前端需要实时计算，性能较差。

平仓类型存储在平仓主表，不能支持明细级别不同原因。

1.3 目标
概念对齐：数据库模型与 ta4j 的 TradingRecord / Position / Trade 清晰对应

架构简化：最大程度复用 ta4j 原生组件，减少自定义接口

保留现有能力：支持多空、加减仓、部分平仓、FIFO 配对

最小改动：在现有表基础上重命名、增加字段，避免大规模迁移风险

**五层职责：**

| 层级 | 组件 | 职责 | 适用场景 |
|------|------|------|----------|
| 执行调度层 | DefaultDealStrategyTradeV7.execStrategy | 分布式锁 + 幂等 + 数据重建 + BarSeries 维护 + Worker 生命周期 | 实盘调度 |
| 回测执行层 | DualBarStrategy | 实现 ta4j Strategy 接口，包装多空两个 BaseStrategy，一次遍历完成双向回测 | 回测 |
| 执行模型层 | DirectionAwareExecutionModel | 方向感知 + 防重复下单 + 回调执行业务数据 | 回测 + 实盘 |
| 回调解耦层 | OrderExecutionCallback | @FunctionalInterface，解耦执行模型与业务 | 回测 + 实盘（callback 非空时写入业务数据） |
| 业务实现层 | OrderExecutionManager | 开仓/平仓/补仓/分批出场/限价单的全部业务逻辑 + 分布式锁 + 日内风控 | 实盘业务 |

**关键设计决策：**

- **不修改任何 ta4j 源码**，所有扩展均为新增组合/包装
- **数据与执行分离**：CompositeTradingRecord 不实现任何 ta4j 接口，仅作为两个原生 BaseTradingRecord 的容器
- **回测/实盘共享同一数据模型**：回测通过 DualBarStrategy 写入 CompositeTradingRecord，实盘通过 execStrategy 直接操作 CompositeTradingRecord
- **增量替换旧代码**：新增组件与旧 MultiPositionTradingRecord 等并存，逐步迁移后统一删除旧代码
- 数据库只持久化必要的交易数据，不存储会话表
- 定时任务启动时从数据库加载重建内存记录
- 运行过程中产生的开平仓同步写入数据库并更新内存

2.3 为什么选择组合方案
对比项	旧方案（MultiPositionTradingRecord）	新方案（CompositeTradingRecord + DualBarStrategy）
实现方式	自定义实现 TradingRecord 接口	数据层：组合两个原生 BaseTradingRecord；执行层：包装两个原生 BaseStrategy
代码量	~3000+ 行自定义代码	~800 行（核心模块，不含待迁移业务层），且均为新增，不修改原代码
自定义接口数	6+（DirectionalRule, ExitSignal 等）	仅新增 1 个回调接口 `OrderExecutionCallback`
双向管理	自定义 BUY/SELL 双 List	原生 PositionBook 各管各的
回测方式	需要自定义回测引擎	复用原生 BarSeriesManager + DualBarStrategy 一次遍历
实盘方式	依赖自定义 TradingRecord	直接操作 CompositeTradingRecord 的 longRecord/shortRecord
数据与执行耦合	耦合	解耦：数据聚合与执行逻辑分离
代码侵入性	侵入式，需修改多处调用	非侵入式，新增组件与旧代码并存，可逐步替换
测试覆盖	需自测全部逻辑	数据层继承 ta4j 原生测试保障；执行层独立可测

4.2 内存层：CompositeTradingRecord（数据聚合 POJO）
职责： 纯数据容器，不实现任何 ta4j 接口。内部持有 longRecord + shortRecord 两个原生 BaseTradingRecord，分别管理多头和空头持仓，提供聚合查询方法和绩效计算数据源。

**与 DualBarStrategy 的关系**：CompositeTradingRecord 是数据层，独立于回测方式。DualBarStrategy 是回测执行层，运行时将多空交易写入 CompositeTradingRecord。实盘执行层 execStrategy 也直接操作 CompositeTradingRecord。回测与实盘共享同一数据模型。

核心数据结构
java
public class CompositeTradingRecord {
    private final BaseTradingRecord longRecord;   // BUY→SELL
    private final BaseTradingRecord shortRecord;  // SELL→BUY
    private final ExecutionMatchPolicy matchPolicy; // FIFO / AVG_COST / SPECIFIC_ID
    // 可选：订单适配器（用于 DB 持久化）
    private TradingOrderServiceAdapter orderAdapter;
    
    public CompositeTradingRecord() {
        this.longRecord = new BaseTradingRecord(TradeType.BUY);
        this.shortRecord = new BaseTradingRecord(TradeType.SELL);
        this.matchPolicy = ExecutionMatchPolicy.AVG_COST;
    }
}

3. 部分平仓（AVG_COST 拆单）

由于 BaseTradingRecord 本身不支持部分平仓，我们需要手动拆单。拆单逻辑在 CompositeTradingRecord 中实现：

java
public void exitPartial(int index, Num price, Num amount, TradeType exitType) {
    BaseTradingRecord record = (exitType == TradeType.SELL) ? longRecord : shortRecord;
    Position currentPos = record.getCurrentPosition();
    if (currentPos == null || !currentPos.isOpened()) {
        throw new IllegalStateException("No open position to partial exit");
    }
    Num totalAmount = currentPos.getAmount();
    if (amount.isGreaterThanOrEqual(totalAmount)) {
        // 全平，直接调用原生 exit
        record.exit(index, price, amount);
        return;
    }
    
    // 拆单：创建已平仓部分 Position 和剩余部分 Position
    // 获取当前持仓的入场 Trade（假设单次入场，AVG_COST 模式下平均入场价）
    Trade entryTrade = currentPos.getEntry();
    Trade exitTrade = new Trade(index, price, amount, exitType);
    
    // 已平仓部分
    Position closedPosition = new Position(entryTrade, exitTrade);
    // 剩余部分：需要新建一个 Position，入场信息复制 entryTrade，但数量减少
    Trade remainingEntry = new Trade(entryTrade.getIndex(), entryTrade.getPrice(),
                                     totalAmount.minus(amount), entryTrade.getType());
    Position remainingPosition = new Position(remainingEntry);
    
    // 替换 record 内部的 PositionBook 中的最后一个 Position
    // 注意：需要反射或通过扩展方法，因原生 PositionBook 不提供 replace 方法
    // 本系统通过自定义 Record 子类或使用 PositionBook 的 removeLast + add 实现
    replaceLastPosition(record, remainingPosition);
    record.getClosedPositions().add(closedPosition);
}
为了不修改 ta4j 源码，我们采用扩展 BaseTradingRecord 的方式实现上述替换操作，但该扩展不对外暴露，仅内部使用。

4. 从数据库重建

java
public void rebuildFromDB(TradingOrderServiceAdapter adapter, String accountId, String symbol) {
    List<PositionEntity> openPositions = adapter.loadOpenPositions(accountId, symbol);
    for (PositionEntity pos : openPositions) {
        Trade entry = new Trade(pos.getEntryIndex(), pos.getEntryPrice(), 
                                pos.getTotalEntryQty(), pos.getSide());
        if (pos.getSide() == TradeType.BUY) {
            longRecord.enter(entry);
        } else {
            shortRecord.enter(entry);
        }
        // 加载该仓位下所有已平仓明细？不需要，因为已平仓不会影响未平仓状态
        // 但对于部分平仓，需要调整 remaining_qty，已经在 entry 中保存了剩余数量？
        // 实际重建时，需要将开仓明细中 remaining_qty > 0 的视为未平仓部分。
        // 简化方案：每个开仓明细单独作为一个 Trade（不支持合并平均价）
        // 当使用 AVG_COST 时，需要将同一方向所有未平仓明细合并为一个 Position
    }
}
实际重建时，需根据持仓模型（FIFO / AVG_COST）分别处理。本文档假设系统采用 AVG_COST 模式，则重建时将同一方向所有未平仓的 entry 合并为一个加权平均入场价的 Position，剩余数量为总和。

4.3 回测层：支持两种方式
方式一：两次独立回测（简单、无需同时双向持仓）
java
BarSeriesManager manager = new BarSeriesManager(series);
TradingRecord longRecord = manager.run(longStrategy);
TradingRecord shortRecord = manager.run(shortStrategy);
CompositeTradingRecord composite = new CompositeTradingRecord();
// 合并结果（如需）
方式二：DualBarStrategy（支持同时双向持仓，如对冲、网格）
DualBarStrategy 是一个继承 ta4j `BaseStrategy` 的包装器，它内部持有 `CompositeTradingRecord` 和多空两个 `BaseStrategy`，在 `shouldOperate` 中手动调用入场/出场逻辑。**与旧设计文档的区别：**
- 继承 `BaseStrategy` 而非实现 `Strategy`（兼容 ta4j 构造函数要求）
- 使用 `TradeExecutionModel.execute()` 统一入口，而非分离的 `enter()/exit()`
- 始终返回 `false` 阻止原生 `BarSeriesManager` 操作传入的 `dummyRecord`

**文件**: `ai-extension/.../v7/DualBarStrategy.java` ✅

```java
public class DualBarStrategy extends BaseStrategy {
    private final Strategy longStrategy;
    private final Strategy shortStrategy;
    private final CompositeTradingRecord compositeRecord;
    private final TradeExecutionModel executionModel;
    private final BarSeries series;
    private final Num amountPerTrade;

    public DualBarStrategy(Strategy longStrategy, Strategy shortStrategy,
                           CompositeTradingRecord compositeRecord,
                           TradeExecutionModel executionModel,
                           BarSeries series, Num amountPerTrade) {
        // BaseStrategy 必须传入 entryRule/exitRule，传入 dummy
        super((Rule) (i, r) -> false, (Rule) (i, r) -> false);
        this.longStrategy = longStrategy;
        this.shortStrategy = shortStrategy;
        this.compositeRecord = compositeRecord;
        this.executionModel = executionModel;
        this.series = series;
        this.amountPerTrade = amountPerTrade;
    }

    @Override
    public boolean shouldOperate(int index, TradingRecord dummyRecord) {
        // 出场优先（先平后开，避免方向冲突）
        if (longStrategy.shouldExit(index, compositeRecord.getLongRecord()))
            executionModel.execute(index, compositeRecord.getLongRecord(), series, amountPerTrade);
        if (shortStrategy.shouldExit(index, compositeRecord.getShortRecord()))
            executionModel.execute(index, compositeRecord.getShortRecord(), series, amountPerTrade);
        // 入场
        if (longStrategy.shouldEnter(index, compositeRecord.getLongRecord()))
            executionModel.execute(index, compositeRecord.getLongRecord(), series, amountPerTrade);
        if (shortStrategy.shouldEnter(index, compositeRecord.getShortRecord()))
            executionModel.execute(index, compositeRecord.getShortRecord(), series, amountPerTrade);
        // 阻止原生 BarSeriesManager 操作 dummyRecord
        return false;
    }
}
```

    new DirectionAwareExecutionModel(new TradeOnCurrentCloseModel());

// 结果在 composite 中

### DirectionAwareExecutionModel（方向感知执行模型）✅

**文件**: `ai-extension/.../v7/DirectionAwareExecutionModel.java`

**职责**：实现 `TradeExecutionModel` 接口的方向感知包装器。在委托给实际执行模型更新内存记录之前，提取交易方向并触发实盘回调。

**核心功能**：
1. **方向识别**：通过 `TradingRecord.isClosed()` 判断入场/出场，通过 `getStartingType()` 或 `getEntry().getType()` 获取方向。
2. **防重复下单**：同一 index 内相同 `(direction, isEntry)` 组合只回调一次。
3. **callback 非空时执行业务数据**：由调用方决定是否传入 `OrderExecutionCallback`（回测/实盘均可选择写入业务数据）。

```java
public class DirectionAwareExecutionModel implements TradeExecutionModel {

    private final TradeExecutionModel delegate;
    private final OrderExecutionCallback callback;

    private int lastProcessedIndex = -1;
    private final Set<String> processedKeys = new HashSet<>();

    public DirectionAwareExecutionModel(TradeExecutionModel delegate) {
        this(delegate, null);
    }

    public DirectionAwareExecutionModel(TradeExecutionModel delegate,
                                         OrderExecutionCallback callback) {
        this.delegate = Objects.requireNonNull(delegate);
        this.callback = callback;
    }

    @Override
    public void execute(int index, TradingRecord record, BarSeries series, Num amount) {
        boolean isEntry = record.isClosed();
        TradeType direction = isEntry ? record.getStartingType()
                                      : record.getCurrentPosition().getEntry().getType();

        // 防重复下单：同一 index 内相同方向+入场/出场的组合只执行一次
        if (callback != null) {
            if (index != lastProcessedIndex) {
                processedKeys.clear();
                lastProcessedIndex = index;
            }
            String key = direction + ":" + isEntry;
            if (processedKeys.contains(key)) {
                log.debug("跳过重复订单: index={}, direction={}, isEntry={}", index, direction, isEntry);
                delegate.execute(index, record, series, amount);
                return;
            }
            processedKeys.add(key);
            Bar bar = series.getBar(index);
            long barTime = bar.getBeginTime().toEpochMilli();
            callback.onOrder(isEntry, direction,
                             bar.getClosePrice(), amount, barTime);
        }

        log.info("{} {} at index={}, price={}, amount={}",
                 isEntry ? "ENTRY" : "EXIT", direction, index,
                 series.getBar(index).getClosePrice(), amount);

        delegate.execute(index, record, series, amount);
    }
}
```

使用示例：

```java
// 回测模式：不传 callback，仅更新内存

    new DirectionAwareExecutionModel(new TradeOnCurrentCloseModel());

// 实盘/写业务数据模式：传入 callback
DirectionAwareExecutionModel executionModel =
    new DirectionAwareExecutionModel(new TradeOnCurrentCloseModel(),
            orderExecutionManager.buildCallback());
```

public class StopLossRule extends AbstractRule {
    private final Indicator<Num> priceIndicator;
    private final Num percentage;

    public StopLossRule(Indicator<Num> priceIndicator, double percentage) {
        this.priceIndicator = priceIndicator;
        this.percentage = priceIndicator.getBarSeries().numFactory().numOf(percentage);
    }

    @Override
    public boolean isSatisfied(int index, TradingRecord record) {

        Position current = record.getCurrentPosition();
        Num entryPrice = current.getEntry().getPrice();
        Num currentPrice = priceIndicator.getValue(index);
        if (record.getStartingType() == TradeType.BUY) {
            return currentPrice.isLessThanOrEqual(entryPrice.multipliedBy(numOf(1).minus(percentage)));
        } else {
            return currentPrice.isGreaterThanOrEqual(entryPrice.multipliedBy(numOf(1).plus(percentage)));
        }
    }
}

### 4.7 OrderExecutionManager（业务执行管理器）✅

**位置**: `ai-engine/.../core/impl/OrderExecutionManager.java`（新建 Spring @Service）

**职责**：承担完整的实盘订单业务实现，接收 `OrderExecutionCallback` 回调后执行开仓/平仓/补仓/限价单全部业务逻辑，是 v7 架构的**业务实现层**。

#### 核心接口

```java
@Service
public class OrderExecutionManager {

    // 依赖注入
    private final TradeOrderServiceAdapter orderAdapter;
    private final IntradayRiskManager riskManager;
    private final RedissonDistributedLock distributedLock;

    /**
     * 统一订单执行入口 - 被 OrderExecutionCallback 调用
     */
    public void executeOrder(boolean isEntry, int index,
                             TradeType direction, BigDecimal price, BigDecimal amount) {
        // 分布式锁 + Redis 幂等检查
        String lockKey = buildLockKey(direction, isEntry, index);
        if (!distributedLock.tryLock(lockKey, 5, TimeUnit.SECONDS)) {
            log.warn("获取分布式锁失败: {}", lockKey);
            return;
        }
        try {
            if (isEntry) {
                handleEntry(direction, price, amount);
            } else {
                handleExit(direction, price, amount);
            }
        } finally {
            distributedLock.unlock(lockKey);
        }
    }
}
```

| 方法 | 职责 | 状态 |
|------|------|------|
| `handleEntry()` | 开仓：仓位计算 -> 日内风控 -> 补仓判断 -> 订单创建 | ✅ |
| `handleExit()` | 平仓：FIFO 分摊遍历持仓 -> 逐笔 closeOrderByVolumeExact | ✅ |
| `suppOrder()` | 补仓：浮亏比例 + 时间间隔 + EMA 趋势对齐判断 | ✅ |
| `applyLossSupplementItemTakeProfit()` | 补仓止盈价计算（TechnicalSignal -> 固定百分比） | ✅ |
| `calculateOrderAmount()` | 仓位计算（PositionAdjuster -> TradingUtil 合约折算回退） | ✅ |

| `startPendingOrderWorker()` | 启动限价单轮询 Worker（ScheduledExecutorService） | ✅ |

### 4.8 EquityCurveBuilder（盯市权益曲线）✅

**文件**: `ai-extension/.../v7/EquityCurveBuilder.java`

**职责**：输入 `CompositeTradingRecord` + `BarSeries` + `initialCash`，使用事件驱动增量算法计算每个 Bar 结束时的盯市权益。

**算法**：
1. 收集多空双方所有交易事件（TradeEvent），按 bar index 排序。
2. 逐 bar 处理：
   - 买入：现金减少，净持仓增加。
   - 卖出：现金增加，净持仓减少。
   - 当前 bar 权益 = 现金 + 净持仓 × 当前收盘价。
3. 输出 `EquityCurve`（权益值列表 + BarSeries）。

**权益采样 sampleAndEnqueueEquityPoint**：每根 K 线执行后，从 `CompositeTradingRecord` 计算总盯市利润：
- `longRecord` / `shortRecord` 逐方向聚合已平仓利润 + 当前仓位盯市利润。
- 写入 Redis ZSET，score = 时间戳/10000。

### 4.13 策略信号层重构：SignalMultiDirectionStrategy → 原生 Rule

**文件**：`ai-strategy/.../rule/SignalMultiDirectionStrategy.java`（待删除）
**文件**：`ai-engine/.../impl/DefaultDealStrategyTradeV7.java` `buildStrategy()` 方法（待修改）

#### 4.13.1 当前架构问题

当前 `buildStrategy()` 使用 `SignalMultiDirectionStrategy` 作为信号入场 + 组合出场的统一调度器：

```
buildStrategy()
  ├── 构建 combinedExit（DirectionalRule 组合链）
  ├── SignalMultiDirectionStrategy(series, signalCacheManager, combinedExit, name)
  │    └── 实现 MultiPositionStrategy（遗留自定义接口）
  │         ├── shouldEnterDirection(index, record) → TradeType
  │         └── shouldExitDirection(index, record) → TradeType
  └── lambda Rule 包装（将 TradeType 比较转为 boolean）
       ├── longEntry  = (i, r) → shouldEnterDirection(i, longRecord) == BUY
       ├── longExit   = (i, r) → shouldExitDirection(i, longRecord) == BUY
       ├── shortEntry = (i, r) → shouldEnterDirection(i, shortRecord) == SELL
       └── shortExit  = (i, r) → shouldExitDirection(i, shortRecord) == SELL
```

**问题：**

1. **多余的抽象层**：`SignalMultiDirectionStrategy` + `MultiPositionStrategy` 引入了非 ta4j 标准的自定义接口，然后又被 lambda `Rule` 包装回去，多了一层间接调用。
2. **出场规则双接口**：出场规则（MACD、pin bar、time-based、SMC）实现 `DirectionalRule`（`getDirection()` 返回 `TradeType`），而 `SignalMultiDirectionStrategy` 内部又将它们包裹在 `shouldExitDirection()` 中。本质上是方向特定的 boolean 判断，用原生 `Rule` 即可表达。
3. **维护成本**：`MultiPositionStrategy` 是 Phase 2 计划删除的遗留接口之一。保留它意味着每次改动要同时维护两套接口。
4. **可读性损失**：`buildStrategy` 中 8 行 lambda Rule 通过间接调用传递方向，不如直接声明"入场规则类"直观。

#### 4.13.2 替换方案

**核心思路**：将 `SignalMultiDirectionStrategy` 拆解为多个原生 `Rule` 实现，分别处理入场/出场/方向。组合方式从"一个包装器 + lambda 适配"变为"多个原生 Rule 直接组合"。

##### 新类关系图

```
buildStrategy()
  │
  ├── 入场规则（原生 Rule）
  │   ├── SignalLongEntryRule  (implements Rule)
  │   │    └── isSatisfied(index, record) → signal == "LONG" && SMC 允许
  │   └── SignalShortEntryRule (implements Rule)
  │        └── isSatisfied(index, record) → signal == "SHORT" && SMC 允许
  │
  ├── 出场规则（原生 Rule 组合）
  │   ├── SignalLongExitRule   (implements Rule) — 信号反转退出多
  │   ├── SignalShortExitRule  (implements Rule) — 信号反转退出空
  │   ├── DirectionalExitRuleAdapter (implements Rule) — 包装已有 DirectionalRule
  │   │    └── isSatisfied(index, record) → wrapped.getDirection(index, record) == direction
  │   └── combinedExitRule = OrRule.of(signalExitLong, ruleAdapterList)
  │
  └── 组装 BaseStrategy
      ├── longStrategy  = BaseStrategy(longEntry,  combinedExitLong)
      └── shortStrategy = BaseStrategy(shortEntry, combinedExitShort)
```

##### 入场规则设计

`MultiDirectionEntryRule.getDirection()` 的核心逻辑拆解为两个方向特定的原生 `Rule`：

```java
// 新类：SignalLongEntryRule
public class SignalLongEntryRule implements Rule {
    private SignalCacheManager signalCacheManager;
    // 构造函数注入 signalCacheManager

    @Override
    public boolean isSatisfied(int index, TradingRecord record) {
        SignalInfo signal = signalCacheManager.getSignal(index, series);
        if (signal == null || !"LONG".equals(signal.getSignalType())) {
            return false;
        }
        // 沿用现有 allowDirection() SMC 方向过滤逻辑
        return allowDirection(index, TradingRecord, TradeType.BUY, signal);
    }
}

// 新类：SignalShortEntryRule（对称逻辑）
public class SignalShortEntryRule implements Rule {
    @Override
    public boolean isSatisfied(int index, TradingRecord record) {
        SignalInfo signal = signalCacheManager.getSignal(index, series);
        if (signal == null || !"SHORT".equals(signal.getSignalType())) {
            return false;
        }
        return allowDirection(index, TradingRecord, TradeType.SELL, signal);
    }
}
```

**说明**：
- `record` 参数由 `DualBarStrategy.shouldOperate()` 传入——long 策略收到 `compositeRecord.getLongRecord()`，short 策略收到 `compositeRecord.getShortRecord()`。
- 无需额外传递 `CompositeTradingRecord`，Rule 只做信号匹配判断，持仓查询由上层通过 `TradingRecord` 参数提供。
- SMC 方向过滤逻辑（`allowDirection()`）从原 `MultiDirectionEntryRule` 中提取为静态工具方法，或直接内联到新 Rule 中。

##### 出场规则设计

**信号反转退出**（当前由 `MultiDirectionExitRule` 实现）：

拆分为两个方向特定的原生 Rule：

```java
public class SignalLongExitRule implements Rule {
    @Override
    public boolean isSatisfied(int index, TradingRecord record) {
        // 当前有多头持仓？
        Position currentPosition = record.getCurrentPosition();
        if (currentPosition == null || !currentPosition.isOpened()) return false;
        // 信号没有反转或信号变空白则退出
        SignalInfo signal = signalCacheManager.getSignal(index, series);
        return signal == null || !"LONG".equals(signal.getSignalType());
    }
}

public class SignalShortExitRule implements Rule {
    @Override
    public boolean isSatisfied(int index, TradingRecord record) {
        Position currentPosition = record.getCurrentPosition();
        if (currentPosition == null || !currentPosition.isOpened()) return false;
        SignalInfo signal = signalCacheManager.getSignal(index, series);
        return signal == null || !"SHORT".equals(signal.getSignalType());
    }
}
```

**注意**：当前 `MultiDirectionExitRule` 的实现细节需确认是否有多头信号变"SHORT"时就平多、反之亦然。若存在此逻辑，则退出条件更丰富，但拆分方向特定的 Rule 依然能做到。

**技术出场规则适配**（MACD、pin bar、time-based、SMC 的 `DirectionalRule`）：

现有实现保持不动，新增一个通用适配器将 `DirectionalRule` 包装为原生 `Rule`：

```java
public class DirectionalExitRuleAdapter implements Rule {
    private final DirectionalRule delegate;
    private final TradeType direction;  // BUY 或 SELL

    public DirectionalExitRuleAdapter(DirectionalRule delegate, TradeType direction) {
        this.delegate = delegate;
        this.direction = direction;
    }

    @Override
    public boolean isSatisfied(int index, TradingRecord record) {
        return delegate.getDirection(index, record) == direction;
    }
}
```

**出场规则组合**：

```java
// 多头出场 = 信号反转退出 OR 任何技术规则触发多头出场
Rule longExit = OrRule.of(
    new SignalLongExitRule(signalCacheManager, series),
    new DirectionalExitRuleAdapter(macdRule, TradeType.BUY),
    new DirectionalExitRuleAdapter(pinBarRule, TradeType.BUY),
    new DirectionalExitRuleAdapter(smcExitRule, TradeType.BUY),
    // ... time-based TP/SL 同理
);

// 空头出场 = 信号反转退出 OR 任何技术规则触发空头出场
Rule shortExit = OrRule.of(
    new SignalShortExitRule(signalCacheManager, series),
    new DirectionalExitRuleAdapter(macdRule, TradeType.SELL),
    new DirectionalExitRuleAdapter(pinBarRule, TradeType.SELL),
    new DirectionalExitRuleAdapter(smcExitRule, TradeType.SELL),
    // ... time-based TP/SL 同理
);
```

```java

    // 1. 加载信号数据（不变）
    loadSignalData(params);

    // 2. 构建出场规则（不变，仍为 DirectionalRule，保留适配器复用它们）
    List<DirectionalRule> exitRules = new ArrayList<>();
    // ... 同上，不重复 ...

    // 3. 构建入场 Rule
    Rule longEntry  = new SignalLongEntryRule(signalCacheManager, series);
    Rule shortEntry = new SignalShortEntryRule(signalCacheManager, series);

    // 4. 构建出场 Rule（DirectionalRule → 方向适配）

        new SignalLongExitRule(signalCacheManager, series),

        new SignalShortExitRule(signalCacheManager, series),

    Strategy shortStrategy = new BaseStrategy(shortEntry, shortExit);

    // 6. 创建执行模型 + DualBarStrategy（不变）
    DirectionAwareExecutionModel executionModel = ...;
    return new DualBarStrategy(longStrategy, shortStrategy, compositeRecord,
            executionModel, series, amountPerTrade);

```

#### 4.13.3 关键设计决策

| 决策 | 选项 | 选择理由 |
|------|------|----------|
| 技术出场规则是否重构为原生 Rule | A) 全部重写为原生 Rule | 保留 `DirectionalRule` 实现并用 `DirectionalExitRuleAdapter` 包装。已有 6+ 个 `DirectionalRule` 实现（MACD、pin bar、SMC、time-based 等），全部重写工作量大且易引入回归。适配器模式改动量小，单方向过滤逻辑清晰。 |
| 入场规则是否保留 SMC 过滤 | 保留 | `allowDirection()` 过滤逻辑是 V7 现有功能，拆解时应完整保留。 |
| `DirectionalExitRuleAdapter` 放在哪个模块 | `ai-extension` | 属于通用适配器，与 `DirectionalRule` 接口同模块，不依赖具体业务。 |
| `SignalLongEntryRule`/`SignalShortEntryRule` 放在哪个模块 | `ai-strategy` | 依赖 `SignalCacheManager`，与信号处理同层。 |

#### 4.14.2 需求分析

**关键前提**：入场规则已有 `long` 和 `short` 两个独立配置区（见前端 `entryRules` 结构），"信号规则"应作为指标选项分别配置在两边：

```
entryRules.long.conditions  →  多头入场条件（信号规则：仅匹配 LONG 信号）
entryRules.short.conditions →  空头入场条件（信号规则：仅匹配 SHORT 信号）
```

用户期望的场景：

1. **纯信号入场**：在 `long` 区添加"信号规则"作为唯一条件，TradingView 推送 `LONG` 信号时入场多；在 `short` 区添加"信号规则"，推送 `SHORT` 信号时入场空
2. **信号+指标组合**：信号条件 + 技术指标 AND/OR，例如 `long` 区："信号为 LONG **且** RSI>50"
3. **多空独立控制**：可以仅用信号入场多（`long` 配信号），同时用技术指标入场空（`short` 不配信号、配 RSI）；反之亦然

这与 `SignalMultiDirectionStrategy` → 原生 Rule 重构（4.13）目标一致——信号规则不再是特殊的黑盒，而是可配置的原生 Rule，且天然尊重多空分区。

#### 4.14.5 与 V7 buildStrategy 的集成

信号规则是"入场规则配置"中的一个条件选项，而非独立于 `entryRules` 的配置。因此其集成流程为：

```
用户编辑策略
  │
  ├── 入场规则配置（entryRules）
  │    ├── long.conditions = [{indicator:"signal"}, {indicator:"rsi", ...}]  // 信号+指标组合
  │    └── short.conditions = [{indicator:"signal"}]                          // 仅信号
  │
  ▼
StrategyEntryRuleServiceImpl.saveEntryRules()
  ├── indicator="signal" → indicator_type = "SIGNAL", indicator_params = {"signalType":"LONG"}
  └── indicator="rsi"    → indicator_type = "RSI", indicator_params = {"period":14}
  │
  ▼
StrategyFactory.buildIndicatorDrivenEntryRule()
  └── IndicatorDrivenDirectionRule.buildFromConditions(conditions, direction, series, signalCacheManager)
       ├── conditions[0] (SIGNAL) → SignalLongEntryRule 逻辑   ← 方向由 section 决定
       └── conditions[1] (RSI)    → RSI > 50 Rule 逻辑
       ├── AND 组合 → 信号为 LONG **且** RSI > 50 才入场多
  │
  ▼
buildStrategy()
  ├── 多头入场: OrRule.of(SignalLongEntryRule, RSIOverRule)  ← 从 IndicatorDrivenDirectionRule 拆解
  └── 空头入场: SignalShortEntryRule                          ← 同理
```

**入场规则组合表**（按 section 分别说明）：

| section | 配置 | 行为 |
|---------|------|------|
| `long` | 仅 `{indicator:"signal"}` | 只有 LONG 信号时入场多 |
| `long` | `{indicator:"signal"} AND {indicator:"rsi", gt:50}` | LONG 信号 **且** RSI>50 时入场多 |
| `long` | `{indicator:"signal"} OR {indicator:"macd", cross_up}` | LONG 信号 **或** MACD 金叉时入场多 |
| `long` | 不含 signal | 仅技术指标决定入场（当前行为，不变） |
| `short` | 仅 `{indicator:"signal"}` | 只有 SHORT 信号时入场空 |
| `short` | `{indicator:"signal"} AND {indicator:"rsi", lt:30}` | SHORT 信号 **且** RSI<30 时入场空 |
| `short` | 不含 signal | 仅技术指标决定入场（当前行为，不变） |

**重要说明**：`long` section 的 signal 条件**只匹配 LONG 信号**，`short` section 只匹配 SHORT 信号。这是由 section 上下文隐式决定的，用户 UI 上无需选择信号类型。

#### 4.14.6 关键设计决策

| 决策 | 选项 | 选择 |
|------|------|------|
| 信号方向如何绑定 | A) 由 section 隐式决定：long→LONG, short→SHORT | **隐式绑定**。UI 最简洁，符合直觉，无需新增下拉框 |
|  | B) 用户手动在条件中选择 signalType | 增加复杂度，极少用户需要反手入场 |
| signalType 存哪个字段 | A) threshold 字段复用 | **threshold**（保持字段通用性，减少 DB 迁移） |
|  | B) 新增 signal_type 列 | 不必要的 schema 变更 |
| `SignalCacheManager` 注入方式 | A) `buildFromConditions` 传参 | **传参**（`StrategyFactory` 已持有，改动最小） |
|  | B) Spring 静态上下文查找 | 隐式依赖，不推荐 |
| 信号规则与技术指标规则的关系 | A) 统一在 `IndicatorDrivenDirectionRule` 中处理 | **统一处理**（`buildSingleCondition` 新增 SIGNAL 分支，纯指标配置传 null 不受影响） |
|  | B) 在 `buildStrategy()` 中单独处理 | 增加复杂度 |
| 信号规则与 V7 原 `SignalLongEntryRule` 的关系 | A) 共享同一逻辑，`SignalLongEntryRule` 内部判断 signalType | **两者本质相同**，4.13 的 `SignalLongEntryRule` 就是 `SIGNAL` + `signalType=LONG` 的 Rule 实现 |
|  | B) 两套独立实现 | 不合并，走通即可 |

#### 4.14.7 Phase 2 删除影响

### 4.15 出场规则 DB 配置化

#### 4.15.1 现状分析

当前 V7 出场规则与旧系统共用 `loadExitRulesConfig()` + `StrategyParameter` 表（group=`exit_rules`），但存在以下问题：

1. **信号反转出场硬编码**：`SignalLongExitRule`/`SignalShortExitRule` 不受任何开关控制，始终启用
2. **缺少出场规则开关控制**：旧系统 DB 中有 `signalReversalExitEnabled`、`smcExitEnabled` 等开关，V7 未接入
3. **缺失旧系统的规则类型**：分批止盈/止损（`BatchTakeProfitRule`/`BatchStopLossRule`）、移动止盈/止损（`TrailingStopGainRule`/`TrailingStopLossRule`）、固定百分比止损（`FixedPercentStopLossRule`）在 V7 中未实现
4. **出场规则与入场规则配置方式不统一**：入场规则走 `trading_strategy.entry_rules` JSON 字段，出场规则走 `StrategyParameter` 表

#### 4.15.2 设计目标

- **配置化**：出场规则与入场规则一样，通过 JSON 配置化，支持开关控制
- **与旧系统逻辑一致**：出场规则的行为与旧系统保持一致，不改逻辑只改加载方式
- **统一存储**：出场规则配置存入 `trading_strategy` 表新增字段 `exit_rules_config TEXT`
- **渐进式迁移**：新增配置与旧 `StrategyParameter` 并存，线上验证后删除旧加载路径
