#### 5.13.3 跨应用推送方案（Redis Pub/Sub）

**问题背景：**

- 前端 WebSocket 连接建立在 `ai-quant` 应用上（端口 8080，唯一提供 HTTP/WS 服务的模块）
- `ai-task`（端口 8081，XXL-JOB 执行器独立模块）、`ai-backtest`、`ai-signal` 等模块**没有 WebSocket 端点**，无法直接推送到前端
- 即使这些模块启动 WebSocket，前端也不连接它们，推送仍然到不了

**解决方案：**

以 Redis Pub/Sub 作为跨应用消息总线，将推送分为三个角色：

| 角色 | 模块 | 职责 | 与前端关系 |
|---|---|---|---|
| **发布者** | ai-task / ai-backtest / 任意模块 | 调用 `SignalMessagePublisher` 发布消息到 Redis | ❌ 不直接连前端 |
| **消息总线** | Redis | 承载 `signal:push` 频道，中转消息 | — |
| **订阅转发者** | **ai-quant（唯一）** | 订阅 Redis，通过 `SimpMessagingTemplate` 转发 STOMP | ✅ 持有前端 WS 连接 |

```text
┌─────────────────────────────────────────────┐
│  ai-task (8081)  /  ai-backtest  /  ...      │
│    └─ @Autowired SignalMessagePublisher      │  ← 业务代码主动调用
│        └─ RedisSignalPublisher               │
│            └─ Redis PUBLISH "signal:push"     │
└──────────────────┬──────────────────────────┘
                   │ (跨进程，跨端口)
                   ▼
┌──────────────────────────────────────────────┐
│           Redis Pub/Sub 消息总线               │
│           Channel: "signal:push"              │
└──────────────────┬───────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────┐
│   ai-quant (8080) — 订阅转发                  │
│   RedisPubSubConfig                          │
│     └─ SignalRedisSubscriber                 │
│         └─ SimpMessagingTemplate             │
│             .convertAndSend("/topic/signals") │
└──────────────────┬───────────────────────────┘
                   │ STOMP WebSocket
                   ▼
┌──────────────────────────────────────────────┐
│   前端（连接 ai-quant:8080/ws）                │
│   STOMP 收到 /topic/signals 消息              │
└──────────────────────────────────────────────┘
```

**关键设计原则：**
1. **发布方只发 Redis，不碰 WebSocket** — ai-task 等模块只需注入 `SignalMessagePublisher`，调用 `push()` / `pushSignal()` 即可
2. **订阅转发只在 ai-quant** — 只有 ai-quant 持有 `SimpMessagingTemplate`，负责 Redis → STOMP 的转换
3. **前端只连 ai-quant** — 前端始终只连接 `ai-quant:8080/ws`，端口隔离不受影响

**核心消息体（SignalPushMessage）：**

```java
public class SignalPushMessage {
    // 消息类型
    private String type;              // NEW_SIGNAL | TRADE_UPDATE | SYSTEM_NOTIFY | TASK_PROGRESS
    // 消息来源
    private String source;            // AI_LIVE_ADVICE_SCHEDULED | AI_RADAR | BACKTEST | ML_TRAINING | SYSTEM
    // 标的（可选）
    private String symbol;
    // 方向（可选）
    private String direction;         // BUY | SELL | LONG | SHORT
    // 数值负载（可选，如信号强度、价格等）
    private Map<String, Object> data;
    // 时间戳
    private long timestamp;
    // TTL 有效期（分钟，可选）
    private Integer ttlMinutes;
}
```

**Redis 频道设计：**

| 频道名 | 用途 | 发布者 | 订阅者 |
|---|---|---|---|
| `signal:push` | 通用信号推送 | 任意模块 | ai-quant |
| `signal:push:{module}` | 模块级推送（预留） | 指定模块 | ai-quant |

#### 5.13.14 异步通知架构

##### 5.13.14.1 设计原则

所有通知发送都是异步的，核心原则：

```
业务主流程（交易执行/信号生成）
    │
    │ 不阻塞：发送通知 ≈ 毫秒级（实际是提交到线程池）
    ▼
主流程继续执行 ← ← ← ← ← 立即返回
                           
                           ┌─ notif-1: site_msg (DB insert + WS)
  @Async 线程池 ──────────┼─ notif-2: app (WS推送)
                           ├─ notif-3: email (SMTP, 1~3秒)
                           └─ saveLog (DB insert)
```

- **业务主流程零阻塞**：`send()` 只是把任务提交到线程池，立即返回
- **邮件 SMTP 耗时不影响交易**：即使 SMTP 耗时 3 秒，交易线程毫无感知
- **各渠道独立执行**：一个渠道失败不影响其他渠道

##### 5.13.14.2 线程池配置

| 参数 | 值 | 说明 |
|---|---|---|
| corePoolSize | 2 | 核心线程数，保持 2 个常驻线程 |
| maxPoolSize | 5 | 最大线程数，突发时扩展到 5 个 |
| queueCapacity | 100 | 等待队列，最多缓存 100 个通知任务 |
| threadNamePrefix | `notif-` | 线程名前缀，便于日志定位 |
| rejectedExecutionHandler | CallerRunsPolicy | 队列满时回退到调用线程执行（保底策略，不丢消息） |

##### 5.13.14.3 改造说明

`NotificationRouter.send()` 方法添加 `@Async("notificationExecutor")` 注解，由 Spring AOP 自动将方法调用委派到异步线程池：

```java
@Async("notificationExecutor")
public void send(NotificationMessage message, List<String> channels) {
    // 原逻辑不变，自动在通知线程池中执行
}
```

```text
    │                                │   各线程独立：一个失败不影响其他                             │
    │                                │   全部执行完后各自记录 NotificationLog                       │
    │                                                                                           │
    │                                                                                           │
    │  跨应用推送（如 ai-task → Redis PUBLISH）同样不阻塞                                    │
    │────► SignalMessagePublisher.push()                                                         │
    │       └─ Redis PUBLISH signal:push (微秒级，不阻塞)                                        │
    │          └─ ai-quant SignalRedisSubscriber                                                │
    │             └─ 同样是 @Async 异步处理 ──────────────► STOMP /topic/signals ────►│ 信号面板 │
```

##### 5.13.16.4 实现现状分析

**基础设施（✅ 已完成）：**
- `NotificationRouter` 路由中心：支持多渠道分发 + 用户配置过滤 + 日志记录
- **所有通知发送已异步化**：`NotificationRouter.send()` 使用 `@Async("notificationExecutor")` 线程池，业务主流程零阻塞
- `Notifier` 实现：`SiteMsgNotifier`（站内信）、`AppNotifier`（App推送）、`EmailNotifierAdapter`（邮件）、`SmsNotifier`（预留）
- `NotificationMessage` 统一消息体：支持 type/severity/symbol/metadata
- `NotificationEventListener` Spring 事件监听器
- 前端配置页：通知类型多选 + 各渠道开关
- 跨应用信号推送：`SignalMessagePublisher` → Redis → ai-quant → STOMP

**关键缺口（❌ 待实现）：**
- **没有任何业务代码调用通知** — `NotificationEvent` 和 `notificationRouter.send()` 在整个项目中无调用方
- `ai-order` 模块无 `ai-quant` 依赖，无法直接调用 `NotificationRouter`
- 需要通过 **跨模块通知机制** 实现（可选方案见下文）

##### 5.13.16.5 跨模块通知方案

由于 `ai-order` 和 `ai-task` 是独立模块，不依赖 `ai-quant` 的 `NotificationRouter`，需要跨模块通知机制：

**方案 A：Redis Pub/Sub 扩展（推荐 ✅）**

在已有的 `signal:push` 频道基础上，新增 `notification:push` 频道，复用现有的 Redis → STOMP 转发架构：

```text
ai-order / ai-task                            ai-quant                         前端
    │                                            │                              │
    │ Redis PUBLISH "notification:push"           │                              │
    │────────────────────────────────────────►   │                              │
    │                                            │                              │
    │                                     NotificationRedisSubscriber           │
    │                                       ├─ 反序列化为 NotificationMessage  │
    │                                       └─ notificationRouter.send(msg)    │
    │                                            │                              │
    │                                            ├─ site_msg ────────────────► 站内信
    │                                            ├─ app ─────────────────────► 实时弹窗
    │                                            └─ email ──────────────────► 邮件
```

优点：
- 复用现有 Redis Pub/Sub 架构，零新增中间件
- `ai-order`/`ai-task` 只需依赖 `ai-common` 即可发布
- 与现有 `signal:push` 架构一致，维护成本低

**方案 B：Spring 事件 + 消息队列**

通过 RocketMQ/RabbitMQ 异步解耦，`ai-order` 发送 MQ 消息，`ai-quant` 消费后调用 `NotificationRouter`

优点：
- 高可靠，支持事务消息
- 适合跨机房/跨集群部署

缺点：
- 引入新中间件，架构复杂度高
- 小团队运维成本高

##### 5.13.16.6 推荐优先实现的通知点

按业务价值排序：

| 优先级 | 编号 | 场景 | 理由 |
|---|---|---|---|
| P0 | T6 | 止损触发 | 风控核心，用户最关心 |
| P0 | T7 | 止损执行失败 | 需要立即人工干预 |
| P1 | T1 | 开仓成功 | 基础交易通知 |
| P1 | T3 | 全平平仓成功 | 基础交易通知 |
| P1 | T5 | 止盈触发 | 盈利确认 |
| P2 | T2 | 开仓失败 | 需要关注但非紧急 |
| P2 | T4 | 部分平仓 | 常见操作 |
| P3 | T10-T13 | 系统/策略通知 | 锦上添花 |
