量化交易资金管理系统设计文档
1. 引言
   1.1 背景
   在量化交易系统中，资金（余额）管理是核心基础组件，直接影响交易决策的正确性与风险控制。传统的单一数据源模式存在明显缺陷：

仅依赖交易所查询：受限于 API 频率、网络延迟，无法反映交易过程中的冻结资金，且可能因限频导致数据不可用。

仅依赖本地账本：可能因程序崩溃、网络中断、外部操作（手动转账、资金费、充值提现）导致与实际余额不符，引发超买超卖风险。

1.2 目标
设计一个可靠、实时、一致、可扩展的资金管理系统，满足以下要求：

支持多交易所、多账户的统一管理；

为策略提供低延迟的本地余额查询；

自动捕获并处理交易所余额变化（包括外部操作）；

定期校准，保证本地账本与交易所实际余额最终一致；

具备风控、监控、审计等能力，确保系统安全稳健运行。

1.3 当前状态说明
账户服务：已完成大部分功能，但需集成密钥加密存储等安全增强，并调整部分字段。

交易服务：已存在，但需调整以适配新的资金服务接口。

风控服务：已存在，下单前会调用资金服务检查余额。

策略服务：已存在，通过交易服务下单。

资金服务：（需开发） 核心待开发模块。

对账服务：（需开发） 负责实时和日终对账。

消息队列：暂不开发，所有异步操作改为同步或数据库直接写入。

3.1.3 密钥加密存储本地实现（暂不引入KMS）
由于生产环境初期可能不引入独立的密钥管理服务（KMS），采用本地加密存储方案，但必须遵循严格的安全措施。

3.1.3.1 加密算法与流程
算法：AES-256-GCM（提供加密与完整性认证）。

密钥长度：256 位（32 字节）。

初始化向量（IV）：12 字节，每次加密随机生成。

输出格式：IV + 密文 整体进行 Base64 编码，存入数据库对应字段（如 api_secret_enc）。

解密：Base64 解码后提取 IV，使用相同密钥解密。

3.1.3.2 加密密钥管理
密钥来源：通过环境变量 API_ENCRYPTION_KEY 提供 Base64 编码的 32 字节密钥。例如：

bash
export API_ENCRYPTION_KEY="4vK3xP9...（Base64 编码的 32 字节密钥）"
密钥生成：使用 OpenSSL 生成随机 32 字节并 Base64 编码：

bash
openssl rand -base64 32
密钥保护：

环境变量仅限服务启动用户可读，禁止硬编码在代码或配置文件中。

若使用配置文件，需设置权限 600，仅运行用户可读。

严禁将密钥提交到版本控制系统。

3.1.3.3 运行时解密与缓存
为避免每次交易所请求都解密（影响性能），采用内存缓存策略：

缓存框架：使用 Caffeine 或 Guava Cache，设置过期时间（如 1 小时）和最大条目数。

缓存内容：AccountSecrets 对象，包含 char[] 类型的 apiKey、apiSecret、passphrase（使用 char[] 而非 String，便于用后覆盖）。

加载函数：从数据库读取密文，调用解密工具得到明文，存入缓存。

启动预热：服务启动时加载所有启用账户的密钥到缓存，避免首次请求延迟。

内存安全：使用 char[] 存储敏感信息，用后通过 Arrays.fill() 覆盖；避免将明文打印到日志。

示例代码片段：

java
// 解密工具类
public class AesGcmEncryptor {
public String encrypt(String plainText, byte[] key) throws Exception { ... }
public String decrypt(String encryptedData, byte[] key) throws Exception { ... }
}

// 缓存加载
LoadingCache<Long, AccountSecrets> secretsCache = Caffeine.newBuilder()
.expireAfterWrite(1, TimeUnit.HOURS)
.maximumSize(1000)
.build(accountId -> {
TradingAccount account = accountMapper.selectById(accountId);
byte[] key = Base64.getDecoder().decode(System.getenv("API_ENCRYPTION_KEY"));
AesGcmEncryptor encryptor = new AesGcmEncryptor(key);
String apiKeyPlain = encryptor.decrypt(account.getApiKeyEnc());
String apiSecretPlain = encryptor.decrypt(account.getApiSecretEnc());
String passphrasePlain = account.getPassphraseEnc() == null ? null : encryptor.decrypt(account.getPassphraseEnc());
AccountSecrets secrets = new AccountSecrets();
secrets.setApiKey(apiKeyPlain.toCharArray());
secrets.setApiSecret(apiSecretPlain.toCharArray());
secrets.setPassphrase(passphrasePlain != null ? passphrasePlain.toCharArray() : null);
// 清除临时字符串引用
apiKeyPlain = null; apiSecretPlain = null; passphrasePlain = null;
return secrets;
});
3.1.3.4 密钥轮换
定期更换加密密钥（如每 3 个月）。

编写离线脚本：使用旧密钥解密所有密文，再用新密钥加密并更新数据库。

密钥更换期间，服务需重启或重新加载缓存。

3.1.3.5 与资金服务交互
资金服务或交易所适配层通过账户ID从缓存获取 AccountSecrets，取出 char[] 构造签名。

禁止将明文密钥通过网络传输，仅在内存中使用。

3.1.4 审计日志
记录所有密钥解密操作（账户ID、时间、调用方），便于异常追踪。

3.2 资金服务（需开发）
资金服务是整个系统的核心，采用“本地钱包 + 交易所权威数据”的双账本机制。

3.2.1 本地钱包
每个交易所账户的每个币种在 Redis 中维护一个余额副本，包含：

total：交易所端总余额（由定时同步或 WebSocket 更新）。

frozen：本地冻结余额（已下单未成交部分占用的资金）。

available：本地可用余额（available = total - frozen）。

提供线程安全的操作接口（RPC 或 HTTP）：

freeze(account_id, asset, amount)：下单前冻结，更新 available 和 frozen。

unfreeze(account_id, asset, amount)：订单取消/失败时解冻。

apply_trade(account_id, asset, cost, fee)：成交后实际扣款，调整 frozen 和 total。

sync_from_exchange(account_id, asset, new_total)：用交易所全量数据更新 total，重新计算 available。

apply_websocket_update(account_id, asset, new_total)：根据 WebSocket 推送更新 total，重新计算 available。

get_available(account_id, asset)：查询可用余额（供风控和交易服务调用）。

3.2.2 实时更新（WebSocket）
每个交易所账户建立一条 WebSocket 连接，订阅账户更新频道（如 Binance 的 outboundAccountPosition）。

收到推送后，解析余额变化，调用 apply_websocket_update 更新 Redis 中的实时余额，并同步写入 MySQL 资金流水表。

处理乱序问题：推送消息携带时间戳或序列号，本地仅当新消息的序列号大于当前记录时才更新，否则丢弃。

3.2.3 定时全量同步
每 5 分钟（可配置）调用交易所 REST API 拉取全量余额。

对每个币种，调用 sync_from_exchange 更新本地钱包。

若发现差异超过阈值（如 0.001 USDT），触发告警并自动纠正，同时记录对账日志。

3.2.4 资金流水
所有资金变动（交易、资金费、划转、手续费等）记录流水日志，存储于 MySQL。

字段包括：账户ID、币种、变动类型、变动金额、变动前后余额、关联ID（如订单ID）、时间戳。

用于审计、对账及异常溯源。由于无消息队列，流水写入采用同步事务或批量插入。

3.3 交易服务（已有，需适配）
订单管理：接收策略下单请求，调用风控服务进行前置检查，然后调用资金服务的 freeze 冻结资金，再通过交易所适配器发送订单。

状态同步：通过 WebSocket 或轮询监听订单状态变更，当订单成交时，调用资金服务的 apply_trade 更新余额；当订单取消/失败时，调用 unfreeze。

幂等控制：使用全局唯一 ID（如 UUID）防止重复下单。

错误处理：订单发送失败时及时调用 unfreeze 释放冻结资金。

3.4 风控服务（已有）
前置风控：下单前调用资金服务的 get_available 获取可用余额，检查是否足够，同时检查持仓、杠杆率等。

动态限频：统一管理交易所 API 调用频次，防止触发限频导致封禁。

熔断机制：当某个交易所连续报错或网络异常时，自动暂停相关交易，待恢复后手动或自动重启。

3.5 对账服务（需开发）
日终对账：每天拉取交易所历史成交和账单，与本地流水逐笔核对，生成差异报告。

实时对账：结合 WebSocket 推送和定时查询，对实时余额进行一致性校验，发现偏差及时告警。

补偿机制：当发现本地与交易所余额不一致时，锁定该账户的交易，进行对账修复，修复后重新启用。修复过程可借助资金流水回溯。

3.6 交易所适配层（已有框架，需扩展）
统一接口：定义标准接口（查询余额、下单、撤单、获取订单状态、订阅 WebSocket 等），每个交易所实现具体适配器。

协议转换：处理交易所特有的签名、参数格式、错误码。

连接池与重试：管理 HTTP 连接，实现可配置的重试策略和退避算法。

为资金服务提供：余额查询接口和 WebSocket 订阅接口。

   每个交易所账户建立独立的 WebSocket 连接，订阅账户更新频道。

收到推送后，解析余额变动，更新 Redis 中的实时余额，并同步写入 MySQL 流水表（无消息队列，直接写库）。

处理乱序：推送消息携带时间戳或递增序列号，本地仅当新消息的序列号大于当前记录时才更新，否则丢弃。

5.2 定时全量同步（资金服务实现）
每 5 分钟（可配置）调用 REST API 拉取账户余额，与 Redis 中的本地钱包对比。

对比逻辑：|(local.total - exchange.total)| > threshold 触发告警。

若差异超过阈值，记录异常日志，并根据配置自动修复（用交易所数据覆盖 local.total，重新计算 available）。

同步间隔可根据交易所限频调整，避免超限。

5.3 操作时的余额检查（交易服务调用资金服务）
下单前，交易服务调用资金服务的 get_available 接口（从 Redis 读取），进行快速风控。

如果本地余额不足，直接拒绝下单；如果足够，则先调用 freeze 冻结资金，然后发送订单。

订单状态变更（成交、取消）时，通过回调调用资金服务的 apply_trade 或 unfreeze 更新余额。

5.4 补偿机制（对账服务实现）
当定时同步发现余额偏差且自动修复失败，或对账服务检测到异常时，立即锁定该账户的交易，停止接受新订单。

触发详细的对账流程：拉取交易所历史流水，与本地流水逐条比对，找出差异原因。

修复后手动或自动解锁账户。

5.5 防重复与幂等
所有资金变动操作（如冻结、解冻、成交）均使用唯一流水号（可由调用方生成），确保幂等性。资金服务需检查流水号是否已处理。

6. 扩展性与高可用
   6.1 新增交易所
   只需实现新的适配器类，实现标准接口（查询余额、下单、撤单、WebSocket 订阅等）。

交易所配置（如域名、限频、WebSocket 地址）放在配置中心，动态加载。

6.2 水平扩展
业务服务层（交易、风控、资金）均为无状态服务，可多实例部署，通过负载均衡分发请求。

Redis 和 MySQL 做集群（主从、分片），避免单点故障。

WebSocket 连接分布在多个实例上，可通过网关统一管理或使用 Redis Pub/Sub 广播状态更新（资金服务需支持分布式锁保证冻结操作原子性）。

6.3 异步处理（无消息队列方案）
由于暂不开发消息队列，所有原本异步的操作（如流水写入）改为同步执行。为降低延迟，可考虑批量写入或使用本地内存队列+定时刷盘。

资金服务的 apply_trade 等操作需保证数据库和 Redis 的一致性，可使用本地事务或分布式事务方案（如 TCC），但简单场景下可接受最终一致性，通过定时同步修复。

7. 安全性设计
   密钥加密存储：API 密钥在数据库中加密（AES-256-GCM），加密密钥通过环境变量配置，运行时解密并缓存于内存（详见 3.1.3 节）。所有敏感信息使用 char[] 存储，用后立即覆盖，禁止打印日志。

IP 白名单：限制交易所 API 调用的服务器 IP，避免密钥泄露后被盗用。

操作审计：记录所有敏感操作（如修改账户、划转资金、密钥解密）的日志，包括操作人、时间、IP。

风控隔离：不同账户之间资金隔离，防止单个账户风险扩散影响全局。

8. 监控与告警
   余额偏离告警：定时对账或实时同步发现本地与交易所余额差异超过阈值时触发邮件、钉钉或短信通知。由对账服务和资金服务实现。

API 异常告警：调用交易所接口失败率上升、超时等异常。由适配层和交易服务实现。

WebSocket 断线重连：连接断开后自动重连，并补发期间数据（通过拉取全量余额恢复）。由资金服务实现。

资金流水异常：单笔流水金额过大、频繁资金变动等触发人工审核。由监控系统实现。

系统资源监控：CPU、内存、网络、数据库连接数等。

9. 开发计划概要
   账户服务修改（需开发）：

实现 API 密钥加密存储（AES-256-GCM），采用本地加密方案（环境变量管理密钥）。

移除 balances 和 allocations 字段，或将其废弃。

提供解密接口（或缓存机制）供资金服务使用。

资金服务（核心开发）：

实现本地钱包（Redis）及操作接口。

实现 WebSocket 订阅、推送处理、流水写入。

实现定时全量同步任务。

提供 RPC/HTTP API 供交易服务调用。

对账服务（并行开发）：

实现日终对账脚本，拉取交易所账单对比本地流水。

实现实时对账模块，监听资金流水，与交易所快照对比。

实现异常锁定与修复流程。

交易服务适配（需调整）：

修改下单流程，调用资金服务进行冻结和解冻。

订单成交后通知资金服务更新余额。

交易所适配层扩展（需开发）：

为每个交易所实现余额查询和 WebSocket 订阅接口。

10. 总结
    本设计方案以“本地钱包+交易所权威数据”的双账本机制为核心，明确了现有模块和待开发模块的边界。账户表需进行加密改造和字段精简，资金服务和对账服务是接下来开发的重点，其他服务需进行少量适配。通过分层架构和清晰的接口定义，系统能够实现多交易所资金账户的准确、实时管理，并为策略执行提供可靠的基础支撑。
