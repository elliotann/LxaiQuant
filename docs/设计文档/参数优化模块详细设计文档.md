参数优化模块详细设计文档（最终版）
版本：1.2
日期：2025-03-13
作者：交易系统开发团队

1. 引言
   1.1 背景
   当前量化交易系统已实现基于 ta4j 0.22.2 的双向持仓策略引擎，支持多批次加仓、方向性出场规则（止损、止盈、信号反转、分批止盈等），并已集成订单系统与内存仓位管理。为进一步提升策略表现，需要引入参数优化功能，通过自动化搜索寻找最优参数组合，以改善夏普比率、降低最大回撤等关键绩效指标。

1.2 目标
支持对双向策略中的数值参数（如指标周期、倍数等）进行网格搜索优化。

能够针对历史数据运行回测，计算并记录每组参数对应的性能指标。

支持多目标优化（如最大化夏普比率、最小化最大回撤），并提供灵活选择。

优化过程应可配置、可扩展，并能与现有策略引擎无缝集成。

结果可持久化，便于后续分析和应用。

2. 现有系统概述
   2.1 核心组件
   组件	描述
   MultiPositionStrategy	双向策略接口，提供 shouldEnterDirection、shouldExitSignal 等方法。
   SignalMultiDirectionStrategy	基于信号缓存的方向性策略实现，支持外部配置出场规则组合。
   MultiPositionBarSeriesManager	双向策略回测执行器，遍历K线并调用策略的入场/出场信号，生成 MultiPositionTradingRecord。
   MultiPositionTradingRecord	双向持仓记录，管理多头和空头的批次（PositionLot）。
   ExitType、DirectionalRule 等	方向性规则及退出类型枚举。
   DefaultDealStrategyTrade	策略执行框架实现，包含加仓、平仓、数据库持久化等逻辑。
   BacktestService	回测服务，已包含参数范围优化功能（runParameterRangeOptimization）。
   ParameterRangeOptimizationRequest	参数优化请求对象，定义参数范围、优化目标等。
   BacktestEngine	回测引擎，负责执行回测并计算绩效指标。
   2.2 现有参数优化能力
   已支持对连续数值参数（min、max、step）进行网格搜索。

支持设置最大组合数（maxCombinations）和返回最优个数（topK）。

支持多种优化目标：总收益率、最大回撤、胜率、收益/回撤比。

可动态构建信号缓存，支持基于信号服务的策略（如 BOLL_RSI）。

回测执行基于 BacktestEngine，可获取 PerformanceMetrics（总收益率、最大回撤、胜率、交易次数等）。

前端已实现参数范围输入、开始优化按钮、WebSocket 进度推送。

3. 参数优化需求
   3.1 待优化参数示例
   以某技术指标策略为例，可能包含以下参数：

period：指标计算周期（如移动平均周期），范围 10~50，步长 5。

multiplier：倍数（如布林带宽度），范围 1.5~3.0，步长 0.2。

maType：移动平均类型，枚举值（如 "SMA"、"EMA"、"WMA"）。

3.2 优化目标
主要目标：最大化夏普比率（SharpeRatioCriterion）。

次要目标：最小化最大回撤（MaximumDrawdownCriterion），或在夏普相近时优先选择回撤小的参数。

可扩展：支持用户自定义加权评分，例如：

text
score = weight_sharpe * sharpe - weight_drawdown * drawdown
权重可通过请求参数传入。

3.3 约束条件
同一策略的其他固定参数（如是否启用加仓、分批止盈等）保持不变。

回测数据范围统一（同一段历史K线）。

每次回测独立，结果互不影响。

成交模型、费用模型、基础交易数量等必须固定，以保证不同参数间的可比性。

绩效计算器：使用 ta4j 的分析标准计算指标，当前 PerformanceMetrics 需扩展以包含夏普比率。

5. 详细设计
   5.1 参数定义与范围
   参数通过配置类定义，支持连续数值范围与离散枚举值。现有 ParameterRange 类需扩展支持 values 字段。

java
public class ParameterRange {
private String name;          // 参数名，如 "period"
private BigDecimal min;        // 最小值（连续数值时使用）
private BigDecimal max;        // 最大值（连续数值时使用）
private BigDecimal step;       // 步长（连续数值时使用）
private List<BigDecimal> values; // 离散值列表（枚举或固定值）
}
当 values 不为空时，优先使用离散值列表；否则使用 min/max/step 生成等差序列。

支持整数、浮点数等类型，前端需根据实际类型进行渲染。

当前实现：前端仅支持数值型范围（min/max/step），自动忽略非数值参数。离散枚举参数暂未在前端界面中体现，仅在后端参数表配置中预留。文档标注此为后续扩展方向。

5.2 策略参数化
现有策略通过 BacktestRequest 的 parameterOverrides 传入参数覆盖。在优化循环中，每次构建 BacktestRequest 并设置 parameterOverrides 为当前参数组合，然后调用 createStrategyByType 创建策略实例。策略内部应使用这些覆盖值构建指标和规则。

5.3 回测执行器复用
使用现有的 BacktestEngine.runBacktest(strategy, series) 方法，返回包含 PerformanceMetrics 的结果。需扩展 PerformanceMetrics 以包含夏普比率、Calmar 比率等指标，可调用 ta4j 的 AnalysisCriterion 计算。

java
// 在 BacktestEngine 中添加方法
public SharpeRatioCriterion sharpeCriterion = new SharpeRatioCriterion();
Num sharpe = sharpeCriterion.calculate(series, tradingRecord);
metrics.setSharpeRatio(sharpe.doubleValue());
5.4 绩效计算与多目标评分
现有 calculateOptimizationScore 基于单一目标硬编码。需改为支持权重组合，从请求中读取 objective 配置。

java
public class OptimizationObjective {
private String type; // "weighted" 或 "single"
private Map<String, Double> weights; // 当 type="weighted" 时使用
private String target; // 当 type="single" 时使用，如 "SHARPE_RATIO"
}
指标符号约定：

total_return：总收益率，正数表示盈利，负数表示亏损。

max_drawdown：最大回撤，统一表示为正值（例如 0.15 表示 15% 的回撤）。前端显示时如需加负号，由前端处理。

sharpe_ratio：夏普比率，正数表示优于无风险收益，数值越大越好。

win_rate：胜率，0~1 之间的小数，可转换为百分比显示。

优化目标枚举（前后端保持一致）：

"SHARPE_RATIO"：夏普比率

"TOTAL_RETURN"：总收益率

"MAX_DRAWDOWN"：最大回撤（优化时取负值）

"WIN_RATE"：胜率

"RETURN_OVER_MAX_DRAWDOWN"：收益/回撤比

当前前端将 "sharpe" 映射为 "RETURN_OVER_MAX_DRAWDOWN"，需统一调整为 "SHARPE_RATIO"。文档建议后续版本对齐。

5.5 优化算法
现有实现采用递归深度优先遍历所有参数组合，并通过 maxCombinations 限制总数。可保持此方式，后续可扩展随机采样。

并行与采样复现：

增加任务级配置 parallelism（并行度），控制 ForkJoinPool 的并行线程数。

若启用随机采样，增加 seed 字段，确保结果可复现。

json
"samplingConfig": {
"enabled": true,
"sampleSize": 500,
"seed": 42
}
5.6 样本外验证（可选）
支持在请求中提供 testRange（开始时间、结束时间）。优化时，先在整个数据集上训练（优化），然后计算测试区间上的指标，返回两个区间的结果。现有接口未支持，需扩展 ParameterRangeOptimizationRequest。

5.7 结果记录与持久化
现有优化结果直接返回内存，未持久化。建议新增 optimization_task 和 optimization_result 表，将任务和结果存入数据库。

表结构建议：

sql
CREATE TABLE optimization_task (
id BIGINT AUTO_INCREMENT PRIMARY KEY,
task_id VARCHAR(50) NOT NULL,
strategy_id VARCHAR(50),
coin_id VARCHAR(20),
start_time BIGINT,
end_time BIGINT,
param_ranges JSON,
objective JSON,
config JSON,                     -- 包含执行配置（杠杆、费率、并行度、采样配置等）
engine_version VARCHAR(20),       -- 引擎版本（如 "1.2"）
strategy_version VARCHAR(20),     -- 策略版本
num_type VARCHAR(20),             -- 数值类型：DOUBLE/DECIMAL
execution_model VARCHAR(20),       -- 成交模型：NEXT_OPEN / MARKET
fee_model VARCHAR(20),             -- 费用模型：ZERO / FIXED_RATE
status VARCHAR(20),
progress INT,
total_combinations INT,
created_at DATETIME,
updated_at DATETIME
);

CREATE TABLE optimization_result (
id BIGINT AUTO_INCREMENT PRIMARY KEY,
task_id VARCHAR(50) NOT NULL,
param_values JSON,
total_return DECIMAL(10,4),
max_drawdown DECIMAL(10,4),
win_rate DECIMAL(10,4),
sharpe_ratio DECIMAL(10,4),
score DECIMAL(10,4),              -- 综合评分，用于排序
created_at DATETIME,
INDEX idx_task_id (task_id)
);
结果排序与 Top-K：结果按 score 降序排列，取前 topK 条返回。

5.8 异步任务与进度推送
现有接口同步执行，对于大量组合可能超时。需改造为异步任务，并通过 WebSocket 推送进度。

任务流程：

客户端 POST /api/optimization/task 创建任务，返回 taskId。

服务端异步执行优化，更新任务状态。

服务端通过 WebSocket 向 ws://{host}/ws/backtest/{taskId} 推送进度事件。

客户端通过 WebSocket 接收进度，实时更新界面。

任务完成后，客户端可通过 GET /api/optimization/task/{taskId}/results 获取结果。

WebSocket 推送事件结构：

json
{
"type": "progress",           // 事件类型：progress / completed / error
"taskId": "opt_20250313_001",
"data": {
"progress": 45,            // 百分比 0-100
"status": "RUNNING",       // PENDING / RUNNING / COMPLETED / FAILED
"executed": 450,           // 已执行组合数
"total": 1000,             // 总组合数
"eta": 120,                // 预计剩余秒数
"message": "已执行 450/1000 个组合"  // 描述信息
}
}
当前实现：前端已建立 WebSocket 连接，路径为 ws://{host}/ws/backtest/{taskId}，需后端实现推送。文档补充约定。

8. 测试与验证
   单元测试：验证参数生成逻辑、多目标评分计算、结果排序、WebSocket 推送。

集成测试：使用小数据量和少量参数组合，确保异步任务、数据库持久化正常。

性能测试：评估大规模组合下的执行时间和资源消耗，验证并行度和采样配置。

前端联调：验证 WebSocket 进度推送、结果排序、指标显示。

9. 风险与注意事项
   风险	应对措施
   过拟合	可选样本外验证，或在优化目标中加入验证集指标权重。
   计算资源耗尽	设置最大组合数限制，支持随机采样；控制并行度。
   参数范围定义不全	前端支持离散枚举输入，后端兼容现有 min/max/step。
   指标一致性	统一指标符号（如回撤为正），前后端约定一致。
   数据库性能	优化结果表对 task_id 加索引，JSON 字段避免频繁查询。
   接口兼容性	当前 /backtest/parameter-range-optimization 接口保留，逐步迁移至 /api/optimization/task，并确保 WebSocket 路径一致。
   枚举参数前端实现	当前前端未实现离散枚举输入，计划在后续版本增加，文档标注为扩展方向。
10. 总结
    本设计在现有 BacktestService 的参数优化功能基础上，扩展了离散参数支持、多目标加权评分、异步任务和结果持久化，使参数优化模块更完整、可扩展。通过复用现有回测引擎和策略工厂，实现与系统的无缝集成。同时补充了 WebSocket 进度推送、指标符号约定、任务元数据等细节，确保前后端一致。后续可根据需求增加贝叶斯优化等高级算法。
