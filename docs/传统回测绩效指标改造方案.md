# 传统回测绩效指标改造方案

---

## 前置：问题分析

### 一、问题现象

在 MarketKlineV1.vue 中运行**传统回测**后，绩效概览（Performance Overview）部分指标数据显示不正确，部分字段始终显示为 `0` 或 `0.00%`。

---

### 二、数据流全景

#### 2.1 前端调用流程

```
MarketKlineV1.vue runBacktest()
  → runAsyncBacktest(request)            # POST /api/backtest/async/create
  → 轮询 getBacktestTaskStatus()         # GET /api/backtest/task/{taskId}
  → getAsyncBacktestResult()             # GET /api/backtest/async/result/{taskId}
    → normalizeBacktestResult()           # 数据归一化
    → backtestResults.value = normalized  # 渲染到 BacktestRunPanel
```

**传统回测与快速回测的前端调用流程完全一致**，后端执行路径不同。

#### 2.2 后端执行路径

| 阶段 | 快速回测 | 传统回测 |
|------|---------|---------|
| 执行 | `BacktestService.runEnhancedBacktest()` → `BacktestEngine.runBacktest()` | `runTraditionalBacktestWithDataCapture()` → 执行策略+重建交易记录 |
| 指标计算 | `BacktestEngine.calculateMetrics()` 使用 ta4j Criteria | `calculateTraditionalMetrics()` 手动计算 |
| 保存 | `BacktestResultSaveService.saveBacktestResult()` | 同左 |
| 查询 | `BacktestController.getAsyncBacktestResult()` | 同左 |

```

**第 3 层丢失 - API 返回时**

```

---

#### ★ 问题 2（中等）：夏普比率使用简化公式

`PerformanceMetricsConverter.getSharpeRatio()`:

```java
double sharpeRatio = totalReturn / maxDrawdown;
```

这是**严重简化**的计算。正确的夏普比率 = (年化收益 - 无风险利率) / 年化波动率标准差。

ta4j 的 `BacktestEngine.calculateMetrics()` 用 `SharpeRatioCriterion` 计算了正确的夏普比率，但该值在第 1 层丢失，最终 DB 中存储的是简化公式的结果。

---

#### ★ 问题 3（中等）：传统回测缺少高级指标计算

`calculateTraditionalMetrics()` 只计算了 8 个基础字段，没有实现以下计算逻辑：

| 缺失指标 | 可能计算方式 |
|---------|------------|
| 年化收益率 | (1 + totalReturn)^(365 / 回测天数) - 1 |
| 波动率 | 持仓收益率的年化标准差 |
| 索提诺比率 | (年化收益 - 无风险利率) / 下行标准差 |
| 平均盈利 | 总盈利 / 盈利交易次数 |
| 平均亏损 | 总亏损 / 亏损交易次数 |
| 最大连续盈利 | 遍历交易记录，统计最大连续盈利次数 |
| 最大连续亏损 | 遍历交易记录，统计最大连续亏损次数 |
| 平均持仓时间 | 所有持仓时长的平均值 |

---

#### ★ 问题 4（低）：传统回测与快速回测 totalReturn 计算方式不同

| 回测类型 | totalReturn 计算 | 来源 |
|---------|----------------|------|
| 快速回测 | `GrossReturnCriterion.getValue()` | ta4j 标准计算 |
| 传统回测 | `totalPnl / initialAmount` | 手工计算 |

两者在手续费、滑点、未实现盈亏的处理方式不同，结果可能存在差异。

---

### 四、影响总结

| 问题 | 影响类型 | 影响字段数 | 严重度 |
|:----|:-------|:--------:|:-----:|
| 问题1：API 字段缺失 | 传统 + 快速 | **8 个**始终为 0 | **严重** |

**建议优先修复问题 1 和 3**，补齐字段通路和计算逻辑。

## 一、改造背景

传统回测走的是**模拟实盘**模式，与快速回测的 ta4j 引擎模式有本质区别：

| 维度 | 快速回测（ta4j 引擎） | 传统回测（模拟实盘） |
|:----|:-------------------|:------------------|
| 执行方式 | ta4j 在 BarSeries 上模拟交易 | 真实策略写入订单 DB，再回读 |
| 数据来源 | `TradingRecord`（内存） | `OrderVO`（DB）+ `TradeRecord`（重建） |
| 回撤计算 | `BacktestEngine.calculateEquityCurveAndDrawdown()` | 同左（复用同一方法） |
| 指标计算 | `BacktestEngine.calculateMetrics()` 用 ta4j Criteria | `calculateTraditionalMetrics()` 手工计算 |
| 数据完备性 | 缺少订单明细字段 | 有 charge/returnRate/closeReason 等 |

当前问题的核心是：**两种模式下计算结果口径应该一致，但目前传统回测的指标计算过于简陋，且数据模型层不支持完整字段**。

---

## 二、改造目标

1. **传统回测和快速回测产出相同的绩效指标结构**（16 个字段保持一致）
2. **传统回测各指标计算逻辑正确**，充分利用模拟实盘的数据优势
3. **数据模型层扩展**，支持全部 16 个字段的存储和传输
4. **代码可复用**，传统回测和快速回测共享指标计算核心逻辑

## 四、传统回测指标计算改造

### 4.1 总体架构

将 `calculateTraditionalMetrics()` 从 `BacktestController` 中**提取为独立 Service**，与快速回测共享计算逻辑：

```
                          ┌──────────────────────────────┐
                          │   MetricsCalculationService   │
                          │   (共享指标计算服务)          │
                          └──────────┬───────────────────┘
                                     │
              ┌──────────────────────┼──────────────────────┐
              ▼                      ▼                      ▼
  ┌─────────────────────┐  ┌──────────────────┐  ┌──────────────────┐
  │ calculateQuick()    │  │ calculateByTR()  │  │ calculateByTR()  │
  │ (ta4j TradingRecord)│  │ (ta4j TradingRecord│  │ (ta4j TradingRecord│
  │ 已存在，需扩展)     │  │ 重建自订单DB)    │  │ 来自ta4j引擎)    │
  └─────────────────────┘  └──────────────────┘  └──────────────────┘
                                     │
                                     ▼
                          ┌──────────────────────────────┐
                          │    计算所有 16 个指标          │
                          │    (统一公式，统一口径)        │
                          └──────────────────────────────┘
```

**关键设计**：传统回测和快速回测最终调用的都是同一个 `MetricsCalculationService.calculateByTradingRecord()` 方法，传入的是同一个类型的 `TradingRecord` 参数，保证了指标口径一致。

### 4.2 传统回测的执行链路改造

改造后链路：

```
runTraditionalBacktestWithDataCapture()
  → strategy.execStrategy(params)         # 执行策略，订单写入 DB
  → reconstructTradeRecordsFromOrders()   # 从 DB 重建 TradeRecord 列表
  → buildTradingRecordFromTradeRecords()  # ★ 新增：将 TradeRecord 重建为 ta4j TradingRecord
  → calculateEquityAndDrawdown()          # 沿用：计算权益曲线和回撤
  → MetricsCalculationService.calculateByTradingRecord(series, tradingRecord, config)
                                           # ★ 改造：走共享计算服务
  → 得到完整 16 个指标                      # ★ 改造：一次性得到所有指标
```

`buildTradingRecordFromTradeRecords()` 方法将订单重建的 `TradeRecord` 列表转换为 ta4j 的 `TradingRecord`（即 `BaseTradingRecord`），然后传给共享计算服务。**这个转换逻辑在 `calculateEquityAndDrawdown()` 中已经存在**，只需提取为独立方法即可复用。

### 4.3 各指标计算公式

以下公式对传统回测和快速回测**统一适用**：

#### 基础指标

| 指标 | 公式 | 说明 |
|:----|:----|:-----|
| totalReturn | `finalValue / initialAmount - 1` | 总收益率 |
| annualReturn | `(1 + totalReturn)^(365 / days) - 1` | 年化收益率，days = 回测天数 |
| volatility | `std(dailyReturns) * sqrt(365)` | 每日收益率的年化标准差 |
| finalValue | `initialAmount * (1 + totalReturn)` | 最终价值 |

#### 风险指标

| 指标 | 公式 | 说明 |
|:----|:----|:-----|
| maxDrawdown | `max(peak - trough) / peak` | 从回撤序列中取最大值 |
| sharpeRatio | `(annualReturn - riskFreeRate) / volatility` | 标准夏普比率，riskFreeRate 取 0.02~0.03 |
| sortinoRatio | `(annualReturn - riskFreeRate) / downsideDeviation` | 索提诺比率，只考虑下行波动 |
| calmarRatio | `annualReturn / maxDrawdown` | 卡玛比率 = 年化收益 / 最大回撤 |

#### 交易指标

| 指标 | 公式 | 说明 |
|:----|:----|:-----|
| totalTrades | 已平仓交易数 | 过滤 pnl ≠ 0 的记录 |
| winRate | `winningTrades / totalTrades` | 胜率 |
| profitFactor | `sumWinning / abs(sumLosing)` | 盈利因子 = 总盈利 / 总亏损 |
| averageWin | `sumWinning / winningTrades` | 平均盈利额 |
| averageLoss | `abs(sumLosing) / losingTrades` | 平均亏损额 |
| maxConsecutiveWins | 遍历交易序列，统计连续盈利最多次数 | 按顺序遍历 |
| maxConsecutiveLosses | 遍历交易序列，统计连续亏损最多次数 | 按顺序遍历 |
| avgTradeDuration | `avg(exitTime - entryTime)` | 平均持仓时间（天） |

### 4.4 传统回测特有计算逻辑说明

由于传统回测的 `TradeRecord` 来自订单 DB，数据更丰富，需要注意以下差异：

**1. PnL 方向判断**

```java
// 传统回测的 TradeRecord 中 pnl 字段含义：
// 正数 = 盈利，负数 = 亏损（和快速回测一致）
// ⚠️ 注意：传统回测的 TradeRecord 是 OrderVO 转换而来，
//   order.getIncome() 可能为 null，需处理
```

**2. 收益率计算口径**

```java
// 传统回测 totalReturn 计算：
//   totalPnl / initialAmount
// 这与快速回测 GrossReturnCriterion (finalValue/initialAmount - 1) 等价
// ✅ 改造后统一走 ta4j GrossReturnCriterion 或等价公式
```

**3. 手续费处理**

```java
// 传统回测的 TradeRecord.charge 来自 order.getCharge()
// 但订单 DB 中 charge 可能不完整
// 建议改造为：从 TradingRecord 的交易成本模型中统一计算
```

### 4.5 权益曲线和回撤序列

传统回测已复用 `BacktestEngine.calculateEquityCurveAndDrawdown()`，该逻辑不需要改动。唯一需要注意的是：

```java
// 传统回测中传入的 TradingRecord 是用订单 DB 重建的，
// 需要确保 Position 的 entry/exit 正确配对。
// 当前 reconstructTradeRecordsFromOrders() 是逐条构建的，
// 在 buildTradingRecordFromTradeRecords() 中应保证：
//   1. 按时间排序
//   2. LONG 方向：BUY=enter, SELL=exit
//   3. SHORT 方向：SELL=enter, BUY=exit
// 这个逻辑在 calculateEquityAndDrawdown() 中已经实现了，只需提取
```

### 4.6 通过 DB 订单重建权益曲线的风险与对策

传统回测通过订单 DB 重建 `TradingRecord` 再计算权益曲线和最大回撤，数据质量高度依赖订单 DB 的完整性。以下 5 个风险点需要针对性地处理：

---

#### ★ 风险 1（严重）：未平仓持仓丢失 → 最终权益错误

**问题描述**：

传统回测执行完策略后，订单 DB 中可能只记录了**完整平仓**的订单（有 entry + exit），而回测结束时**仍持有未平仓部分**可能没有平仓记录。`reconstructTradeRecordsFromOrders()` 如果只遍历已平仓订单重建 `TradeRecord`，则未平仓持仓的市值被忽略，最终权益 `finalValue` 计算偏低，连带影响 `totalReturn`、`annualReturn`、`sharpeRatio` 等一系列指标。

```
示例：
  初始资金 100,000
  买入 10,000 市值股票，未平仓（当前市值 11,000）
  已平仓交易盈利 2,000
  
  正确 finalValue = 100,000 + 2,000 + (11,000 - 10,000) = 103,000
  丢失未平仓  = 100,000 + 2,000                       = 102,000 ❌
```

**解决方案**：

| 方案 | 做法 | 优缺点 |
|:----|:----|:------|
| **方案 A（推荐）** | 策略执行完毕后，强制平仓所有未平仓持仓（`closeAllPositions`），写入订单 DB | 保证 DB 中所有记录完整，重建逻辑简单，数据自洽；但会额外产生平仓订单 |
| 方案 B | 从订单 DB 中识别未平仓持仓（有 entry 无 exit），用最新 Bar 价格估算未实现盈亏，手动附加到 TradingRecord 中 | 无需额外平仓操作，重建逻辑复杂，需要处理价格对齐和持仓估值 |
| 方案 C | 在 `executeAfter()` 或策略回调中自动平仓，由策略框架保证无持仓遗留 | 对策略框架有要求，改动面较大 |

**实施建议**：采用**方案 A**，在 `runTraditionalBacktestWithDataCapture()` 的最后一步调用强制平仓。这是最稳健的做法，且对后续所有计算透明。

#### ★ 风险 2（中等）：权益曲线粒度不足 → 最大回撤低估

**问题描述**：

`calculateEquityAndDrawdown()` 基于 `TradingRecord` 的**平仓事件**计算权益点，即每笔交易平仓时才记录一个权益快照。若交易日少（如趋势跟踪策略整个回测区间只有 30 笔交易），则权益曲线只有 30 个采样点，粒度极粗。

两个交易之间的**日内浮亏**不会被捕获，导致最大回撤严重低估：

```
按日粒度实际权益曲线：
  100,000 → 98,000 → 95,000 → 97,000 → 102,000
  最大回撤 = (100,000 - 95,000) / 100,000 = 5%

按交易事件粒度曲线（只有平仓点）：
  100,000 → 102,000
  最大回撤 = 0% ❌（完全没捕获到中间波动）
```

**解决方案**：

| 方案 | 做法 | 优缺点 |
|:----|:----|:------|
| **方案 A（推荐）** | 权益曲线计算粒度提升到 **K 线级别**（每根 Bar 计算一次权益），持仓市值用对应 Bar 的价格估算，权益曲线 = 现金 + 持仓市值 | 粒度与 BarSeries 一致，回撤计算精确；计算量较大但可控 |
| 方案 B | 保留现有交易事件粒度 + 日内线性插值 | 实现简单，但仍然是估算，不能反映真实波动 |
| 方案 C | 回测执行阶段收集每个 K 线收盘时的快照数据 | 数据最准确，但需要改造策略执行引擎 |

**实施建议**：采用**方案 A**，改造 `calculateEquityAndDrawdown()` 使其按照 Bar 粒度扫描。遍历 `BarSeries` 中的每根 Bar，在每个 Bar 结束时：
1. 确定当前持仓状态（通过 TradingRecord 的 `getCurrentPosition()`）
2. 若已持仓，用当前 Bar 价格估算持仓市值
3. 权益 = 现金余额 + 持仓市值
4. 记录权益点 → 计算回撤

#### ★ 风险 3（中等）：时间戳对齐问题 → 持仓位置错误

**问题描述**：

订单 DB 的时间戳是**撮合时间/数据库时间**，而 `BarSeries` 的时间是 **K 线时间**。两者对齐可能存在偏差：

```
示例：
  订单撮合时间：2026-05-15 10:33:00
  对应 15min K 线范围：10:30 ~ 10:45
  如果错误地归到 10:15 ~ 10:30 这根 K 线
  → 持仓位置前置了一个 K 线
  → 盘口价格、权益曲线全部错位
```

时间戳错位的影响：
- 持仓开始/结束时间与市场价格不匹配
- 权益曲线的涨跌节点与实际持仓周期错位
- 年化计算中的天数偏差（影响 annualReturn/volatility）

**解决方案**：

| 方案 | 做法 | 优缺点 |
|:----|:----|:------|
| **方案 A（推荐）** | 统一以 Bar 的**开始时间**为基准进行对齐，订单时间戳 `floor` 到最近的 Bar 开始时间（`bar.getBeginTime()`） | 对齐规则明确，与交易引擎周期一致，实现简单 |
| 方案 B | 后端存储专用的 `barIndex` 字段记录订单所属的 K 线索引 | 存储冗余，但查询时 O(1) 定位，无需时间计算 |
| 方案 C | 采用 Bar 的结束时间作为对齐基准（`bar.getEndTime()`） | 适合收盘价成交策略，需要与策略引擎约定一致 |

**实施建议**：采用**方案 A**。关键约束是：**重建 TradingRecord 时，entry 和 exit 的 index 必须与 BarSeries 中的 Bar 严格对应**。时间戳对齐规则为：

```java
// 订单撮合时间 → Bar 索引的映射逻辑
int barIndex = series.getBarCount() - 1;
for (int i = 0; i < series.getBarCount(); i++) {
    Bar bar = series.getBar(i);
    // 订单时间在 [bar.getBeginTime(), bar.getEndTime()) 范围内 → 归属该 Bar
    if (timestamp >= bar.getBeginTime() && timestamp < bar.getEndTime()) {
        barIndex = i;
        break;
    }
}
// 将订单 entry/exit 的 index 设置为 barIndex
```

⚠️ 注意：传统回测和快速回测在 `buildTradingRecordFromTradeRecords()` 中应使用相同的时间戳对齐逻辑，确保口径一致。

#### ★ 风险 4（中低）：手续费/滑点缺失 → 回撤偏小

**问题描述**：

订单 DB 中的 `charge` 字段可能为 `0` 或不完整，取决于：
- 策略是否设置了手续费/滑点参数
- 订单写入时是否计算了成本
- `OrderVO` 转换时是否保留了 `charge` 字段

如果手续费缺失，则每笔交易的净利润**偏高**，导致：
- 权益曲线整体偏高
- 最大回撤偏小（浮亏被盈利补偿掩盖）
- SharpeRatio 偏高（收益高估，波动低估）
- ProfitFactor 偏高

```
示例：
  实测权益曲线（已扣手续费）：
    100,000 → 99,500(扣费5) → 99,200(扣费3) → 103,000(扣费7)
    最大回撤 = (100,000 - 99,200) / 100,000 = 0.8%
  
  缺失手续费的权益曲线：
    100,000 → 99,505 → 99,205 → 103,014
    最大回撤 = (100,000 - 99,205) / 100,000 = 0.795% ❌ 偏低
```

**解决方案**：

| 方案 | 做法 | 优缺点 |
|:----|:----|:------|
| **方案 A（推荐）** | 策略执行阶段确保每笔订单写入 DB 时包含 `charge`，使用统一的费率模板 | 数据源头正确，下游无需补算；需要改造策略的订单写入逻辑 |
| 方案 B | 重建 TradingRecord 时，若 `charge` 为空，根据统一的费率配置（万分之 x 手续费 + y 滑点）补算 | 灵活兼容旧数据，但补算逻辑需要与策略执行时的费率保持一致 |
| 方案 C | 将 `totalCost` 从 PerformanceMetrics 中独立计算，不依赖订单级别 charge | 最简单，但失去了订单级成本细粒度 |

**实施建议**：组合方案 **A + B**：
- **优先方案 A**：在策略执行阶段确保 `closeOrder.setCharge(...)` 正确写入
- **回退方案 B**：在 `buildTradingRecordFromTradeRecords()` 中检测 `charge` 是否为 `null`/`0`，若缺失则根据统一的费率默认值补算

```java
// 重建 TradingRecord 时的手续费补算逻辑
private double resolveCharge(OrderVO order, BacktestConfig config) {
    if (order.getCharge() != null && order.getCharge().compareTo(BigDecimal.ZERO) > 0) {
        return order.getCharge().doubleValue();          // 优先使用订单原始数据
    }
    // 补算：按成交金额 * 费率
    double turnover = order.getPrice() * order.getAmount();
    return turnover * config.getFeeRate();               // 默认费率补算
}
```

#### ★ 风险 5（严重）：空头方向处理错误 → 权益曲线完全错误

**问题描述**：

ta4j 原生的 `TradingRecord` 和 `Position` 对**做空（SHORT）**方向的支持有限：

- `Position` 默认构造方法假设 `entry = BUY`（多头）
- `Order.OrderType` 有 `BUY` 和 `SELL`，但 `TradingRecord` 的 `getCurrentPosition()` 内部逻辑硬编码了 `entry = BUY` 的假设
- 传统回测如果支持做空（SHORT 方向：`SELL` = enter, `BUY` = exit），重建 `TradingRecord` 时方向处理错误会导致权益曲线完全错误

```
正确做空逻辑：
  开仓：SELL 100 股 @ 100 → 空头持仓
  平仓：BUY  100 股 @ 80  → 盈利 (100-80)*100 = 2,000
  权益曲线：100,000 → 102,000 ✅

错误做空逻辑（被当多头处理）：
  开仓：SELL 100 股 @ 100 → 被当作 entry
  平仓：BUY  100 股 @ 80  → 被当作 exit，认为亏损 2,000
  权益曲线：100,000 → 98,000 ❌（方向完全反了）
```

**解决方案**：

| 方案 | 做法 | 优缺点 |
|:----|:----|:------|
| **方案 A（推荐）** | 做空时，将空头交易的 entry/exit 在 `TradingRecord` 级别**统一转换为多头语义**：空头开仓（SELL）→ 记录为 `OrderType.BUY`（买开），空头平仓（BUY）→ 记录为 `OrderType.SELL`（卖平），持仓方向和盈亏符号在校验后统一修正 | ta4j 原生支持，不需要修改 ta4j 源码；但需要在转换时正确反转 PnL 的符号 |
| 方案 B | 改造 `TradingRecord` 或自定义实现支持做空 | 需要修改或扩展 ta4j 核心类，维护成本高 |
| 方案 C | 做空和做多分开处理：做多的 `TradingRecord` 正常重建，做空的单独记录 PnL，在计算时聚合 | 逻辑分支多，代码复杂，容易遗漏 |

**实施建议**：采用**方案 A**。`buildTradingRecordFromTradeRecords()` 中检测订单方向：

```java
private TradingRecord buildTradingRecordFromTradeRecords(
        List<TradeRecord> tradeRecords, BarSeries series) {
    BaseTradingRecord tradingRecord = new BaseTradingRecord();
    
    for (TradeRecord trade : tradeRecords) {
        OrderVO entryOrder = trade.getEntryOrder();
        OrderVO exitOrder = trade.getExitOrder();
        
        if ("SHORT".equals(trade.getDirection())) {
            // 做空：转换为多头语义
            // 注意：PnL 符号需要保持正确（空头盈利 = 价格下跌）
            Order buyOrder = createOrder(series, entryOrder, Order.OrderType.BUY);
            Order sellOrder = createOrder(series, exitOrder, Order.OrderType.SELL);
            // 由于方向反转，PnL 和 closePrice 需要在后续指标计算中处理
            tradingRecord.operate(buyOrder);
            tradingRecord.operate(sellOrder);
        } else {
            // 做多（LONG）：正常处理
            Order buyOrder = createOrder(series, entryOrder, Order.OrderType.BUY);
            Order sellOrder = createOrder(series, exitOrder, Order.OrderType.SELL);
            tradingRecord.operate(buyOrder);
            tradingRecord.operate(sellOrder);
        }
    }
    
    return tradingRecord;
}
```

⚠️ **重要提示**：方案 A 虽然在 `TradingRecord` 层面统一了方向，但空头交易的 PnL 计算逻辑与多头不同。需要在 `MetricsCalculationService.calculateByTradingRecord()` 中确认，ta4j 的 `GrossReturnCriterion` 和 `SharpeRatioCriterion` 是否兼容这种方向转换后的 `TradingRecord`。如果不兼容，则需要自定义 Criterion 或单独处理空头交易的 PnL。

| 风险 | 严重度 | 影响指标 | 推荐方案 |
|:----|:-----|:--------|:--------|
| 未平仓持仓丢失 | **严重** | finalValue, totalReturn, annualReturn, sharpeRatio 等一切依赖最终权益的指标 | 策略执行完毕后强制平仓 |
| 权益曲线粒度不足 | 中等 | maxDrawdown, calmarRatio | 按 K 线粒度计算权益曲线 |

| 空头方向处理错误 | **严重** | 所有指标（权益曲线完全错误） | 统一转换为多头语义 |

## 十、关键设计决策

### 决策 1：为什么不直接让传统回测算完写入 DB，再读取展示？

因为当前架构中传统回测和快速回测共用 `BacktestResultSaveService.saveBacktestResult` 保存链路，从 DB 读回展示。改造后两类回测计算出完整的 16 个指标后，走同一条保存链路，前端无需区分回测类型。

### 决策 2：传统回测是否需要走 ta4j TradingRecord？

需要。理由：
- 权益曲线和回撤计算已依赖 ta4j 的 `TradingRecord`
- 共享 `MetricsCalculationService` 依赖 `TradingRecord` 作为输入
- 订单 DB 转换为 `TradingRecord` 的逻辑在 `calculateEquityAndDrawdown()` 中已存在，提取即可

### 决策 3：传统回测和快速回测的计算结果是否能完全一致？

不完全一致，但**口径一致**：
- 快速回测的 `TradingRecord` 来自 ta4j 引擎模拟，适合用 ta4j Criterion 计算
- 传统回测的 `TradingRecord` 来自真实订单重建，也适合用 ta4j Criterion 计算
- 两者都用同一套 `MetricsCalculationService`，同一公式，同一口径
- 差异仅来自底层数据源不同（模拟 vs 真实），不应来自计算逻辑不同

### 决策 4：是否需要为传统回测保留独立计算路径？

**不需要**。只要 `calculateTraditionalMetrics()` 中的 `TradingRecord` 重建逻辑正确，就可以直接复用 `MetricsCalculationService`。独立路径会增加维护成本，且会导致指标口径不一致。

## 十一、改造前后对比

### 传统回测链路

**改造前**：
```
策略执行 → 订单 DB → 重建 TradeRecord → calculateEquityAndDrawdown()
                                           → calculateTraditionalMetrics()（简陋）→ 8 个基础指标
```

**改造后**：
```
策略执行 → 订单 DB → 重建 TradeRecord → calculateEquityAndDrawdown()
                                           → buildTradingRecordFromTradeRecords()
                                           → MetricsCalculationService.calculateByTradingRecord()
                                           → 16 个完整指标
```

### 快速回测链路

**改造前**：
```
ta4j 引擎 → TradingRecord → BacktestEngine.calculateMetrics()（有正确数据但映射丢失）
                              → BacktestService.buildBacktestResponse()（字段丢失）
                              → 前端只拿到 8 个基础指标
```

**改造后**：
```
ta4j 引擎 → TradingRecord → BacktestEngine.calculateMetrics()（新增 10 个指标计算）
                              → BacktestService.buildBacktestResponse()（完整映射）
                              → 16 个完整指标
```
