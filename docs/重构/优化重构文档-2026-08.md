# Lenzeto 优化与重构文档

> **版本**：2026-08-17 · 基于当前源码盘点  
> **关联**：[后端重构计划](./Lenzito-后端重构计划.md) · [执行清单](./执行清单.md) · [MarketKlineV1 组件化](../componentization/MarketKlineV1组件化方案.md) · [REFACTORING_PLAN](../REFACTORING_PLAN.md)  
> **原则**：先护栏与边界，再拆 God Class；不做过早微服务；每步可编译、可回归

---

## 1. 执行摘要

Lenzeto（灵猞量化）是 **Maven 模块化单体 + Vue3 主控台**：可启动应用仅 `ai-quant`（REST/WS）与 `ai-task`（XXL-JOB）。业务域模块（信号/订单/风控/策略等）概念清晰，但存在三类核心债务：

| 维度 | 现状 | 影响 |
|------|------|------|
| **巨型单体** | 前端 `MarketKlineV1.vue` ~1.3 万行；后端多处 1k～4k 行 God Class | 难测、难改、热更新/首屏成本高 |
| **边界泄漏** | 库模块内嵌 Controller；`ApiResponse` 三份；ML 仍在 `ai-quant`；Job 分散 | 依赖网状、任务节点过重 |
| **护栏缺失** | 正式单测约 6 个 Java + 前端几乎无用例；覆盖率粗估 &lt;2% | 重构无安全网 |

**目标**：在 4～6 个迭代内，把「可维护性」推到可安全演进状态——统一 API 契约、收敛引擎、拆分热点、补最小测试护栏；**不**追求一次微服务拆分。

## 2. 现状架构（简图）

```text
Browser / Mobile
       │  REST + STOMP/WS
       ▼
  ai-quant (:8118)  ←── ComponentScan 拉起几乎全部库模块
       │
  ai-task (XXL-JOB) ←── 仍偏重依赖（目标：切断 → ai-quant）

库模块：ai-engine(engine2) · ai-signal · ai-order · ai-risk · ai-strategy
       ai-data · ai-backtest · ai-member · ai-agent · ai-logs · ai-extension · ai-xchange-extends
规划：ai-ml（尚未建模块，代码在 ai-quant）
废弃：ai-account（空占位）
```

**数据主路径**

1. 行情：Job 采集 → MySQL / Redis → `KLineV1Service` → REST/WS → 图表  
2. 信号：指标 / 权重规则 / SMC → 技术信号 & 业务信号 → 机器人  
3. 交易：信号或手动 → `TradeOrderServiceImpl` → 交易所直连  
4. 回测/实盘：`engine2`（Backtest / Paper / Live）→ 持久化 Gateway

### 3.3 结构性债务

| 项 | 现状 | 目标 |
|----|------|------|
| 双引擎 | `engine.*` 残留 + `engine2.*` 自研并存 | 文档化删除时间线；新功能只进 engine2 |
| ApiResponse | `ai-common` + `ai-quant` dto + vo **三份** | 只保留 `ai-common` 一处 |
| HTTP 在库模块 | member / signal / logs / agent 含 Controller | Controller 上收 `ai-quant`（或未来 `ai-api`） |
| ML | `ai-quant/.../service/ml/**` | 新建库模块 `ai-ml` |
| Job | `ai-quant/jobhandler` 与 `ai-task` 并存 | 调度入口收敛到 `ai-task` |
| JSON | Jackson + fastjson + org.json | 新代码只用 Jackson；存量逐步替换 |
| FeatureVector | quant / signal 各一份 | 合并到单一模块 |
| DB 迁移 | 手写 SQL 在 `docs/db/` | 引入 Flyway/Liquibase（中期） |
| 文档 | README / 完整架构文档部分过时 | 补「实现状态」表；端口与启动命令对齐 |

## 4. 性能优化关注点

| 区域 | 风险 | 方向 |
|------|------|------|
| K 线图表 | 大批量 `setData`、多均线重复 `addSeries`、Vue 深响应式 | 非响应式缓冲 + 按需更新；见均线性能分析 |
| K 线查询 | 冷路径直打 MySQL | 落实 Redis ZSET 缓存设计 |
| 回测 | 大区间内存、MTF | 保持循环内零 DB；批量写；限制并发回测 |
| 信号 Job | MACD/SMC/艾略特重计算 | 线程池隔离；结果复用（见 SMC 复用方案） |
| 订单 | 长事务 + 锁 | 对照 `ai-order` 并发指南审边界 |
| 前端包体 | monaco / echarts / chart.js / lightweight-charts 并存 | 按路由懒加载；淘汰重复图表库 |

## 5. 分阶段路线图

与 [执行清单](./执行清单.md) 对齐，并补前端与性能轨。

### 阶段 0 — 基线与护栏（进行中）

- 完成 bin ignore、空模块决策、文档对齐（README / 架构「实现状态」）
- 固化回归用例 R1～R5（K 线 / 信号 / 下单 / 回测 / 登录）
- **验收**：主应用可启、全量 compile、无脏产物

### 阶段 1 — 边界清晰化

1. 新建 `ai-ml`，迁出 ML/因子代码  
2. 统一 `ApiResponse`；库模块去 web starter / 上收 Controller  
3. 切断 `ai-task → ai-quant`（引入薄依赖或 scheduler 包）  
4. **验收**：`ai-ml` 独立 compile；task 不再传递依赖整个 quant Web

### 阶段 2 — God Class 与前端热点（可并行两条线）

**后端线**（每拆一类先补 1 个表征测试）：

1. `TradeOrderServiceImpl`  
2. `ElliottWaveEvaluator`  
3. `MacdSignService` / `DefaultSignService`  
4. 巨型 Controllers → Application Service  

**前端线**：

1. `MarketKlineV1` 按组件化方案拆分（优先：图表壳 / 指标层 / 信号层 / WS）  
2. 均线与 SMC 渲染性能  
3. `api/base.ts` 响应适配收敛  

### 阶段 3 — 测试与可观测性

- 回测一致性、下单校验链、K 线缓存命中的最小集成测  
- 关键路径结构化日志与指标（下单失败率、回测耗时、缓存命中率）  
- **目标**：核心路径有回归；覆盖率从 &lt;2% 提升到「有护栏」而非虚高数字

### 阶段 4 — 收敛与卫生（可选）

- 删除旧 `engine` 残留；包名与 artifact 对齐（成本高，可延后）  
- DB 迁移工具化；JSON 库统一  
- 前端重复图表库清理

## 6. 建议实施顺序（接下来 2～4 周）

| 周次 | 事项 | 产出 |
|------|------|------|
| W1 | 收尾阶段 0 文档/卫生；统一 ApiResponse | PR：契约统一 |
| W1～W2 | `MarketKlineV1` 第一刀（抽出 2～3 个 composable/子组件，壳降到 &lt;8k） | 可合并的垂直切片 |
| W2 | `ai-ml` 骨架 + 无 HTTP 类首批迁移 | 新模块可 compile |
| W3 | `TradeOrderServiceImpl` 拆出校验/下单协作类 + 1 个单测 | 门面变薄 |
| W3～W4 | K 线 Redis 缓存落地或均线性能优化二选一（按线上痛点） | 可测的性能收益 |

**不做**：同期大包重命名、一次删光旧引擎、全面微服务化。

## 7. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 拆分引入行为回归 | 每步 R1～R5；关键类先测后拆 |
| 双引擎并存行为不一致 | 新功能只写 engine2；对比回测抽样 |
| 前端拆分破坏 K 线交互 | 按方案「壳保留、逻辑外提」；每 PR 手工点图表 |
| task 断依赖失败 | 先列 quant 传递依赖清单，再逐个下沉到库模块 |
