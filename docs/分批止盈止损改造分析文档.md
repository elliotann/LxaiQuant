# 分批止盈止损改造分析文档

> 文档目的：分析现有系统止盈止损实现，提出分批止盈止损的改造方案

---

## 一、现有系统架构分析

### 1.1 核心数据模型

| 模型 | 作用 | 关键字段 |
|------|------|----------|
| `TradeOrder` | 订单主表 | `lossPrice`, `gainPrice`, `volume`, `closedVolume` |
| `TradeOrderItem` | 订单项（开仓批次） | `lossPrice`, `gainPrice`, `volume`, `closedVolume`, `orderItemSn` |
| `TradeOrderClose` | 平仓记录 | `orderSn`, `closedVolume`, `sellPrice`, `closeOrderType`(ExitType), `closeMethod` |
| `OrderVO` | 订单视图 | `lossPrice`, `gainPrice`, `volume`, `orderSide` |

### 1.2 出场类型枚举（ExitType）

```
STOP_LOSS                // 固定止损
TAKE_PROFIT              // 固定止盈
FIXED_PERCENT_TAKE_PROFIT // 固定百分比止盈
BATCH_TAKE_PROFIT        // 分批止盈
TRAILING_STOP_LOSS       // 移动止损
TRAILING_STOP_GAIN       // 移动止盈
TECHNICAL_INDICATOR      // 技术指标出场
SIGNAL_REVERSAL          // 信号反转出场
ORDER_ITEM_TAKE_PROFIT   // 订单项止盈（补仓批次独立止盈）
TIME_TAKE_PROFIT         // 时间止盈
TIME_STOP_LOSS           // 时间止损
PROFIT_TARGET            // 目标位止盈
ORDER_BLOCK              // 订单块出场
SMC_EXIT                 // SMC出场
MACD_GOLDEN_CROSS        // MACD金叉出场
MACD_DEAD_CROSS          // MACD死叉出场
```

### 1.3 现有分批止盈流程

```
ExitRulesConfig (exit_rules配置)
  ├── batchTakeProfitEnabled    // 分批止盈开关
  ├── batchTakeProfitCount      // 批次数
  ├── batchTakeProfitPercents   // 各批次盈利百分比 [5%, 10%, 15%]
  ├── batchTakeProfitRatios     // 各批次仓位比例 [30%, 30%, 40%]
  └── batchPlans                // 完整方案列表 [{percent, amount/ratio}]

执行流程:
  1. processPositionExits() 遍历持仓订单
     └── handleBatchTakeProfit(order, series, endIndex, params)
          2. BatchTakeProfitRule 检查价格是否触发某批止盈线
          3. Redis key "strategy:batchTakeProfit:orderSn:{sn}" 记录已执行到的批次索引
          4. 根据索引从 batchTakeProfitPercents/Ratios 取出比例
          5. 计算目标平仓量 = totalOpen * ratio
          6. 调用 adapter.closePartialPosition(orderSn, target, price, time)
          7. 批次索引+1，存入Redis
```

### 1.4 固定百分比止盈止损

开仓时在 `createDirectionalOrder()` 中根据 ExitRulesConfig 计算：
- `lossPrice` = entryPrice × (1 ∓ percent/100) 写入 TradeOrder
- `gainPrice` = entryPrice × (1 ± percent/100) 写入 TradeOrder

平仓时在 `closePosition()` 中按 ExitType 使用对应价格：
- `STOP_LOSS` → `order.getLossPrice()`
- `TAKE_PROFIT` / `FIXED_PERCENT_TAKE_PROFIT` → `order.getGainPrice()`

### 1.5 补仓场景的止盈处理

补仓（suppOrder）时创建的 `TradeOrderItem` 包含独立的 `gainPrice`，引擎在 `determineOrderItemTakeProfitExit()` 中逐项检查：
- 遍历 `TradeOrderItem`，检查其 `gainPrice` 是否被K线高低价触及
- 若触发，调用 `closeOrderByVolumeExact(orderSn, itemOpenVolume, price, time, ORDER_ITEM_TAKE_PROFIT)`
- 该机制实现了**按补仓批次独立止盈**

### 1.6 现有移动止盈止损（Trailing Stop）流程

移动止盈止损由 ExitRulesConfig 中的两套配置控制：

```
止损侧 (stopLoss → fixed_percent_trailing):
  trailingStopLossEnabled   // 移动止损开关
  trailingStopLossPercent   // 回撤百分比（如 0.03 = 3%）
  trailingStopLossBarCount  // 极值回溯窗口K线数

止盈侧 (takeProfit → fixed_percent_trailing):
  trailingStopGainEnabled   // 移动止盈开关
  trailingStopGainPercent   // 回撤百分比（如 0.03 = 3%）
  trailingStopGainBarCount  // 极值回溯窗口K线数
```

**执行流程**：
```
buildExitDecisionReason() 中检查各退出规则:
  1. fixedPercentStopLoss → "FIXED_PERCENT_STOP_LOSS"
  2. trailingStopLoss    → "TRAILING_STOP_LOSS"     ← 移动止损
  3. fixedPercentTakeProfit → "FIXED_PERCENT_TAKE_PROFIT"
  4. trailingStopGain    → "TRAILING_STOP_GAIN"     ← 移动止盈
  5. batchTakeProfit     → "BATCH_TAKE_PROFIT"
  6. technical indicators... → MACD, PIN_VOLUME 等

→ closePosition() 中根据 decisionReason 映射 ExitType
→ adapter.closeOrderByVolume(orderSn, volume, price, time, exitType)
  （全量平仓，非分批）
```

**两套 Rule 实现对比**：

| 特征 | ExtTrailingStopLossRule / ExtTrailingStopGainRule | DirectionalTrailingStopRule |
|------|--------------------------------------------------|-----------------------------|
| 位置 | ai-strategy | ai-extension |
| 用途 | `buildExitDecisionReason()` 中的检查 | consolidated exit rules（indicator_driven / multi_direction 策略） |
| 价格指标 | ClosePriceIndicator | 多头用 HighPriceIndicator，空头用 LowPriceIndicator |
| 方向感知 | 通过 `getCurrentPosition().getEntry().isBuy()` 判断 | 通过构造时传入的 TradeType 判断 |
| 多仓位支持 | 仅当前 Position（ta4j 标准） | MultiPositionTradingRecord（含平均入场价） |
| 状态管理 | 内部维护 lastStop / lastPositionIndex | 内部维护 lastStop / lastBarIndex |
| 返回值 | `boolean isSatisfied()` | `ExitSignal getSignal()` |

**移动止损核心算法**（以多头为例）：
```
1. 在回溯窗口内找最高价 extreme
2. 理论止损价 = extreme × (1 - lossPercentage)
3. 若理论止损价 > 当前止损价 → 止损价上移（只向有利方向锁）
4. 若当前价 ≤ 止损价 → 触发
5. 空头对称：最低价 → 理论止损价 = extreme × (1 + lossPercentage)
```

**SMC 移动止损**：
SMC 出场配置中也有独立的移动止损：
```
smcUseTrailingStop = true
smcTrailingStopPercent = 0.05    // 5% 回撤
```
由 SMC 出场逻辑内部实现，与上述通用移动止损相互独立。

## 二、现有方案的问题与不足

### 问题 1：分批止盈按订单独立执行，未跨订单聚合

当前 Redis key 的格式是 `strategy:batchTakeProfit:orderSn:{sn}`，每个订单独立维护批次索引。
- 如果有补仓（suppOrder），主订单和补仓订单各自独立执行分批止盈
- 无法在整个持仓级别（所有同方向订单）上统一管理分批止盈

**示例问题**：
```
初始开仓 100张，batchTakeProfitRatios = [30%, 30%, 40%]
触发第一档 → 平掉 30张（订单A）
补仓 50张（订单B）
触发第二档 → 订单A又平 30%（基于订单A剩余量），而不是基于总持仓
```

**期望**：
```
总持仓 = 初始开仓100张 + 补仓50张 = 150张
第一档止盈 → 平掉 150×30% = 45张（按FIFO/LIFO匹配到订单A、B）
第二档止盈 → 平掉 150×30% = 45张
```

### 问题 2：无分批止损

目前仅支持分批止盈（`batchTakeProfitEnabled`），没有对应的分批止损。
- 止损只有单一价格（`lossPrice`）
- 不支持分批止损（例如：跌到 -3% 平掉 30%，跌到 -5% 平掉 70%）

### 问题 3：分批止盈与按批独立止盈（ORDER_ITEM_TAKE_PROFIT）冲突

`ORDER_ITEM_TAKE_PROFIT` 是为每个补仓批次设置的独立止盈价，而 `BATCH_TAKE_PROFIT` 是策略级别的多级止盈。
- 两者可能同时触发，造成重复平仓
- 缺乏明确的优先级规则

### 问题 4：批次状态无持久化

批次索引存储在 Redis 中（TTL 7天），系统重启或Redis丢失后批次索引重置为0，导致：
- 已执行过的止盈档位重新执行
- 无法查询历史批次执行情况

### 问题 5：无前端可视化

- 无法查看当前仓位已触发的批次
- 无法查看每批的盈亏详情
- 无法手动干预（如跳过某批止盈）

### 问题 6：批量平仓与订单项级别止盈的交互不清晰

当同时启用分批止盈（BATCH_TAKE_PROFIT）和订单项止盈（ORDER_ITEM_TAKE_PROFIT）时：
- `processPositionExits` 中先处理 `ORDER_ITEM_TAKE_PROFIT` 再调用 `handleBatchTakeProfit`
- 若某订单项因 `ORDER_ITEM_TAKE_PROFIT` 被平掉，`getMultiPositionRecord().getOpenAmount()` 计算的总量可能不准确

### 问题 7：移动止盈止损总是全量平仓，无法分批

当前移动止盈止损（`TRAILING_STOP_LOSS` / `TRAILING_STOP_GAIN`）被触发时：
- 直接调用 `adapter.closeOrderByVolume(orderSn, volume, price, time, exitType)` 全量平仓
- 没有"分级移动止损"的概念，即无法实现：
  - 价格回撤 3% 时平掉 30%
  - 价格回撤 5% 时平掉 70%
- 在补仓场景下，移动止损触发时会平掉整个持仓（含所有补仓），缺少分批处理能力

**示例问题**：
```
开仓 100张（入场价 10000）
补仓 50张（入场价 10500）
最高涨到 11000，移动止损 5% → 止损价 = 11000 × 0.95 = 10450
价格回撤到 10450 → 触发移动止损 → 一次性平掉所有 150张
```
期望行为：先平补仓部分（亏损），保留初始仓位等待反弹。

### 问题 8：两套移动止损 Rule 实现不一致

`ExtTrailingStopLossRule` / `ExtTrailingStopGainRule` 与 `DirectionalTrailingStopRule` 的行为不完全一致：
- 前者用 ClosePrice 触发判断，后者用 High/Low 判断
- 前者不支持 MultiPositionTradingRecord，后者支持
- 前者在 `buildExitDecisionReason()` 中使用且不会交叉影响，后者在 consolidated exit rules 中可能被同时触发

### 问题 9：移动止盈止损与分批止盈的交互顺序不明确

在 `buildExitDecisionReason()` 中的检查顺序为：
```
trailingStopLoss → 先于 batchTakeProfit
trailingStopGain → 先于 batchTakeProfit
```
当价格先触发移动止损再触发分批止盈时，分批止盈将没有机会执行。
但若移动止损设置为较宽松的回撤，分批止盈先执行了部分平仓后，移动止损的回撤计算基数（持仓量）不再准确。

### 问题 10：移动止盈止损状态不可见

- 移动止损的 lastStop（当前止损价）存在 Rule 实例内存中，重启后丢失
- 无法查看当前仓位的移动止损价位、已锁定的利润空间
- 无法前端展示"移动止损已锁定到 XX 价位"

### 3.3 核心改造点

#### 改造点 1：策略级分批出场管理器（BatchExitManager）

**目标**：将分批止盈/止损从"每个订单独立执行"改为"策略级别统一管理"

**位置**：新增 `BatchExitManager` 类，替代现有的 `handleBatchTakeProfit` 方法

**功能**：
1. 查询当前方向所有持仓订单，计算总持仓量
2. 根据批次配置和触发价格计算应平仓量
3. 使用 `PositionMatcher` 将平仓量分配到具体订单
4. 调用 `closePartialPosition` 执行平仓
5. 记录批次执行到DB

```
BatchExitManager.executeBatchExit(series, endIndex, params, direction)
  │
  ├─ 1. 获取 ExitRulesConfig（含 batchTakeProfit 和 batchStopLoss 配置）
  │
  ├─ 2. 判断当前价格是否触发某批止盈/止损线
  │     ├─ 使用 BatchTakeProfitRule 判断止盈
  │     └─ 使用 BatchStopLossRule 判断止损（新增 Rule）
  │
  ├─ 3. 从DB查询已执行到的最大批次索引
  │     SELECT MAX(batch_index) FROM ai_trade_order_batch_exit
  │     WHERE strategy_id=? AND symbol=? AND side=? AND exit_type=?
  │
  ├─ 4. 若无新档位触发 → 返回
  │
  ├─ 5. 计算本次平仓量
  │     totalPosition = sum(all open orders volume)
  │     targetVolume = totalPosition × batchRatios[batchIndex]
  │
  ├─ 6. PositionMatcher.match(totalOpenOrders, targetVolume, strategy)
  │     ├─ FIFO: 从最早订单开始匹配
  │     ├─ LIFO: 从最晚订单开始匹配
  │     └─ PROPORTION: 按各订单持仓比例分配
  │
  └─ 7. 对各订单执行 closePartialPosition
       并记录批次执行到 DB
```

#### 改造点 2：PositionMatcher 匹配器

**位置**：新增 `PositionMatcher` 工具类

**策略**：

```java
public class PositionMatcher {
    // FIFO: 从最早的开仓订单开始匹配
    // LIFO: 从最晚的开仓订单开始匹配
    // PROPORTION: 按各订单当前持仓量比例分配平仓量
    
    public static List<MatchResult> match(
        List<OrderPosition> positions,  // 持仓列表（含 orderSn, remainingVolume, openTime）
        BigDecimal targetVolume,         // 需要平仓的总量
        MatchStrategy strategy           // FIFO / LIFO / PROPORTION
    );
}

class MatchResult {
    String orderSn;           // 订单号
    BigDecimal closeVolume;   // 该订单需要平仓的量
}
```

#### 改造点 3：MultiPositionTradingRecord 增强

在 `MultiPositionTradingRecord` 中：
1. 暴露 `getOpenPositions(direction)` 方法，返回当前方向所有持仓
2. 支持根据 `orderSn` 查询特定持仓量
3. 支持根据 `orderItemSn` 查询特定订单项持仓量

当前已有 `getOpenAmount(TradeType)` 返回总持仓量，需要补充按订单粒度查询。

#### 改造点 4：OrderVO 扩展（前端支持）


#### 改造点 6：分批移动止盈止损（BatchTrailingStop）

**目标**：将现有的全量移动止损/止盈改造为多级分批移动止盈止损，价格回撤到不同档位时平仓对应比例的头寸

**背景**：当前移动止损/止盈是"一触即发、全量平仓"，分批移动止盈止损允许用户设置多级回撤档位，在趋势回调时分批离场，既锁定利润又保留部分仓位等待趋势延续。

**核心算法（以多头分批移动止损为例）**：

```
入场后不断追踪最高价 extreme
每个档位维护独立的临时止损价：stopPrice[i] = extreme × (1 - retracePercent[i]/100)

触发判断：
  for each 未执行档位 i:
    if currentPrice <= stopPrice[i]:
      执行第 i 档 → 平仓 ratio[i] 比例
    
档位执行后锁定：
  一旦第 i 档触发，该档位的止损价不再变动（已触发）
  后续档位继续按最新 extreme 更新止损价
  若价格重新上涨，未触发档位的止损价继续上移
```

**示例**：
```
配置：batchTrailingStopLoss = [{retracePercent: 3, ratio: 30}, {retracePercent: 8, ratio: 70}]
开仓 100张，入场价 10000

价格涨到 11000：
  档0 止损价 = 11000 × 0.97 = 10670
  档1 止损价 = 11000 × 0.92 = 10120

价格继续涨到 11500：
  档0 止损价 = 11500 × 0.97 = 11155 ↑（上移锁定利润）
  档1 止损价 = 11500 × 0.92 = 10580 ↑

价格回撤到 11155 → 触发档0 → 平 30张（在11155锁定部分利润）
  档1 继续追踪：最新 extreme 保持 11500（不会因回调而降低）

价格后续若从 11500 再次回撤到 10580 → 触发档1 → 平剩余 70张
```

**核心创新**：
1. **多档位独立追踪**：每个档位有独立的回撤百分比，各自维护止损价
2. **档位锁定机制**：已触发的档位停止追踪，未触发的继续随价格移动
3. **极值不受已触发档位影响**：exterme 追踪不受中间回调影响
4. **配合 PositionMatcher**：分批平仓时按 FIFO/LIFO 分配到具体订单

**实现位置**：新增 `BatchTrailingStopLossRule` 和 `BatchTrailingStopGainRule`，或合并在 `BatchExitManager` 中作为统一逻辑

### 3.6 与现有机制的关系

#### 优先级规则（同一持仓同时触发时）

```
ORDER_ITEM_TAKE_PROFIT（补仓批次独立止盈）
  ↓ 高于
BATCH_TAKE_PROFIT（策略级分批止盈）
  ↓ 高于
BATCH_TRAILING_GAIN（分批移动止盈：追踪最高点回撤锁定利润）
  ↓ 高于
BATCH_STOP_LOSS（策略级分批止损：固定百分比止损）
  ↓ 高于
BATCH_TRAILING_LOSS（分批移动止损：追踪最高点回撤保护本金）
  ↓ 高于
SINGLE_PRICE_STOP_LOSS（单一价位止损：lossPrice 作为最后防线）
```

上述规则确保：
1. **补仓批次独立止盈优先执行**——如果补仓批次有独立的 gainPrice，先用它锁定利润
2. **策略级分批止盈次之**——整体按固定百分比分批锁定利润
3. **分批移动止盈作为跟随趋势的保护**——价格回撤时逐批锁定利润，保留部分仓位继续持有
4. **分批止损在回撤加深时启用**——固定百分比止损作为回撤保护
5. **分批移动止损跟随追踪**——在极端行情回调时保护本金
6. **单一止损价作为最后防线**——绝对止损价，永不失效

**执行顺序的设计原则**：
- **盈利优先**：先止盈再止损，优先锁定利润
- **固定优先**：移动止盈/止损的触发条件更动态，排在固定百分比之后，避免移动档位的动态止损价干扰固定档位的确定性
- **防线递进**：从宽松到严格，确保每个层级都有机会独立触发

#### 互斥规则

在同一个订单上，分批止盈（`batchTakeProfitEnabled`）和补仓批次独立止盈（`ORDER_ITEM_TAKE_PROFIT`）不应同时启用，应在业务逻辑层做参数校验。

## 附录 B：与智能加仓（SmartAddPosition）的关系

智能加仓功能（`SmartAddPositionRule` / `EnhancedMultiPositionTradingRecord`）是分批出场的重要前提：
- 加仓增加持仓量后，分批出场才有"分批次"的基础
- 加仓后的持仓包含多个成本价格，分批止盈应能自动匹配到最早批次（FIFO）以锁定利润
- 分批止损也应按成本排序，优先保护利润

分批出场改造应与智能加仓配合，确保：
1. `PositionMatcher` 的匹配策略与加仓批次管理一致
2. 加仓记录中的成本价用于计算分批出场的盈亏
3. 可视化界面同时展示加仓批次和出场批次
