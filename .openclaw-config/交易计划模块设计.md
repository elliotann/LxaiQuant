1. 引言
   1.1 背景
   当前量化交易系统已实现自动化信号生成和订单执行，信号表 technical_signal 存储技术指标信号，订单相关表（ai_trade_order、ai_trade_order_item、ai_trade_order_close）记录交易全过程。为进一步提升决策智能化水平，拟引入 AI 助手 OpenClaw，作为“决策副驾”，在现有信号基础上进行综合分析，生成更精细的交易计划，并交由原交易引擎执行。

1.2 目标
双向通信：OpenClaw 能调用量化系统 API 获取数据、执行操作；量化系统能通过自主聊天界面调用 OpenClaw 的 AI 能力。

决策增强：OpenClaw 结合技术信号和市场信息生成交易计划，计划经人工确认后执行，形成“信号 → AI 决策 → 人工确认 → 订单”完整链路。

实时交互：聊天界面支持 SSE 流式回复，提升用户体验；结构化数据可在前端渲染为图表。

可追溯：交易计划携带唯一 ID 和关联信息（信号 ID、对话 ID），便于复盘分析。

安全可控：所有交易指令必须经过人工确认，强制鉴权，支持幂等。

2. 总体架构
   2.1 核心组件
   OpenClaw：AI 核心，通过 Channel 接收外部消息，通过 Skill 调用量化系统 API。

量化系统后端：提供 REST API 供 OpenClaw 调用，包含信号查询、订单执行、计划管理等；同时运行交易引擎，定时扫描信号表或经确认后直接下单。

量化系统前端：自主开发的 Web 界面，包含自定义聊天组件，可发送消息至 OpenClaw 并接收 SSE 流式回复，渲染图表和计划卡片。

数据库：MySQL，存储信号、计划（可选）、订单等数据。

3. 详细设计
   3.1 OpenClaw 侧组件
   3.1.1 量化交易 Skill（quant-trader-skill）
   功能：将自然语言指令转换为对量化系统桥接 API 的调用。

实现：Node.js 模块，通过 HTTP 调用量化系统 /api/openclaw/* 接口。

3.1.2 HTTP/SSE 混合 Channel（当前实现）
功能：提供 HTTP 接口供量化系统前端调用，接收消息并返回 AI 回复，支持 SSE 流式输出。

端点：

POST /api/llm/generate：前端调用此接口发送用户消息，后端转发给 OpenClaw，并以 SSE 格式逐步返回回复内容。

说明：原文档中的 WebSocket Channel 作为可选未来增强，当前采用 SSE 实现流式效果，降低复杂度。

3.4 数据流程（核心）
3.4.1 被动模式：信号自动触发 OpenClaw 分析
信号产生：策略程序生成信号，写入 technical_signal 表，状态为 pending（或新增 status 字段）。

自动触发：量化系统后端监听信号表（可通过事件监听、定时扫描或消息队列），检测到新信号后，自动调用 OpenClaw 的 analyze_signal 能力（通过 /api/llm/generate 或直接调用 Skill）。

OpenClaw 分析：

OpenClaw 获取信号详情（包括 symbol、方向、强度等），结合当前市场数据、风险状况，生成分析结果。

分析结果包括：是否建议执行、建议仓位、建议入场类型（市价/限价/挂单）、建议止损价、建议止盈目标、置信度等。

更新信号表：OpenClaw 调用 PATCH /api/openclaw/signals/{signalId} 接口，将建议数据写入信号表的 suggested_* 字段，并生成一个 plan_uuid（即使不创建完整计划表，也可用此字段关联）。

前端展示：用户可在界面上看到信号已被 AI 分析，并显示建议卡片（含确认按钮）。确认后触发下单，流程同 3.4.4。

特点：无需用户主动询问，信号产生即触发 AI 分析，实现自动化辅助决策。

3.4.2 主动模式：纯 AI 计划（用户聊天触发）
用户触发：用户在聊天界面输入指令，如“帮我制定一个 BTC 今日的交易计划”。

OpenClaw 生成计划：

OpenClaw 分析当前市场，生成包含入场、止损、止盈、仓位等的完整计划。

若计划需要与信号表关联（例如作为新信号供引擎扫描），则 OpenClaw 可同时创建一条信号记录，写入 technical_signal 表，填充 plan_uuid、suggested_* 字段，并标记 execution_type（如 limit 表示挂单，market 表示市价立即执行）。

计划落库：调用 POST /api/openclaw/trade-plans 将计划存入 ai_trade_plan 表（如采用路线 B），状态为 pending。

前端展示：返回计划卡片给用户预览，用户确认后执行。

信号表扩展说明：

通过 execution_type 字段区分挂单（limit）和市价单（market），交易引擎可根据该字段决定下单方式。

suggested_price 为限价单的指定价格；suggested_stop_loss 和 suggested_take_profit 作为建议止损止盈，交易引擎可在下单时附加条件单，或由后续风控模块处理。

3.4.3 计划执行状态查询
用户询问：“计划 abc 执行得怎么样了？”

OpenClaw 调用：GET /api/openclaw/trade-plans/{plan_uuid}，获取计划详情及关联的订单列表（通过 order_ids 字段或关联查询）。

返回结果：OpenClaw 返回自然语言描述，并可附带结构化数据（如订单列表、盈亏），前端渲染为表格或图表。

3.5 交易计划模块（核心流程）
3.5.1 设计目标
辅助决策：OpenClaw 生成的结构化交易计划，供用户在 UI 预览和确认，而非全自动执行。

安全可控：所有交易指令必须经过人工确认（Confirm）后才发往交易引擎。

可追溯：计划需携带唯一 ID 和关联信息（如信号 ID、对话 ID），便于后续复盘。

灵活扩展：当前以“副驾式半自动”为主，未来可平滑过渡到全自动落库执行模式。

3.5.2 两条可选路线
路线 A（推荐当前落地）：计划 = 可视化预检 + 人工确认

流程：

OpenClaw 生成计划（含入场、止损、止盈、仓位、风险检查等），返回给前端。
前端以卡片形式展示计划摘要，并附带 previewId（预检 ID）和 planUuid。
用户审阅后，点击“确认”按钮，前端调用 /api/openclaw/trade-plans/{planUuid}/confirm 接口，携带 previewId。
后端验证后，直接调用交易引擎下单（或通过原有订单接口），并记录订单与计划的关联。
此路线不强依赖 ai_trade_plan 表，但为追溯可选择性落库（如只记录 planUuid 和 order_ids）。
优点：快速落地，与现有“副驾式半自动”模式无缝衔接，无需改造交易引擎扫描逻辑。

路线 B（产品化/复盘驱动）：计划落库 + 引擎扫描

流程：

OpenClaw 生成计划，调用 /api/openclaw/trade-plans 将计划存入 ai_trade_plan 表，状态为 pending。
交易引擎定时扫描该表，获取待执行计划，按 plan_content 中的指令下单。
执行后更新计划状态和 order_ids。
优点：适合全自动策略、批量执行、历史复盘。

缺点：需改造交易引擎，增加扫描模块，适合未来系统演进。

文档后续内容以路线 A 为主，同时标注路线 B 的扩展点。

3.5.3 计划对象规范（plan_content 字段）
为使计划具备可执行性和可复盘性，plan_content 必须包含以下核心字段：

字段	类型	必填	说明
symbol	string	是	交易对，格式与交易引擎一致，如 BTC-USDT-SWAP
side	string	是	方向，统一为 LONG 或 SHORT（引擎内部可映射为 BUY/SELL）
entry	object	是	入场条件：包含 type（market/limit/stop/stop_limit）、price（限价时）、stopPrice（止损触发价）、timeCondition（时间条件）、executeTime、triggerPrice 等
stopLoss	object	是	止损规则：type（固定价/ATR/结构）、price 或 distance（如 2%）
takeProfit	array	是	止盈目标列表：每个目标含 price 或 percent、volume（分批平仓比例）
quantity	number	是	开仓数量或金额（与 quantityType 配合，如 fixed/percent）
riskChecks	object	否	风险检查：maxLossAmount、maxPositionPercent、leverage、cooldownSeconds
executionPolicy	object	否	执行策略：orderType（市价/限价）、slippageTolerance、timeInForce、cancelAfter
idempotencyKey	string	是	幂等键（由 OpenClaw 生成，防重复确认/下单）
trace	object	是	追溯信息：signalIds、conversationId、userId、requestId
previewId	string	是	预检 ID（后端生成，确认时携带）
入场条件细化：

子字段	类型	必填	说明
type	string	是	价格类型：market（市价）、limit（限价）、stop（止损市价）、stop_limit（止损限价）
price	number	否	当 type 为 limit 或 stop_limit 时必填，指定价格
stopPrice	number	否	当 type 为 stop 或 stop_limit 时必填，触发价
timeCondition	string	否	时间触发条件：immediate（立即）、at_time（指定时间）、price_trigger（价格触发）、candle_close（K线收盘）、manual（人工）
executeTime	string	否	当 timeCondition 为 at_time 时必填，ISO 格式时间戳
triggerPrice	number	否	当 timeCondition 为 price_trigger 时必填，触发价格

3.5.5 追溯字段说明
planUuid：计划唯一标识，由 OpenClaw 生成，用于查询和确认。

previewId：预检 ID，由后端生成并返回，确认时携带，用于防止重复确认、确保预览内容未被篡改。

trace.conversationId：关联的 OpenClaw 对话 ID，可追溯完整的对话上下文。

3.7 多轮对话管理
前端在首次发送消息时不传 conversation_id，后端生成并返回（在 SSE 的 done 事件中）。

4. 安全设计
   强制鉴权：所有 /api/openclaw/* 接口必须验证请求头中的 X-API-Key，与后端配置的 OPENCLAW_BRIDGE_TOKEN 匹配。若该环境变量未配置，接口应直接返回 503 并拒绝服务，防止因配置遗漏导致接口暴露。

幂等保障：idempotencyKey 由 OpenClaw 生成，后端记录已处理的键，确保同一请求不会被重复执行。

下单限额：下单前校验订单金额、数量是否超过用户/系统预设上限，防止 AI 误操作或恶意调用。

人工确认：任何实际下单操作必须经过用户点击确认，后端接口需验证 previewId 的有效性和时效性（如 5 分钟内有效）。

操作审计：所有通过 OpenClaw 触发的操作记录到日志表（可选），便于追溯。

5. 实施步骤建议
   环境准备：确认 OpenClaw 版本，熟悉插件开发流程；配置 OPENCLAW_BRIDGE_TOKEN 环境变量。

数据库扩展：执行 technical_signal 表的扩展 DDL，增加 plan_uuid、suggested_* 等字段；按需创建 ai_trade_plan 表。

开发 Skill：实现 quant-trader-skill，包含 get_trading_signals、execute_order、check_risk、create_trade_plan、analyze_signal 等动作，测试调用桥接 API。

开发后端桥接接口：实现 /api/openclaw/* 各端点，包括信号更新接口 PATCH /api/openclaw/signals/{signalId}，确保鉴权、幂等、限额等功能。

实现信号自动触发：在量化系统后端添加监听器（如数据库触发器、定时任务），新信号产生时自动调用 OpenClaw 分析接口。

修改前端：集成聊天组件，支持 SSE 流式接收、计划卡片和信号分析卡片渲染；实现确认按钮逻辑。

测试：先仿真环境，验证被动模式（信号自动触发分析）、主动模式（聊天生成计划）、确认执行全流程，确保幂等和安全控制有效。
